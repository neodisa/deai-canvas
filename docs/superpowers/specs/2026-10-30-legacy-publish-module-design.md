# Етап 4b-1: публікація простору ЛІГА через модуль `vercel-publish` (0.9.0)

Дата: 30.10.2026. Попередній етап — 4a (0.8.0, git як модуль). Дорожня карта етапу 4 — `docs/design/spaces-and-modules.md`.

## Рішення власника

- **26.10.2026 (етап 4):** чисте ядро + паритет — усе, що вміє ЛІГА, стає модулями, ЛІГА згодом переходить на Deai без
  втрат. 4b — стара публікація й коментарі ЛІГИ переїжджають на наявні модулі, зашиті константи й профілі йдуть з ядра.
- **26.10.2026:** доступ до віддалених систем — через СИСТЕМНІ інструменти людини; Deai секретів не зберігає (для git це
  вирішено в 4a; тут — те саме для Vercel: вхід `vercel login` на машині).
- **30.10.2026:** 4b ділиться на три релізи: **4b-1** публікація (ця спека, 0.9.0) → **4b-2** коментарі й константи
  Supabase (0.10.0) → **4b-3** профілі (0.11.0).
- **30.10.2026:** ЛІГА теж прибирає старі публікації на Vercel, лишаючи 3 найновіші (як модуль). Постійні адреси
  `pv-…vercel.app` живуть; перестають відкриватись лише прямі адреси старих публікацій.

## Проблема

Публікація ЛІГИ — ≈200 рядків транспорту у `app/serve.py` (`Handler._publish`, гілка `'legacy'`, і помічники
`_deploy_urls`, `_stable_alias`, `_check_published`, `_remember_vercel_scope`, `_deploy_hint`): `npx vercel link` +
`vercel deploy --prod` під входом машини, без токена. Модуль `vercel-publish` уміє лише REST API з токеном простору,
тому ЛІГА не може ним публікувати: кожному дизайнерові довелося б завести токен, а стан проєкту (імʼя, scope) у ЛІГИ
лежить у `tasks.json` (і їде в реєстр), а не в `iterations.json.publish_remote`. До того ж ЛІГА ніколи не прибирає
старих публікацій — 09.10.2026 це вперлося в ліміт сховища Vercel.

## Мета

1. Модуль `vercel-publish` отримує другий спосіб входу — **системний Vercel CLI** (`auth: cli`), доступний будь-якому
   простору: без токена, той самий набір команд, що ЛІГА використовує сьогодні, і прибирання старих публікацій.
2. ЛІГА публікує через цей модуль як **неявний постачальник** (за зразком 4a: `vcs_provider` + `_vcs_legacy_ctx`):
   ядро будує контекст ЛІГИ, кличе модуль і складає відповідь ЛІГИ.
3. Транспорт Vercel зникає з `serve.py`.
4. Паритет: збірка, `iterations.json`, `tasks.json`, реєстр, дашборд, автокоміт і відповідь `/api/publish` для ЛІГИ —
   ті самі, що в 0.8.0. Свідомі відмінності — лише прибирання (рішення власника) і один новий необовʼязковий ключ
   відповіді (`cleanup_warning`).

## Не мета (і де це буде)

- Коментарі, `SUPABASE_URL`/`SUPABASE_KEY`, `COMMENT_SNIPPET`, `/api/comment-config` — 4b-2.
- Профілі, `PROFILE_REPOS`, `work_root`, чипи «Задач» — 4b-3.
- Реєстр (`_registry_push`), дашборд (`_overview_sync`) — лишаються викликами ядра для ЛІГИ; у ролі `dashboard` — 4c.
- Мінт імені проєкту ЛІГИ в `tasks.json` (`_vercel_project`), пароль превʼю ЛІГИ (`preview_password`,
  `/api/preview-password`), `git_autocommit` після публікації — лишаються в ядрі як адаптер ЛІГИ до 4d.
- Літерал `'legacy'` у `capabilities.publish` (смуга, палітра, золоті знімки) — не змінюється до 4d.
- Перевірка превʼю в режимі `token` лишається як є (200 = `verified`); уніфікація з перевіркою гейта — беклог.
- `ops/reseal_gate.py` — без змін (збірка ЛІГИ лишається з міткою `build: legacy`).

## Дизайн

### 1. Модуль `vercel-publish` 1.1.0: налаштування `auth`

`module.json`:

```json
{"key": "auth", "type": "select", "label": "Вхід у Vercel",
 "options": [{"value": "token", "label": "Токен"}, {"value": "cli", "label": "Системний Vercel CLI (vercel login на цій машині)"}],
 "default": "token"}
```

(форма `options` — `[{value, label}]`, як її вже приймає `deai_modules` для типу `select`.)
`token` стає `required: false`; обовʼязковість перевіряє сам модуль: `auth == 'token'` без токена → як зараз
(`vercel-auth`). `team` у режимі `cli` — значення `--scope` (slug чи id команди; порожньо — особистий акаунт).
`password` — без змін (його вкладає збірка ядра).

Режим `token` — **побайтово той самий код**, що в 1.0.0. Режим `cli` — окрема гілка `_publish_cli` у тому ж `server.py`
(ядро виконує один файл модуля; сусідніх модулів він не імпортує).

### 2. Режим `cli`: що робить `publish(ctx, build_dir, task)`

Вхід: `ctx['npx']` — шлях до `npx`, який розвʼязало ЯДРО (`_node_bin('npx')`, бо PATH GUI-застосунку неповний, див.
`_node_bin`); `None` → `ModuleError('no-node')`. `task = {id, title, dir, state}`; у режимі `cli` `state` —
`{project, scope, task}` (без `project_id`: CLI працює за іменем).

Кроки — ті самі команди й таймаути, що в гілці ЛІГИ 0.8.0, з `cwd=build_dir`:

1. **Проєкт.** `state.project`, коли `state.task` збігається з id задачі; інакше новий `pv-<8 цифр>` (як `OWN_NAME_RE`).
   Імʼя зі стану в режимі `cli` НЕ мусить бути `pv-…` (у ЛІГИ є старі імена) — але мусить бути безпечним аргументом:
   `^[a-z0-9][a-z0-9._-]{0,99}$`, інакше `module-error` («імʼя проєкту в стані недійсне»), нічого не запускається.
   Скоуп: `state.scope`, інакше `settings.team`, інакше без `--scope`. Скоуп — той самий фільтр безпечного аргументу
   (`^[A-Za-z0-9_-]{1,100}$`).
2. `npx --yes vercel link --yes [--scope S] --project P` (120 с) — результат не перевіряється (як у 0.8.0: відмову
   скаже `deploy`).
3. `npx --yes vercel deploy --prod --yes [--scope S]` (300 с). Ненульовий код → `ModuleError('vercel-deploy',
   message=<текст ЛІГИ>)`: підказка `_deploy_hint` + `\n\n— вивід vercel —\n` + останні 300 знаків виводу, або лише
   останні 400, коли підказки нема (тексти — байт у байт із 0.8.0). `OSError`/таймаут → `ModuleError('vercel-deploy',
   message=str(e))`.
4. Адреси з виводу — `_deploy_urls` (перенесено як є). Нема жодної → `ModuleError('vercel-no-url', message=<текст 0.8.0>)`.
5. Постійна адреса — `_stable_alias` (перенесено: найкоротший кандидат із виводу `deploy` і `vercel inspect <url>`).
6. Перевірка — `_check_published` (перенесено як є: `verified` лише коли в тілі є `authgate`; редирект на
   `vercel.com/sso` → `reason: vercel_protection` + підказка). Сертифікати — той самий контекст, що й у режимі `token`
   (`_fetch_preview` модуля), а не `_ssl_context` ядра.
7. Скоуп після публікації — `orgId` з `build_dir/.vercel/project.json` (логіка `_remember_vercel_scope`, без запису:
   модуль лише повертає значення).
8. **Прибирання** (нове для ЛІГИ, рішення власника): `npx --yes vercel list P --json [--scope S]` (60 с) → `deployments`
   (`[{url, name, createdAt, …}]`, сторінка `pagination.next` — до 5 сторінок через `--next`); у кандидати йдуть лише
   записи з `name == P` і непорожнім `url`; сортування за `createdAt` спадно; поточна публікація (її адреса з кроку 4)
   завжди лишається; лишаємо `KEEP = 3` разом із нею; решта — `npx --yes vercel remove <url> --safe --yes [--scope S]`
   (60 с кожна, ≤ `CLEANUP_MAX_S` усього). ⛔ `vercel remove` ніколи не отримує імʼя проєкту — лише адреси публікацій
   (з іменем проєкту CLI видаляє ВЕСЬ проєкт). `--safe` — CLI сам пропускає публікації з активним alias. Будь-який збій
   прибирання (код, таймаут, не JSON, інша форма) — попередження, не помилка; нічого не видаляється, коли список не
   розібрано.
9. Результат:

```python
{'url': url, 'verified': bool, 'warnings': [...],          # як у режимі token
 'deploy_url': urls[-1],                                    # нове, необовʼязкове: адреса самої публікації
 'verify': {'reason': str, 'hint': str} | None,             # нове, необовʼязкове: чому не verified
 'cleanup_warning': str | None,                             # нове, необовʼязкове
 'state': {'project': P, 'scope': S_or_None, 'task': task_id}}
```

Ядро перевіряє форму результату ролі `publish` — нові ключі необовʼязкові й мусять пройти ту перевірку (рядки ≤ меж,
без самотніх сурогатів).

Жодних токенів: режим `cli` не читає `secrets.token` і не передає `VERCEL_TOKEN`; оточення підпроцесів — як у 0.8.0.

`check(ctx)` у режимі `cli`: `npx --yes vercel whoami [--scope S]` (120 с — холодний `npx` спершу завантажує CLI; ядру для
цього маніфест просить `check_timeout_s: 130`, див. «Поправки») → `{ok: true, detail: <імʼя користувача>}`;
нема `npx` → `{ok: false, error: 'no-node'}`; ненульовий код → `{ok: false, error: 'vercel-auth', detail: <≤200
знаків виводу>}`.

### 3. Ядро: неявний постачальник для ЛІГИ

`deai_modules.provider('publish')` і далі повертає `'legacy'` для ЛІГИ (UI, золоті знімки). Нове — у `serve.py`:

- `_publish_legacy_ctx(task)` — `ctx` для модуля `vercel-publish` у ЛІГИ: `settings = {'auth': 'cli', 'team': ''}`,
  `secrets = {}`, `npx = _node_bin('npx')`, `ModuleError`, плюс ключі, яких вимагає каркас (`call`). Модуль береться
  з каталогу вбудованих (як `git-sync` у 4a), а не з `space.json`.
- Гілка `'legacy'` у `Handler._publish` після збірки (без змін до `build_preview` включно, `build='legacy'`):
  1. `proj = _vercel_project(tid, task)` — як у 0.8.0, ДО деплою (мінт у `tasks.json`; відмова з інструкцією, якщо задача
     вже публікувалась без поля). Це гарантує, що імʼя переживає збій посеред деплою.
  2. `state = {'project': proj, 'scope': task.get('vercel_scope'), 'task': tid}`.
  3. `npx is None` → відповідь `deploy_error = NODE_MISSING_HINT`, `deploy_blocked = 'no-node'` (до виклику модуля,
     як у 0.8.0), `git_autocommit`, `_overview_sync`.
  4. Виклик модуля через каркас (`deai_modules.call(...)`, як `_vcs_call` у 4a). `ModuleError` з кодом `vercel-deploy`/
     `vercel-no-url` → `result['deploy_error'] = <ПОВНИЙ текст помилки>`; інший код → `deploy_error` = текст.
     Каркас зараз ріже текст `ModuleError` до 300 знаків (`_run`, `deai_modules.py`: вичищає секрети з `_full`, потім
     `[:MAX_MESSAGE]`), а текст ЛІГИ — підказка + до 300 знаків виводу. Тому `_run` додатково зберігає на
     перевикинутому `ModuleError` вичищений повний текст (≤ `MAX_FULL_MESSAGE`) у публічному полі `full`; `message`
     лишається ≤ 300 для всіх інших споживачів. Адаптер ЛІГИ бере `full`.
  5. Успіх → у тому ж порядку, що 0.8.0: запис `vercel_scope` у `tasks.json` (коли змінився; функція-наступник
     `_remember_vercel_scope`, що бере значення, а не читає файл), `_registry_push(tid)`, перечитаний `iterations.json`
     ← `publish_url`, `published_at`, `publish_verified`; відповідь: `url`, `deploy_url`, `domain_warning`,
     `not_task_link`, `verified`, `verify_error` (= `verify.reason`), `verify_hint` (= `verify.hint`) — ті самі ключі й
     порядок; `cleanup_warning` — ОСТАННІМ ключем і лише коли є.
  6. `git_autocommit` і `_overview_sync` — як у 0.8.0 (на всіх шляхах, де вони були).
- `publish_remote` у `iterations.json` для ЛІГИ НЕ пишеться (стан ЛІГИ — у `tasks.json` і реєстрі, як було).
- Видаляються з `serve.py`: `_deploy_urls`, `_stable_alias`, `_check_published`, `_remember_vercel_scope` (у
  теперішньому вигляді), `_deploy_hint` і блок `subprocess.run([... 'vercel' ...])` у `Handler._publish`.
  `NODE_MISSING_HINT`, `_node_bin`, `_vercel_project`, `_preview_domain_warning`, `_not_task_link`, `preview_password`
  лишаються.

### 4. Звичайний простір у режимі `cli`

Диспетчер `publish_with_module` / `_publish_by_url` не змінюється, окрім передачі `ctx['npx']` (ядро розвʼязує його для
будь-якого модуля ролі `publish`; модулі, яким він не потрібен, його ігнорують). Стан — як для режиму `token`:
`publish_remote.state` в `iterations.json`; модуль бере зі стану імʼя лише коли `state.task` — ця задача, і лише імʼя
`pv-<8 цифр>` (інакше нове імʼя й попередження), а скоуп — виключно з налаштування `team`: цей стан їздить через git, тож він
недовірений (див. «Поправки»). Довіряє стану лише адаптер ЛІГИ (`task['legacy_state'] = True`).
«Підключення»: картка Vercel показує вибір входу; у режимі `cli` поле токена приховане (або неактивне) і не
обовʼязкове, «Перевірити» кличе `check` (`vercel whoami`). Майстер — той самий вибір на кроці налаштувань.

### 5. Тексти й i18n

Нові ключі (uk + en): підпис налаштування й варіантів (з `module.json`), вердикти `check` для `no-node` і `vercel-auth`
у режимі `cli` (чи наявні ключі підходять — перевірити в `connections-model.js`), текст попередження прибирання.
Тексти помилок ЛІГИ — без змін (вони з `serve.py` 0.8.0, перенесені в модуль байт у байт).

## Поправки (план, 30.10.2026)

План `docs/superpowers/plans/2026-10-30-legacy-publish-module.md`, розділ «Поправки до спеки», уточнює цю спеку і має
перевагу: `ctx['find_tool']` замість `ctx['npx']`; `task['gated']` (режим `cli` перевіряє маркер гейта лише коли гейт
є); модуль віддає КОДИ відмов, а тексти ЛІГИ (`_deploy_hint`, підказка захисту) лишаються в ядрі як адаптер до 4d;
`ModuleError.full`; поле токена не ховається; нові коди `STATUS`; шов `_publish_legacy_call`; живий тест — шлях без
мережі.

Що ще вийшло інакше, ніж у тексті вище (звірено з кодом 30.10.2026): `check` у режимі `cli` при ненульовому коді дає
`vercel-login` (не `vercel-auth`), а також `check-timeout` і `no-node`; ключ `verify` модуля — лише `{reason}` (текст
підказки Deployment Protection збирає ядро з причини `vercel_protection`); `deploy` із порожнім виводом ядро ЛІГИ
перекладає в людський рядок (`_LEGACY_EMPTY_OUTPUT`), а не в порожній `deploy_error`, як було у 0.8.0; `_fetch_page`
модуля шле заголовки `User-Agent` і `Accept`, а причину недосяжності зводить до одного рядка; імʼя проєкту й скоуп
перевіряються суворіше (`^[a-z0-9][a-z0-9._-]{0,99}$` і `^[A-Za-z0-9][A-Za-z0-9_-]{0,99}$`).

Після фінального ревʼю (30.10.2026) додано й виправлено: (1) необовʼязковий ключ маніфесту `check_timeout_s` (ціле 1..150;
типово 5 с `CHECK_TIMEOUT`) — `vercel-publish` просить 130 с, а клієнтський запит «Перевірити»/«Увімкнути»/панелі/майстра чекає
його + 15 с (решта модулів — 20 с); `whoami` має 120 с (не 30 з тексту вище); (2) стан звичайного простору в режимі `cli`
недовірений: імʼя — лише `pv-<8 цифр>` (інакше новий проєкт і попередження), скоуп — лише з `team`; ЛІГА передає
`task['legacy_state'] = True` і довіряє своєму стану (будь-яке безпечне імʼя, скоуп зі стану), звичайний диспетчер цього ключа
не ставить ніколи; (3) збій `vercel link` (код ≠ 0) зупиняє публікацію з кодом за `_cli_code` — свідоме відхилення від 0.8.0
(там код `link` не читали, а текст кроку 2 вище «результат не перевіряється» втратив чинність); (4) у звичайному просторі
помилка `vercel-deploy` показує хвіст виводу CLI (`full[-300:]`), а не голову `message`.

## Відомі обмеження

- Режим `cli` у звичайному просторі: стан недовірений (див. «Поправки»), тож проєкт, якого стан називає не `pv-<8 цифр>`, не
  вживається: створюється новий `pv-…` із попередженням, а старий лишається у Vercel (його старі публікації не прибираються).
- Режим `cli` у звичайному просторі: імʼя нового проєкту — випадкове `pv-<8 цифр>` БЕЗ проби на зайнятість (режим
  `token` пробує `GET /v9/projects/<імʼя>`); колізія малоймовірна (100 мільйонів значень), але не виключена, і тоді `link` міг би
  приєднатися до наявного проєкту з таким імʼям у тому ж акаунті.
- Режим `cli` у звичайному просторі: якщо `deploy` впав після `link`, новий порожній проєкт `pv-…` лишається у Vercel,
  а наступна спроба створить ще один (у ЛІГИ цього нема — імʼя мінтиться в `tasks.json` до деплою).
- Прибирання бачить до 5 сторінок `vercel list`; старші публікації понад це — у наступні рази.
- `vercel list --json` / `remove --safe` — форма й прапорці з CLI 65.x (перевірено 30.10.2026); старіший CLI без них —
  прибирання дає попередження, публікація не страждає.
- Перевірка в режимі `cli` — за маркером гейта (`authgate`, лише коли `task['gated']`), у режимі `token` — за 200;
  розбіжність свідома (паритет).
- Перевірка превʼю в режимі `token` не має контексту `certifi` (режим `cli` має) — у беклозі разом з уніфікацією перевірки.
- Свідомі дрібні відмінності ЛІГИ від 0.8.0 — у `CHANGELOG.md` `[0.9.0]` (порожній вивід `deploy`, заголовки перевірки,
  суворіша перевірка імені й скоупа, збій `link` зупиняє публікацію).
