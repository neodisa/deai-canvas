# Етап 4c-1: командний дашборд як роль `dashboard` і модуль `supabase-dashboard` (0.12.0)

Дата: 02.11.2026. Попередній етап — 4b-3 (0.11.0, мітки задач). Дорожня карта — `docs/design/spaces-and-modules.md`.

## Рішення власника

- **26.10.2026 (етап 4):** чисте ядро + паритет; усе, що робить простір ЛІГА, стає модулем.
- **02.11.2026:** модулі 4c — **вбудовані й загальні** (як `vercel-publish`/`supabase-comments` у 4b), специфіка ЛІГИ — у
  конфігу й адаптері ядра. 4c = **4c-1 дашборд (ця спека, 0.12.0)** → 4c-2 трекер `jira-tracker` (0.13.0) → 4c-3 тиша
  Teams через роль `notify` (0.14.0).

## Проблема

Командний дашборд — зашитий шлях ЛІГИ в ядрі, паралельний модулям:

- **читання** (вкладка «Команда» екрана «Задачі»): `_team_fetch` (`app/serve.py`) — GET `overview_projects` Supabase ЛІГИ
  з `TEAM_COLS`, кеш `team_snapshot` (60 с рядки, 10 с помилка, збій не стирає останні рядки), гілка `integrations_on()` у
  `/api/tasks-overview`; статус Jira й лічильник коментарів своїх карток беруться ЛИШЕ з рядка дашборда;
- **запис**: `Handler._overview_sync` запускає `bin/overview_push.py sync` фоном після публікації й синку git; скрипт
  збирає картки (`build_row`, `discover_row`, `map_status`, PII-фільтр, фікстури), читає реєстр задач (гілка `registry`
  GitLab) для базових карток, рахує відкриті коментарі з таблиці `comments`, тягне статуси Jira і робить upsert у
  `overview_projects`;
- `overview_push.py` імпортує сервер (`from serve import supabase_config`) і читає оточення раніше за `tasks.json`
  (відоме обмеження 0.10.0);
- звичайний простір командного дашборда не має взагалі: роль `dashboard` лише зарезервована (`ROLES_RESERVED`).

## Мета

1. Роль `dashboard` у ядрі: ядро кличе модуль для читання рядків команди і для запису карток задач.
2. Вбудований модуль **`supabase-dashboard`** зі своєю схемою: будь-хто зі своїм Supabase отримує командний дашборд.
3. ЛІГА — через той самий модуль як **неявний постачальник** (зразок 4a/4b): `ctx` будує ядро з конфігу установки
   (`supabase_config()`), таблиця — `overview_projects`. Нового кроку при оновленні нема.
4. Збирання карток — у ядрі (`app/dashboard.py`), одне для всіх постачальників; модуль лише зберігає й віддає.
5. Паритет ЛІГИ: ті самі рядки «Команди», ті самі картки в базі, ті самі тригери синку. Свідомі відмінності — нижче.

## Не мета

- Статуси Jira як роль — 4c-2 (до неї статуси для ЛІГИ тягне той самий код, що зараз, кроком адаптера).
- Тиша Teams — 4c-3. Тригери бази ЛІГИ (`ov_comments_recount`, `cl_send_teams`) — у базі, канвас їх не чіпає.
- Реєстр задач на гілці GitLab (`_registry_push`, `bin/registry.py`) і крок «базові картки з реєстру» — лишаються шляхом
  ЛІГИ (крок адаптера) до 4d.
- Прапорець `integrations`, літерал `'legacy'` — 4d.
- `schema.sql` модуля на спільному проєкті ЛІГИ НЕ запускається: таблиця `overview_projects` уже має потрібні колонки.

## Дизайн

### 1. Роль `dashboard`

- `ROLES_CALLED` += `'dashboard'`, з `ROLES_RESERVED` прибирається (лишаються `tracker`, `notify`).
- Обовʼязкові функції `server.py`: `check(ctx)`, `rows(ctx)`, `push(ctx, cards, mode)`.
  - `rows(ctx)` → список словників-рядків команди; ядро бере лише ключі `TEAM_KEYS` = `id, name, jira, jira_status,
    jira_status_cat, open_comments, thumb_url, code_url, updated_at, designer, iterations, pages` (решта відкидається),
    рядки без рядкового `id` відкидаються, не більше `DASHBOARD_MAX_ROWS = 500`.
  - `push(ctx, cards, mode)` — `mode` ∈ `'merge'` (оновити наявний рядок, нові поля зверху) | `'insert'` (лише нові
    рядки, наявні не чіпати — базові картки). Повертає `{'ok': n, 'failed': {id: текст}}`; кидає `ModuleError`, коли
    сервіс недосяжний цілком.
- Необовʼязкова функція `open_comments(ctx)` → `{канал: кількість відкритих}` — лічильник для статусу картки `review`
  (`map_status`). Нема функції чи збій → `{}` (як зараз).
- `LEGACY_ROLES` += `'dashboard'`; у `LEGACY_ON_ERROR_ROLES` — НІ (зашитий шлях — спільний Supabase ЛІГИ, як `comments`).
- `capabilities.dashboard` — id модуля / `'legacy'` / `null`.
- Тайм-аути: `rows` — `DASHBOARD_READ_TIMEOUT = 4` с (екран «Задачі» — перша сторінка; було 3 с на запит), `push` і
  `open_comments` — у фоновому синку, `DASHBOARD_PUSH_TIMEOUT = 60` с на весь виклик.
- Коди помилок у `STATUS`: `dashboard-unconfigured` 409 (ЛІГА без конфігу Supabase), `dashboard-error` 502.

### 2. Модуль `supabase-dashboard` (вбудований, 1.0.0)

- Налаштування: `url` (text, обовʼязкове — ті самі правила адреси, що в `supabase-comments`), `key` (secret, **НЕ**
  `public`, обовʼязкове), `table` (text, типово `deai_dashboard`, `[a-z_][a-z0-9_]{0,62}`).
- ⛔ Ключ — **непублічний** (`service_role` чи ключ окремої ролі): у картках є імʼя й пошта дизайнера, а публічний ключ
  проєкту їде в кожне опубліковане превʼю (`supabase-comments`). Тому `schema.sql` НЕ дає `anon` доступу до таблиці
  дашборда, а `check` відмовляє публічному ключу (`sb_publishable_…` чи JWT з `role: anon`) текстом «потрібен
  непублічний ключ». Ключ живе в `~/.deai/secrets.json` (лише власник), у сторінки не потрапляє ніколи.
- `schema.sql`: таблиця з колонками карток (§4), `id text primary key`, RLS увімкнено, політик для `anon` нема;
  ідемпотентний; попередження «окремий проєкт / не адоптуй чужу таблицю», як у `supabase-comments`.
- `rows`: `GET {url}/rest/v1/{table}?select=<TEAM_KEYS>&limit=500`; `push`: `POST {url}/rest/v1/{table}?on_conflict=id`,
  `Prefer: resolution=merge-duplicates|ignore-duplicates,return=minimal`, пакетами по 50 карток (ЛІГА зараз шле по одній —
  див. «Свідомі відмінності»); `open_comments`: `GET {url}/rest/v1/comments?status=eq.open&select=project_id` (таблиця
  `supabase-comments` у тому ж проєкті; нема таблиці → `{}`).
- TLS — certifi, як у `supabase-comments`; тексти помилок без ключа й без тіла запиту.

### 3. Адаптер ЛІГИ (неявний постачальник)

- `_dashboard_legacy_ctx()` (у новому `app/dashboard.py`, БЕЗ імпорту `serve`): `url`/`key` — з `supabase_config()`
  (переїжджає з `serve.py` у `app/install_config.py`, `serve` реекспортує імʼя), `table` = `_LEGACY_DASHBOARD_TABLE =
  'overview_projects'`; модуль — вбудований `supabase-dashboard`. Ключ ЛІГИ — той самий, що зараз (без перевірки
  «непублічний»: паритет; `check` у ЛІГИ кличеться лише з екрана «Підключення»).
- Нема конфігу → `ModuleError('dashboard-unconfigured')`; на екрані «Команда» — та сама плашка з текстом помилки, що зараз
  («Supabase не налаштовано»).
- ⛔ Ізоляція (закон 03.08.2026): `DC_TASKS_FILE` чи `DC_NO_OVERVIEW` → шлях ЛІГИ не ходить у мережу ні на читання, ні на
  запис (рядки — `[]` + пояснення, як зараз). Шов `DC_TEAM_FAKE` лишається для читання ЛІГИ. `DC_NO_OVERVIEW` глушить
  **запис** дашборда для будь-якого постачальника.
- Кроки, що лишаються ЛІГИ до 4c-2/4d (передаються в синк як колбеки адаптера, у модуль не йдуть):
  - базові картки з реєстру (`discover_projects` → `push(…, 'insert')`);
  - статуси Jira (`jira_statuses`, `_JIRA_BASE`, облікові з `~/.claude/pipeline-feedback/`) — до 4c-2.

### 4. Збирання карток — `app/dashboard.py`

- Переїжджають з `bin/overview_push.py` без зміни поведінки: `gitlab_web`, `to_iso`, `map_status`, `preview_source`,
  `build_row` → `build_card`, `discover_row` → `discover_card`, `row_has_pii` → `card_has_pii`, `_drop_fixtures`,
  `comment_project_key`, `_identity`. Ті самі ⛔-коментарі (None не шлемо; `open_comments` не шлемо; авторство чужої
  картки не присвоюємо; задачу без теки не пишемо) — разом з кодом.
- `sync(space, provider, ctx, cfg, *, discover=None, statuses=None, log=print)` — один прохід:
  1. `discover` (лише ЛІГА): базові картки → PII-фільтр → `push(…, 'insert')`;
  2. `open_comments(ctx)` (якщо є) → лічильники;
  3. `statuses` (лише ЛІГА до 4c-2) → статуси Jira;
  4. задачі простору з текою на цій машині → `build_card` → PII-фільтр → `push(…, 'merge')`;
  5. підсумок у `log` тими ж рядками, що зараз (`✅ overview: синхронізовано N…`, пропуски вголос).
- `rows(space)` для екрана — `provider.rows(ctx)` з нормалізацією §1; кеш `team_snapshot` лишається в ядрі, але
  **ключується простором** (зараз — один на процес; відмова одного простору не стає станом іншого).

### 5. Запуск синку

- Тригери ті самі: після публікації, після синку git, що штовхнув, після автосинку, що змінив стан.
- Гейт — **`capabilities.dashboard` простору запиту** (не прапорець `integrations`): нема постачальника — тиша. ЛІГА —
  як зараз (вона має `'legacy'`).
- Фоновий процес лишається (`python3 bin/overview_push.py sync --space <id>`): синк не займає потік сервера й не ділить
  з ним памʼять. Новий — **один на простір одночасно**: поки дитина живе, повторний тригер ставить позначку «ще раз», і
  після її завершення стартує рівно один повтор.
- Лог: ЛІГА — той самий `~/.claude/pipeline-feedback/overview-sync.log`; інші простори — `<DEAI_HOME>/logs/dashboard-sync.log`
  (тека створюється з правами лише власника).
- `bin/overview_push.py`: тонкий CLI (`sync [--space ID]`, `discover`) поверх `app/dashboard.py`; без `--space` —
  простір ЛІГА (як зараз кличе зовнішній планувальник). `from serve import …` зникає; конфіг — `install_config.supabase_config()`
  (файл раніше за оточення — відоме обмеження 0.10.0 закрито; `SUPABASE_SERVICE_KEY` лишається запасним ключем ЛІГИ).

### 6. Клієнт і «Підключення»

- Вкладка «Команда»: сервер віддає `team: null`, коли в простору нема постачальника `dashboard` (було — коли нема
  `integrations`); клієнт уже ховає вкладку за `team == null` — без змін.
- «Підключення»: роль `dashboard` у `ROLE_ORDER`/`ROLE_KEYS`/`ROLE_ICONS` (іконка з наявного набору), i18n UK/EN
  («Командний дашборд» / "Team dashboard", опис, рядок «Зараз: …»); `disableConsequences` — «вкладка «Команда» зникне,
  картки задач перестануть оновлюватись у спільному дашборді». Майстер нового простору показує роль серед інших.
- Тести, що приколюють `roleKeys("tracker") == null` — лишаються (tracker ще зарезервований); для `dashboard` — нові.

## Паритет і перевірки

- **Знімок 0.11.0 ДО змін** (`tests/fixtures/dashboard/before-4c1.json`, як `before-4b2.json`): (а) запити й відповідь
  `/api/tasks-overview` на шві `DC_TEAM_FAKE` і на заглушці мережі (URL, заголовки без ключа, `team.rows`, `mine` з
  `jiraStatus`/`jiraCat`/`comments`); (б) тіла upsert `overview_push.py sync` на фікстурі задач (реєстр, коментарі,
  Jira — заглушки): порядок, `Prefer`, картки; (в) умови запуску `_overview_sync` (тригери, гейти, оточення дитини).
- Диференційні тести після змін: ті самі рядки, ті самі картки (як множина; групування в пакети — свідома відмінність),
  ті самі гейти.
- Модуль: `check` відмовляє публічному ключу; `rows` нормалізує й обрізає; `push` пакетує, `ignore`/`merge`; помилки без
  ключа в тексті; нема таблиці `comments` → `{}`.
- Мутації: ізоляція `DC_TASKS_FILE`/`DC_NO_OVERVIEW`; `'dashboard'` у `LEGACY_ON_ERROR_ROLES`; кеш без ключа простору;
  один синк на простір; `push` без фільтра None; перевірка непублічного ключа.
- Живі: «Задачі» з фейковим модулем дашборда у звичайному просторі (вкладка «Команда» є, рядки, помилка-плашка, без
  модуля — вкладки нема); «Підключення» — картка ролі. Наявні живі ЛІГИ (`tasks-home`) — зелені без змін.

## Свідомі відмінності від 0.11.0

- Вкладка «Команда» й синк залежать від постачальника `dashboard`, а не від прапорця `integrations` (для ЛІГИ — те саме).
- Модуль шле картки пакетами по 50, а не по одній: один збій пакета → усі 50 у `failed` (ЛІГА бачить це в лозі).
- Кеш рядків команди — на простір.
- Синк — один на простір одночасно (зараз кожен тригер — окремий процес, могли бігти паралельно).
- `overview_push.py` бере конфіг із `tasks.json` раніше за оточення (як сервер).
- Тайм-аут читання рядків — 4 с на виклик модуля (було 3 с на HTTP-запит).

## Відомі обмеження

- ЛІГА користується своїм наявним ключем (публічним) — перевірка «непублічний ключ» до неї не застосовується; таблиця
  ЛІГИ захищена політиками її бази, не схемою модуля.
- Реєстр задач і базові картки з нього — шлях ЛІГИ до 4d; статуси Jira — до 4c-2.
- Звичайний простір не має статусів трекера на картках до 4c-2.
- Розклад синку (кожні 30 хв) — зовнішній планувальник, не канвас.
