# Зворотний зв'язок і оновлення — дизайн (Deai 0.23.0)

Дата: 11.11.2026. Статус: погоджено власником у розмові 11.11.2026 (рішення нижче). Передумова: 0.22.0 (перехід ЛІГИ на Deai виконано).

## Навіщо

Перед розданням Deai команді (і людям поза ЛІГОЮ) потрібні дві речі, без яких розповсюджувати незручно:

1. **Зворотний зв'язок з канвасу.** Людина натискає кнопку, описує проблему чи пропозицію, а потрібні дані (версія, ОС, простір, задача,
   екран, останні помилки) додаються самі. Усе збирається в одному місці в мейнтейнера — однаково для команди ЛІГИ й для чужих установок.
2. **Оновлення.** Канвас сам помічає, що вийшла нова версія, підсвічує кнопку, і по кліку оновлюється й перезапускається.

## Рішення власника (11.11.2026)

- **Р1. Приймач зворотного зв'язку — окремий Supabase-проєкт Deai** (не база ЛІГИ): таблиця лише на запис ззовні (читати не можна), картка
  в Teams мейнтейнера. Дані ЛІГИ й чужі звернення не змішуються.
- **Р2. Джерело оновлень — той git-репозиторій, з якого поставлено установку.** Продукт оновлюється з GitHub (`neodisa/deai-canvas`), робоча
  копія ЛІГИ живе на корпоративному GitLab (дзеркало з тими самими тегами). Канвас не знає «правильного» сервера — питає свій `remote`.
- **Р3. Кнопка «Оновити» сама оновлює і перезапускає.** Якщо щось заважає — нічого не чіпає і пояснює, що зробити руками.

## Не-цілі

- Адмінка для читання відгуків у самому канвасі (читає мейнтейнер у Supabase / Teams).
- Автооновлення без кліку; оновлення через злиття (лише fast-forward на тег).
- Перезапуск під Windows (оновлення застосовується, перезапуск — вручну з підказкою); основна платформа — macOS.
- Збір аналітики/телеметрії без дії людини. Нічого не надсилається, поки людина не натисне «Надіслати».

## Частина А. Оновлення

### А1. Версія й перевірка

- Поточна версія — `package.json` → `version` (єдине джерело; так уже роблять реліз і CHANGELOG).
- Новий модуль `app/updater.py`. Перевірка: `git -C <ROOT> ls-remote --tags --refs <remote>` з тайм-аутом 15 с; `<remote>` — upstream
  поточної гілки, інакше `origin`; перекриття — змінна `DEAI_UPDATE_REMOTE`. Беремо найбільший тег виду `vX.Y.Z` (semver, без
  пре-релізів), порівнюємо з поточною версією.
- Перевірка — у фоновому потоці на старті й кожні 6 годин; ручна — `POST /api/update/check`. Вимкнути — `DEAI_NO_UPDATE_CHECK=1`
  (живі/юніт-тести вмикають це завжди; у тестах git-раннер підміняється — мережі нема).
- Результат — у `<DEAI_HOME>/update.json` (0600): `checked_at`, `latest`, `state`, `reason`, `last_update`.
- `GET /api/update` → `{current, latest, available, checked_at, state, reason, blocked}`; `state` ∈ `ok | offline | no-git | error`.
  Ніяких шляхів і адрес remote у відповіді (лише хост, напр. `github.com` / `gitlab`-хост — щоб людина бачила, звідки).

### А2. Застосування

`POST /api/update/apply` (Origin-гейт, як інші POST). Кроки, кожен зупиняє все з кодом причини, нічого не змінивши:

1. **Передумови** (`blocked`, перевіряються й у `GET /api/update`, щоб кнопка заздалегідь знала):
   - `not-git` — установка не з git-клону;
   - `dirty` — є змінені відстежувані файли (`git status --porcelain --untracked-files=no` не порожній);
   - `detached` / `worktree` — HEAD не на гілці або це git-worktree;
   - `busy` — триває міграція чи інше оновлення.
2. `git fetch <remote> refs/tags/vX.Y.Z:refs/tags/vX.Y.Z` (тайм-аут 60 с) → `offline` при збої.
3. `git merge-base --is-ancestor HEAD vX.Y.Z`, інакше `diverged` (локальні коміти, яких нема в релізі; підказка — команда для ручного
   злиття).
4. `git merge --ff-only vX.Y.Z`.
5. **Димова перевірка нового коду:** `python3 -B -m py_compile app/*.py bin/*.py` у дочірньому процесі. Провал → `git reset --hard <старий
   HEAD>` (безпечно: це був fast-forward), стан `rolled-back`, сервер працює далі на старому коді.
6. Запис `last_update: {from, to, at}` в `update.json`, відповідь `202 {to}`, після відправки відповіді — перезапуск.

**Перезапуск.** `os.execv(sys.executable, [sys.executable, *sys.argv])` з тим самим оточенням і робочою текою, у фоновому потоці
через ~0,5 с після відповіді. Сокет сервера не успадковується (PEP 446), `allow_reuse_address` уже ввімкнено — новий процес знову бере
порт. PID лишається тим самим, тож запускач (`launch.sh`, автостарт) нічого не помічає. Міграції нової версії проходять, як завжди, на
старті.

### А3. Інтерфейс

- У смузі (shell-bar) — пігулка «Оновлення 0.23» лише коли `available`. Клік → діалог: «Встановлено 0.22.0 → доступно 0.23.0», блок
  «Що нового» (розділи CHANGELOG між версіями, `GET /api/update/notes`, лише текст — markdown рендериться безпечно, без HTML), кнопка
  «Оновити й перезапустити».
- Якщо `blocked` — кнопка неактивна, текст причини людською мовою + команда для термінала (копіюється).
- Під час оновлення — стан «Оновлюю…», далі сторінка опитує `GET /api/update`, поки сервер не відповість новою версією, і
  перезавантажується (service worker PWA: нова версія = новий кеш; перевірити, що старий кеш не віддасть стару оболонку).
- ⌘K: «Перевірити оновлення» (ручна перевірка) і «Що нового».
- Невдала перевірка (`offline`/`error`) пігулку не показує — лише рядок у діалозі з ⌘K.

## Частина Б. Зворотний зв'язок

### Б1. Приймач (Р1)

- Окремий Supabase-проєкт «deai» (створює власник; ми даємо SQL). Файл `ops/feedback-collector.sql` у репо — без секретів:
  - таблиця `feedback`: `id uuid primary key` (генерує клієнт), `created_at`, `kind` (`bug`|`idea`), `text` (≤ 10 000 символів),
    `contact` (необовʼязково, ≤ 200), `version`, `os`, `diag jsonb` (≤ 64 КБ), `shot_path` (необовʼязково);
  - RLS: роль `anon` — лише `insert` з перевірками довжин; `select/update/delete` — нікому, крім service role;
  - бакет Storage `feedback-shots`: `anon` лише `insert`, PNG ≤ 2 МБ;
  - тригер → `pg_net` → вебхук Teams (Power Automate), URL вебхука — секрет у Vault (`teams_feedback_webhook_url`), як у ЛІГИ.
- Адреса проєкту й **публікований (anon) ключ** — у конфігу продукту `app/feedback.json` (`{url, key}`); це публічні за задумом значення,
  права обмежує RLS. Перекриття для форку/власного збору: `<DEAI_HOME>/config.json` → `feedback: {url, key}` або `DEAI_FEEDBACK_URL` /
  `DEAI_FEEDBACK_KEY`. Порожній конфіг = лише локальна черга (Б3).

### Б2. Що збирається (сервер, `GET /api/feedback/preview`)

- `version`, ОС і версія Python, мова інтерфейсу;
- простір: вид (`legacy`/звичайний), ролі й ID модулів (без налаштувань і секретів), стан міграції ЛІГИ (статуси кроків);
- задача: `id`, ітерація, сторінка/екран (без назви задачі — назва може бути конфіденційною; людина допише в текст, якщо треба);
- останні помилки: кільце сервера (50 останніх винятків `_guarded`: маршрут без query, тип, повідомлення ≤ 300 символів) + кільце клієнта
  (20 останніх `error`/`unhandledrejection`: повідомлення, файл у `app/`, рядок);
- **Редагування:** домашній шлях → `~`, рядки, схожі на ключі/токени (довгі base64/hex, `eyJ…`, `sk-…`), → `‹приховано›`, e-mail → `‹e-mail›`,
  query-рядки URL відрізаються. Той самий фільтр — для тексту помилок.
- Людина бачить усе, що піде («Що буде надіслано» — розгортаний JSON), і може зняти блоки: діагностика, скриншот.

### Б3. Надсилання й черга

- `POST /api/feedback` (Origin-гейт) `{kind, text, contact?, include_diag, include_shot, client_errors[]}`.
- Спершу запис у `<DEAI_HOME>/feedback/outbox/<id>.json` (0600), потім спроба надіслати (тайм-аут 10 с; скриншот — окремим запитом у
  Storage). Успіх → файл у `sent/`, відповідь `{id, state:'sent'}`; збій → `{id, state:'queued'}`. Номер звернення — перші 8 символів `id`.
- Черга дочищується у фоні на старті й щогодини; запис старший за 30 днів або 20 невдалих спроб — у `failed/` (не губимо, не крутимося).
- Скриншот: кадр поточної ітерації тим самим механізмом знімків, що «Огляд» (`/shot`), лише якщо відкрита задача й галочка стоїть.

### Б4. Інтерфейс

- Кнопка «Відгук» у смузі (іконка) і пункт ⌘K «Баг / ідея» — доступні завжди, на всіх екранах (і на «Задачах», і в майстрі).
- Діалог: перемикач «Проблема / Пропозиція», текстове поле (обовʼязкове, ≥ 10 символів), контакт (необовʼязково), галочки «Додати
  діагностику» (типово так), «Додати скриншот» (типово так, лише коли є задача), «Що буде надіслано», «Надіслати».
- Результат: «Дякуємо! №abcd1234» або «Збережено — надішлемо, щойно буде мережа (№abcd1234)». Помилка введення — під полем.

## Безпека

- Усі нові POST — за існуючим Origin-гейтом; `apply` і `feedback` не приймають шляхів ззовні.
- `updater` запускає лише `git` і `python3` зі списком аргументів (без shell), лише в `ROOT`; тег перевіряється регуляркою `^v\d+\.\d+\.\d+$`
  до будь-якого виклику.
- Відгук не містить секретів простору (фільтр + перелік полів, а не дамп конфігу); юніт-тест на фільтр із прикладами ключів.
- Supabase anon-ключ — лише insert; витік ключа дає спам, не читання (rate-limit — поза цим етапом, записано в ризики).

## Тестування

- `updater`: реальні git-репозиторії в тимчасових теках (bare-remote + клон, теги), без мережі: доступно/недоступно, `dirty`, `diverged`,
  `detached`, `not-git`, fast-forward, відкат при провалі димової перевірки, перезапуск — через підміну `os.execv`.
- `feedback`: фільтр редагування, черга (offline → queued → sent), обрізання розмірів, відсутність секретів у діагностиці, порожній конфіг.
- JS: моделі пігулки/діалогу оновлення й діалогу відгуку (node-тести), i18n обома мовами.
- Живі: пігулка з'являється при підміненому `update.json`; діалог відгуку надсилає в локальний фейковий приймач (порт тесту, без мережі).
- Охоронці: жоден тест не ходить у мережу (`DEAI_NO_UPDATE_CHECK=1`, фейковий приймач); мутації для кожної нової перевірки.

## Відкат 0.23 → 0.22

Нові файли (`update.json`, `feedback/`) 0.22 ігнорує. Відкат — `git checkout v0.22.0` + перезапуск.

## Ризики

- **Спам у приймач** через публічний anon-ключ → обмеження довжин у RLS; rate-limit (edge function) — наступним кроком, якщо знадобиться.
- **Розходження робочої копії ЛІГИ на GitLab** з тегами GitHub → `diverged` з поясненням, нічого не ламаємо.
- **Кеш PWA** віддає стару оболонку після оновлення → перевіряється живим тестом; при потребі — версія в імені кешу service worker.
- **Перезапуск через execv** у процесі, запущеному не з `python3 app/serve.py` (інший argv) → беремо `sys.argv` як є; тест на argv.

## Що потрібно від власника

1. Створити Supabase-проєкт «deai», виконати `ops/feedback-collector.sql`, покласти URL вебхука Teams у Vault.
2. Дати адресу проєкту й publishable-ключ — вони підуть у `app/feedback.json` (до того відгуки лягають у локальну чергу).
3. Дзеркало на корпоративному GitLab має отримувати теги з GitHub (налаштування дзеркала).
