## Проблема

Публікація на Vercel є лише в зашитому шляху ЛІГА: `npx vercel` із залогіненим на машині CLI,
спільний для команди реєстр, дашборд, автокоміт. Людина зі своїм акаунтом Vercel поділитися
превʼю не може — лише покласти його в теку (`static-publish`).

## Мета 0.3.0

- Вбудований модуль `vercel-publish` (роль `publish`): превʼю задачі йде на **власний** Vercel
  людини за її токеном, без Node і без CLI.
- Контракт ролі `publish` розширюється: модуль публікує або **в теку**, або **за адресою**.
- Інтерфейс показує результат, попереджає про публічне превʼю й дає посилання для колег.
- Зашитий шлях ЛІГА не змінюється (відповіді побайтно ті самі).

Поза 0.3.0: коментарі на превʼю Vercel (0.4.0, разом із модулем Supabase), власні домени,
екран «Підключення» (етап 3) — модулем керують через API.

## Модуль `vercel-publish`

`app/modules/vercel-publish/module.json`:

```json
{"api": 1, "id": "vercel-publish", "name": "Vercel", "version": "1.0.0",
 "roles": ["publish"], "publish_target": "url",
 "settings": [
   {"key": "token", "type": "secret", "label": "Токен Vercel", "required": true},
   {"key": "team", "type": "text", "label": "Команда Vercel (slug або team_…; порожньо — особистий акаунт)"},
   {"key": "password", "type": "secret", "label": "Пароль превʼю (необовʼязково)"}
 ]}
```

- `publish_target` — нове НЕобовʼязкове поле маніфесту: `"folder"` (типове, як `static-publish`)
  або `"url"`. Інші значення → модуль `status:'error'` (`bad-manifest`).
- `team`: рядок `team_…` іде в запити як `teamId`, інакше — як `slug`; порожньо — без параметра.
- Модуль — лише stdlib (`urllib`, `hashlib`, `json`, …), не імпортує ні `serve`, ні `deai_modules`
  (як `static-publish`; статичний тест-allowlist імпортів).

### REST API Vercel (без CLI)

База — `https://api.vercel.com`; кожен запит із `Authorization: Bearer <token>` і тайм-аутом
(30 с на запит, 60 с на завантаження файла). Токен іде ЛИШЕ в цей заголовок і ЛИШЕ на базу API:
ні в аргументи процесів, ні в оточення, ні в запит перевірки превʼю, ні в тексти помилок.

1. **Файли.** Обхід зібраної теки (`build_dir`), відносні шляхи через `/`; для кожного файла —
   SHA-1 і розмір; `POST /v2/files` із тілом файла, `Content-Type: application/octet-stream`,
   `x-vercel-digest: <sha1>`, `Content-Length`; однакові вмісти (той самий SHA-1) — один раз.
2. **Публікація.** `POST /v13/deployments` з `{"name": <проєкт>, "project": <проєкт>,
   "target": "production", "files": [{"file", "sha", "size"}…], "projectSettings":
   {"framework": null}}` (без збірки: превʼю вже зібране). Перша публікація задачі створює проєкт.
3. **Очікування.** `GET /v13/deployments/{id}` кожні ~1,5 с до `readyState` = `READY`
   (`ERROR`/`CANCELED` → помилка з `errorMessage` Vercel), загалом ≤ 180 с.
4. **Адреса.** З `alias` готової публікації — найкоротший `*.vercel.app` (продакшн-адреса
   проєкту; адреси окремих публікацій Vercel за замовчуванням закриває захистом).
   Нема жодного `alias` → адреса публікації `https://<url>` з попередженням.
5. **Перевірка.** `GET <адреса>` без заголовка авторизації, без переходів за редиректами,
   ≤ 20 с: 200 → `verified: true`; редирект на вхід Vercel чи 401/403 → `verified: false` і
   попередження «увімкнено Deployment Protection» з підказкою, де вимкнути; інше → `verified:
   false` без зупинки публікації.
6. **Прибирання.** Після успіху — `GET /v6/deployments?projectId=<id>&target=production&limit=20`
   і `DELETE /v13/deployments/{id}` для всіх, крім трьох найновіших (поточна — завжди серед
   них). Лише для проєкту, який створив цей модуль для цієї задачі (його `projectId` записаний
   у стані задачі й збігається з `projectId` публікації). Збій прибирання — попередження, не
   помилка.

`check(ctx)` — `GET /v2/user` (з `team` — ще `GET /v2/teams/<team>`): 200 → `ok`; 401/403 →
`{"ok": false, "error": "vercel-auth"}`; мережа недоступна → `{"ok": false, "error": "network"}`.
Нічого не створює.

### Стан задачі

- Проєкт на задачу: непрозоре імʼя `pv-<8 цифр>` (як у ЛІГА: в адресі ні назви задачі, ні
  клієнта). Імʼя, `projectId` і id останньої публікації модуль повертає як `state`; ядро
  зберігає його в `iterations.json` задачі: `publish_remote = {"module", "state", "published_at",
  "url", "gated"[, "gate_hash"]}` (останні три — власні поля ядра: адреса, що вийшла, чи збірка з
  паролем, і перші 16 hex `sha256` пароля, лише щоб бачити його зміну; сам пароль не пишеться) і
  передає `state` назад у наступний виклик (`task["state"]`). `state` — JSON-обʼєкт ≤ 4 КБ, лише
  рядки/числа (ядро перевіряє; інакше `module-error`).
- Перша публікація задачі (стану ще нема): перед нею `GET /v9/projects/<імʼя>` мусить дати 404 —
  інакше в акаунті вже є проєкт із таким імʼям (не наш), і модуль бере нове імʼя (≤ 3 спроби,
  далі `module-error`). Наступні публікації: проєкт за записаним `projectId` — лише він.

## Ядро: контракт ролі `publish`

`publish_with_module` розгалужується за `publish_target` модуля:

| | `folder` (як у 0.2.0) | `url` (нове) |
|---|---|---|
| налаштування теки, `folder_ok` | так | ні |
| лок | тека збірки + тека призначення | тека збірки задачі |
| результат модуля | `{"path"}` = `<folder>/<task-id>` | `{"url", "state", "verified", "warnings"?}` |
| перевірка результату | `realpath` збігається | `url` — ASCII `https://` з коректними хостом і портом, без облікових даних і фрагмента; `state` — як вище; жодного секрету модуля (крім `password`) в `url`/`state`, у `warnings` секрети вирізаються |
| запис у `iterations.json` | `publish_local` | `publish_url`, `published_at` (`DD.MM.YYYY HH:MM`, як ЛІГА), `publish_verified`, `publish_remote` |
| відповідь | `{ok, local:{path,url}, …}` | `{ok, url, verified, warnings?, …}` |

- Спільне для обох: 400 «no iterations marked», `publish-busy`, збірка
  `build_preview(comments=False, gate_pw=<password або None>)`, ПЕРЕчитування мети перед
  записом, жодних `git_autocommit`-пушу, `_registry_push`, `_overview_sync`. Модуль кличеться
  без `timeout` ядра (у модуля свої тайм-аути на кожен запит). 400 `bad-task-id` — лише для
  `folder` (id задачі стає імʼям теки); для `url` імʼя проєкту непрозоре, id задачі в адресу не
  йде.
- `/api/task` для `url`-модуля: `preview_gate = {state:'module', …}` (форма незмінна);
  `publish_gate` — чи ОПУБЛІКОВАНЕ превʼю з паролем (`publish_remote.gated`; без публікації цього
  модуля — чи пароль заданий зараз), для застереження «превʼю публічне»; `publish_gate_stale: true`
  — пароль зараз відрізняється від опублікованого (задали, зняли, змінили) — превʼю треба
  опублікувати знову; `publish_share_url` — лише коли `publish_remote.module` і `publish_remote.url`
  збігаються з цим модулем і `publish_url` (адреса ЛІГА чи правлена вручну — без нього): `publish_url`
  + `#k=<пароль>` для збірки з паролем, що не змінився, інакше `publish_url` (див. «Межі» —
  свідоме виключення з правила «секрети не йдуть в API»).
- `ops/reseal_gate.py` збірки модулів не чіпає (як у 0.2.0: вирішує за артефактом).

## Помилки

| Ситуація | Відповідь |
|---|---|
| токен не прийнято (401/403 від API) | 409 `vercel-auth` |
| ліміт Vercel / 429 | 409 `vercel-busy` (текст Vercel, без секретів) |
| публікація `ERROR`/`CANCELED`, тайм-аут очікування, неочікувана відповідь | 502 `module-error` |
| нема мережі | 502 `module-error` («Vercel недоступний») |
| захист Vercel, нема `alias`, збій прибирання | 200, публікація є, `warnings` |

`vercel-auth` і `vercel-busy` — нові коди в `STATUS` ядра (409). Тексти помилок ріжуться
ядром (секрети вирізаються, ≤ 300 символів).

## Інтерфейс

- Відповідь з `url` → плашка «Опубліковано на Vercel» з «Відкрити» (`noopener`) і
  «Скопіювати посилання» (`publish_share_url`); `warnings` → другий рядок плашки.
- Без пароля — у дропдауні публікації застереження «превʼю публічне: будь-хто з посиланням його
  бачить» (як застереження ЛІГА).
- Нові коди помилок (`vercel-auth`, `vercel-busy`) — людські тексти uk/en.
- Зона публікації, `pubpw`, Teams — як у 0.2.0 (`pubpw` лише для `legacy`).

## Мережа й вимикач

- Явне ввімкнення модуля людиною — згода: модуль ходить лише на `api.vercel.com` і на адресу
  власного превʼю. Неявного ввімкнення нема (типовий у просторі без інтеграцій лишається
  `static-publish`; другий постачальник `publish` → `role-taken`, тож спершу вимкнути
  `static-publish`).
- Прапорець `integrations` і далі стосується лише зашитого коду ЛІГА; явно ввімкнений модуль має
  пріоритет і в просторі ЛІГА (як у 0.2.0).

## Межі

- **Пароль превʼю — не секрет від глядача** (вшитий у сторінки, гейт клієнтський). Тому
  `/api/task` віддає `publish_share_url` з `#k=<пароль>` — свідоме виключення з правила 0.2.0
  «секрети не йдуть в API»; **токен** не виходить нікуди, крім заголовка до API Vercel.
- Превʼю на `*.vercel.app` публічне (з паролем — за клієнтським гейтом).
- Deployment Protection акаунта може закрити й продакшн-адресу — модуль про це попереджає, але
  не вимикає (налаштування акаунта людини).
- Розмір публікації — у лімітах тарифу Vercel людини; модуль чистить лише старі публікації
  своїх проєктів (три найновіші лишаються).
- Власні домени, коментарі на превʼю Vercel — пізніше.

### Відхилення від ревізії 1 (стан на 0.3.0)

Що збудовано інакше (чи додатково) проти тексту ревізії 1; усе звірено з кодом.

**Ядро (`app/serve.py`, `app/deai_modules.py`)**

- **`publish_remote`** = `{module, state, published_at, url, gated[, gate_hash]}`: `url`, `gated` і `gate_hash`
  — власні поля ядра (`gate_hash` — перші 16 hex `sha256` пароля, лише щоб бачити його зміну; пароль не
  пишеться, у `/api/task` `gate_hash` не йде). `published_at` усередині — ISO UTC, окремо від верхнього
  `published_at` (`ДД.ММ.РРРР ГГ:ХХ`).
- **`/api/task`**: `publish_gate` рахується за ОПУБЛІКОВАНОЮ збіркою (`publish_remote.gated`), а не за
  поточним паролем; додано **`publish_gate_stale: true`** (пароль з того часу змінили); `publish_share_url` —
  лише коли `publish_remote.module` і `.url` збігаються з постачальником і `publish_url`.
- **Результат модуля не приймається на слово**: значення секретів модуля завдовжки ≥ 8 знаків (крім
  `password`) в `url`/`state` → `module-error`, нічого не записано; у `warnings` вирізаються ВСІ такі
  значення, пароль теж. Інші межі: `url` ≤ 2048, `state` — плаский обʼєкт (`str`/`int`/`float`/`bool`/`None`,
  скінченні числа) ≤ 4096 знаків JSON, `warnings` ≤ 5 × 300, `verified` — булеве.
- **Сувора перевірка адреси**: `https://`, лише ASCII, без `#`, `\`, пробілів і керівних знаків, без облікових
  даних, коректний порт, хост — DNS-імʼя з ДВОХ і більше ASCII-міток (≤ 63, не з дефіса й не на дефіс, ≤ 253
  усього; IDN — лише punycode), остання з яких починається з літери; `[::1]` і порожні мітки відхиляються.
  **Виправлено перед тегом 0.3.0**: спершу крапкова IPv4 за формою збігалась з міткою й проходила, хоч докстрінг
  `_url_host_ok` казав протилежне (`https://127.0.0.1/`, `https://2130706433/`, `https://0x7f.1/`,
  `https://169.254.169.254/…`, `https://localhost/`). Тепер вони відхиляються (правило «остання мітка — з літери,
  міток ≥ 2»), а докстрінг описує саме його; DNS-імʼя, що резолвиться в локальну адресу (`127.0.0.1.nip.io`),
  синтаксисом не відсіяти — ядро DNS не питає. Те саме правило дзеркалить `safeRemoteUrl` в UI (імʼя хоста — як
  написано, а не як його нормалізує `URL`: `0x7f.1`, `%2e`).
- **`bad-task-id`** — лише для `folder`-модулів (id задачі стає імʼям теки); для `url` id в адресу не йде.

**Модуль `vercel-publish`**

- **Стан** — `{project, project_id, deployment, task}` (ревізія 1: без `task`). Береться лише як `pv-\d{8}` +
  непорожній `project_id` + `task` = id цієї задачі, інакше «стану нема»; у стані лишається ПЕРВИННЕ імʼя.
  Проєкт шукається за id (`GET /v9/projects/<project_id>`), не за імʼям, і береться лише коли `id` збігається
  з записаним і ТОЧНЕ `name` дорівнює записаному; 404 → створення наново під записаним імʼям, коли воно вільне,
  інакше нове імʼя (≤ 3 спроби). **Підтримку перейменування прибрано перед тегом 0.3.0.** Спершу перейменований у
  панелі проєкт приймався, якщо записана в стані остання `deployment` належала цьому `projectId` — але доказ лежав
  у тому самому стані, тож склонований чи підроблений `iterations.json` з `{project: pv-…, project_id: <чужий
  проєкт>, deployment: <публікація чужого проєкту>, task: <ця задача>}` «доводив» належність: модуль деплоїв у
  чужий проєкт і видаляв його старі публікації (відтворено ревʼюером). Тепер інше імʼя — проєкт «не наш»: у нього
  жодного `POST` і `DELETE`, створюється новий `pv-<8 цифр>` із попередженням «проєкт у стані не збігається —
  створено новий», а перейменований у панелі проєкт задачі просто лишається як був. Ціна — перейменування в
  Vercel відриває задачу від старого проєкту (нова адреса); вона прийнята заради безпеки.
- **Збірка читається цілком до першого запиту**: симлінк, не звичайний файл, імʼя не в UTF-8, порожня
  збірка — відмова; межі **5000 файлів** і **50 МБ на файл**.
- **Очікування**: до `READY` ≤ 180 с; до 3 збоїв мережі/5xx ПОСПІЛЬ терпимо; `ERROR`, `CANCELED`,
  `BLOCKED`, `DELETED` — термінальні. Після `READY` постійну адресу чекаємо ще ≤ 30 с (`*.vercel.app` у
  `alias`, `aliasAssigned` або `aliasError`); це очікування НІКОЛИ не провалює вже готову публікацію —
  будь-який його збій дає адресу публікації й попередження.
- **Завантаження**: один повтор файла при збої мережі/5xx; файл перечитується й звіряється за SHA-1 і
  розміром; усі завантаження ≤ 300 с. Тайм-аути запитів: 30 с (API), 60 с (файл), 20 с (перевірка превʼю).
- **Перевірка превʼю** повторюється до двох разів (з паузою 1,5 с), коли сторінка ще 404/5xx/без відповіді;
  захист — 401/403 чи редирект на `vercel.com`.
- **Прибирання**: `GET /v6/deployments?projectId=<id>&target=production&limit=20`; чіпаються лише записи,
  ПОЗИТИВНО впізнані як цього проєкту (`projectId`, а коли його нема — `name`); лишаються поточна й дві
  найновіші; ≤ 60 с; авторизація чи ліміт зупиняють решту.
- **Видалення проєкту після збою** — лише створеного ЦИМ викликом (`pv-\d{8}`) і лише після трьох перевірок:
  id починається з `prj_`, у проєкті (`GET /v6/deployments?projectId=<id>&limit=5`) нема публікацій, крім цієї,
  `GET /v9/projects/<id>` дає те саме імʼя. Текст помилки завжди каже, видалено проєкт чи ні. Існуючий
  проєкт зі стану не видаляється ніколи.
- **Тексти помилок**: усе, що не має власного коду (`vercel-auth`/`vercel-busy`), модуль кидає як
  `ModuleError('module-error')` ядра (`publish` — обгортка над `_publish`), з текстом без імені класу: звичайний
  виняток ядро показало б як `RuntimeError: …`/`_NetworkError: …`, і людина бачила б це в діалозі. Перед приміткою
  про видалення проєкту основний текст завершується крапкою («… станом ERROR. Створений проєкт … видалено.»).
  Усі попередження й тексти Vercel очищаються від самотніх сурогатів (`\ud800` у JSON): ядро не може записати
  такий рядок в UTF-8 `iterations.json` і відмовило б усю вже вдалу публікацію.
- **Помилки API**: 401 чи `invalidToken` — «Vercel не прийняв токен», звичайний 403 — «Vercel відмовив у
  доступі (HTTP 403)» (обидва `vercel-auth`); 429 — `vercel-busy`; 3xx від API — помилка (за редиректами не
  йдемо); текст Vercel очищається від токена й ріжеться.
- **`check`**: для `team_…` — `GET /v2/teams/<id>`; для slug — читальна проба `GET /v6/deployments?limit=1` у
  цій команді (`GET /v2/teams/<slug>` приймає id, а не slug; ревізія 1 писала просто `GET /v2/teams/<team>`).

**Інтерфейс**

- Гонка «опублікував — перейшов на іншу задачу» (публікація триває хвилини): замість плашки на чужій
  задачі — тост «Опубліковано на Vercel: <задача>»; рішення «ЛІГА чи модуль» береться за простором ВИКЛИКУ.
- «Скопіювати посилання» для адреси, що лишилась від іншого постачальника (простір перемкнули з Vercel на
  `static-publish`), копіює саму адресу (лише безпечну): ЛІГА-шний `#k=<preview_password>&p=…` дописується лише
  для постачальника `legacy`. Кнопка «Опублікувати» оживає на всіх шляхах (`finally`), зокрема коли `render()` кинув.
- «Відкрити» веде на `publish_share_url` (з `#k=<пароль>` для збірки з паролем, що не змінився), а не на голу
  адресу; лише `https:` ASCII, `noopener`. «Скопіювати» кладе `publish_share_url` дослівно.
- `module-error` і `vercel-auth` показують текст сервера (≤ 300, керівні знаки — пробілом) другим абзацом
  діалогу (там, наприклад, «видаліть проєкт вручну»); `vercel-busy` — людський текст без деталей.
- Застереження в дропдауні: `publish_gate === false` → «превʼю публічне», `publish_gate_stale === true` →
  «пароль змінено — перепублікуйте»; поле не прийшло — нічого. Слово «Vercel» у плашці й тості — лише коли
  постачальник `vercel-publish` (інший `url`-модуль — просто «Опубліковано»).

**Відомі межі, названі перед тегом**: сирота — порожній проєкт `pv-…` лишається в акаунті, коли мережа обірвалась
одразу після `POST /v13/deployments` до відповіді (id публікації невідомий, прибрати нічим); завантаження
послідовні, збірка йде ЦІЛКОМ щоразу (≤ 300 с загалом); `check` має 5 с у ядра (повільний канал дає `check-timeout`
при вмиканні — модуль усе одно працює); явні `POST /api/module-check` і `POST /api/module-settings` кличуть
`check()` на `api.vercel.com` і для ВИМКНЕНОГО модуля (автоматично — ніщо).

**Не перевірено на справжньому Vercel** (перший живий прогін): час появи постійної адреси після `READY`,
форма записів `GET /v6/deployments` (`uid`, `created`, `projectId`), перевірка команди за slug, тіло помилки
недійсного токена.
