# Етап 4d-4a: напрямки ЛІГИ — остаточно явні, синонім `profile` — лише на межі (0.20.0)

Дата: 07.11.2026. Попередній етап — 4d-3c (0.19.0, випущено 06.11.2026; спека `2026-11-06-liga-migration-c-design.md`). Дорожня
карта — `docs/design/spaces-and-modules.md`. Номери рядків нижче — за кодом на `v0.19.0` (HEAD `80dc34a`); код — правда, спека — намір.

## Рішення власника

- **26.10.2026 (етап 4):** чисте ядро + паритет; усе, що робить простір ЛІГА, стає загальним механізмом або модулем; для людини
  нічого не змінюється.
- **04.11.2026:** 4d-4 — прапорець `integrations` і старі псевдоніми (`profile`, `gitlab_*`) геть.
- **06.11.2026:** секрети в 4d-3 **копіюються**, оригінали (корінь `tasks.json`, оточення, `~/.claude/pipeline-feedback/`) лишаються
  до 4d-4.
- **07.11.2026:** власник доручив наступний етап автономно («Продолжаем следующий этап, работай автономно»).

## Похідне рішення: 4d-4 ділиться на три підрелізи

Інвентар 0.19.0 (див. «Додаток А») показав, що 4d-4 — це три незалежні шари з різним ризиком, кожен на десятки місць коду й
тисячі рядків тестів. Як 4d-3 (рішення власника 05.11.2026 — ділити), 4d-4 ділиться так:

| Підреліз | Версія | Що | Ризик |
|---|---|---|---|
| **4d-4a** (ця спека) | 0.20.0 | Напрямки ЛІГИ — остаточно явні (четвертий крок міграції), неявний адаптер напрямків і читання `profile` з записів — геть; `profile` лишається лише на межах (API `task-new`, спільний реєстр колег) | низький: лише створення задач і корені |
| 4d-4b | 0.21.0 | Останні копії (`gitlab_ssh_key`/`gitlab_host_ip` → `git-sync`, кореневий пароль превʼю → `vercel-publish`), запасний `Implicit` геть, ядро більше не читає оригіналів (корінь `tasks.json`, оточення, `pipeline-feedback`); видалення секретів з кореня `tasks.json` — окремим кроком міграції з бекапом | високий: немігрована ЛІГА лишається без ролей |
| 4d-4c | 0.22.0 | Прапорець `integrations` (вихідний гейт, `static-publish` за замовчуванням, `task-new`), значення API `'legacy'`, запасні гілки JS, `_liga_flow`, псевдоніми маршрутів `/api/gitlab-*` | середній: публічний контракт API |

Порядок — від найменш ризикового: 4d-4a не залежить від того, чи власник уже стартував мігровану ЛІГУ; 4d-4b прибирає запасний
шлях лише тоді, коли три релізи (0.17–0.20) мігрують ЛІГУ на першому старті й кажуть про кожен пропуск. Нумерація версій
зсувається: 1.0 стає після 0.22.0. **Видалення оригіналів поза `tasks.json`** (змінні оточення, файли `pipeline-feedback`) — не
справа Deai: ці джерела спільні з робочим інструментом ЛІГИ (design-office, «ЛІГА не чіпаємо», 14.10.2026). Deai лише перестає
їх читати (4d-4b); видаляти їх — рішення людини, коли інструмент ЛІГИ піде.

## Проблема

Після 0.19.0 усі шість ролей ЛІГИ — явні модулі, а **напрямки** — ні (у більшості установок): крок `liga-4d3a` пише `tracks` у
`space.json` лише за повного паритету з адаптером (`_compute_tracks` + `_unknown_values`, `app/liga_migrate.py:129`–`160`), інакше
`tracks-parity` / `tracks-unknown-values` — і ЛІГУ далі веде неявний адаптер:

- `_TrackView.adapter` (`app/serve.py:1768`): простір ЛІГИ (`_liga_like`, тобто `integrations`) без непорожнього списку `tracks`;
- `tracks.legacy_tracks/legacy_root/legacy_repos` (`app/tracks.py:194`–`262`) читають корінь старого `tasks.json`
  (`design_work_roots`, `design_work_root`, `profile_repos`) через `serve._legacy_cfg()`;
- `profile_repos()` (`serve.py:112`), `track_root`/`track_repo` (`:1832`, `:1849`), `label_tag(legacy=…)` (`tracks.py:172`),
  `task_ds`, `bin/roots.py` (`plan`, `roots_in_use`), `bin/registry.py:_work_root` (`:432`).

І **`profile`** досі синонім `track` у записах: `tracks.of_task` (`tracks.py:148`) читає `track`, інакше `profile` — бо задачі ЛІГИ,
створені до 0.15.0, мають лише `profile`, а колеги на старому інструменті шлють у спільний реєстр лише `profile`.

## Мета

1. **Паритет для людини:** ті самі мітки, `?ds=`, репозиторії, корені нових задач відомих напрямків, теки задач із реєстру —
   для мігрованої ЛІГИ; задачі, створені до 0.15.0, — ті самі мітки й ДС.
2. **Напрямки ЛІГИ — завжди явні** в її `space.json` після четвертого кроку міграції `liga-4d4a`.
3. **У рантаймі немає адаптера напрямків**: `legacy_tracks`/`legacy_root`/`legacy_repos`/`_LEGACY_LABELS`/`profile_repos` живуть
   лише в `app/liga_migrate.py` (міграція й так читає корінь). ЛІГА для напрямків — звичайний простір.
4. **`profile` не читається з записів задач**: `of_task` — лише `track`. `profile` лишається тільки на двох межах — вхідне поле
   API `task-new` (поблажливе, як у звичайному просторі) і спільний реєстр (пишемо для колег, читаємо як `track`, коли `track` нема).

## Не мета

- `gitlab_*`, кореневий пароль превʼю, запасний `Implicit`, читання оригіналів — 4d-4b.
- `integrations`, `'legacy'` в API, `_liga_flow` як ознака «потоку ЛІГИ» (лише його джерело репозиторіїв переїжджає, див. §5),
  запис `profile` у нові задачі ЛІГИ — 4d-4c (запис потрібен колегам, доки спільний реєстр читають старі машини).
- Новий інтерфейс редагування напрямків.

## Дизайн

### 1. Четвертий крок міграції `liga-4d4a`

`STEP_D = Step('liga-4d4a', {}, True, '-liga-4d4a', <stamp_re>, _entries_d)`, `ALL_STEPS = (A, B, C, D)`. Ролей крок не має
(`_entries_d` → `{}`); дві дії, обидві з бекапом цього кроку (`BACKUP_FILES` уже містить `tasks.json` і `space.json`), позначка
`migrations.liga-4d4a = {roles: [], tracks: bool, records: N, notes: [...]}`, відкат LIFO на чотири кроки.

**(а) Напрямки.** Пишуться рівно тоді, коли ЗАРАЗ діє адаптер: `tracks` у `space.json` нема **або** `tracks.normalize(raw, path,
roots=False)` порожній (той самий критерій, що `_TrackView.adapter`, — винести його в одну функцію `tracks.adapter_applies(raw,
path)` і кликати з обох місць до видалення адаптера; після — лише з міграції). Значення — `_compute_tracks` **без воріт
паритету**: id адаптера в його порядку, `label` з `_LEGACY_LABELS`, `root` розгорнутий, `repo`, `ds = id`, `default_track:
'united'`. Непорожній власний список — `tracks-present`, напрямки не чіпаємо (як 4d-3a).

Розбіжності, через які 4d-3a відмовлявся, — тепер **нотатки** позначки (коди без шляхів і значень; ids напрямків — можна):

| Нотатка | Коли | Що бачить людина після кроку |
|---|---|---|
| `root-dropped:<id>` | `normalize(roots=True)` відкинув корінь напрямку (системна/прихована тека, перетин з іншим простором) | нова задача цього напрямку лягає в теку простору ЛІГИ (адаптер клав би в той корінь) |
| `unknown-values` | у `tasks.json` є задача, чий напрямок не з переліку | нічого: мітка, ДС і репо невідомого значення однакові з адаптером (див. §3); лише API не створить нову з таким значенням |
| `default-root-differs` | корінь `united` ≠ спільному кореню адаптера | нічого для відомих напрямків; невідомий напрямок із реєстру (§4) лягає в корінь `united`, а не в спільний |
| `non-id-keys` | ключ `design_work_roots`/`profile_repos` поза `ID_RE` | свій корінь/репо такого ключа більше не діє для НОВИХ задач (старі теки на місці) |

Старт і `status` друкують нотатки одним рядком (`напрямки: записано; нотатки: root-dropped:seo, unknown-values`) — так людина знає,
що перевірити на «Підключеннях»/`space.json`.

**(б) Записи задач.** Кожна задача у `tasks.json` ЛІГИ, у якої `track` — не непорожній рядок, а `profile` — непорожній рядок,
дістає `track = profile` (значення як є, без звірки з `ID_RE`: ЛІГА завжди зберігала вільний рядок). `profile` у записі
лишається (спільний реєстр, §4). Запис — `atomic_write_json` файла задач ЛІГИ; у позначці — кількість (`records`). Файл, який не
читається, — `skip-tasks-unreadable` (як для інших кроків).

Крок нічого не робить і пише `skip-nothing`, коли напрямків писати не треба і записів без `track` нема. Порядок воріт — як у
`_plan` (шар, ЛІГА, `integrations`, тека, `space.json`, позначка/`held`, ранній `held`, git, файл задач). ⛔ Крок із
`skip-integrations-off`: адаптер такій ЛІЗІ й так не діє (`_liga_like` false) — паритет зберігається.

Перевірка в памʼяті перед записом (аналог `abort-provider`): `serve`-незалежна функція `tracks.normalize(new, path, roots=False)`
дає ті самі id і дефолт, що адаптер, інакше `abort-tracks` (новий код в `ABORT_CODES`).

### 2. Рантайм без адаптера

- `_TrackView.adapter` і гілки `adapter` у `_light`/`_load`/`track_root`/`track_repo`/`task_ds`/`label_tag(legacy=…)` — геть.
  `_liga_like` для напрямків більше не потрібен (лишається в інших місцях до 4d-4c).
- `track_root(sp, cfg, tid)`: знайдений → `root` або шлях простору; невідомий → `root` дефолтного; напрямків нема → шлях простору
  — для ВСІХ просторів. Параметр `cfg` геть (його читав лише адаптер). Прямий виклик `task_new` без `root` — шлях простору.
- `legacy_tracks`, `legacy_root`, `legacy_repos`, `_legacy_roots`, `_legacy_fallback`, `_LEGACY_IDS/_DEFAULT/_LABELS`,
  `FALLBACK_ROOT` переїжджають у `app/liga_migrate.py` (приватні). `serve.profile_repos()` і `serve._legacy_cfg()` для напрямків
  — геть (останній лишається, якщо його читають інші місця — 4d-4b).
- Немігрована ЛІГА (крок не застосовано: `held`, `path-in-git`, файл не читається) — простір без напрямків: мітка = значення як є,
  корінь нової задачі — шлях простору. Старт уже називає пропущений крок і причину; додається рядок «напрямки ЛІГИ не мігровані —
  нові задачі лягають у теку простору».

AST-охоронець `NoTracksAdapter`: `app/**/*.py` (крім `liga_migrate.py`) і `bin/*.py` не згадують `legacy_tracks`, `legacy_root`,
`legacy_repos`, `_LEGACY_LABELS`, `profile_repos`.

### 3. `of_task` — лише `track`

`tracks.of_task(task)` = `task['track']`, коли непорожній рядок, інакше `None`. Після кроку (б) задачі ЛІГИ, створені до 0.15.0,
мають `track` — мітка/ДС/репо ті самі. Звичайні простори `profile` ніколи не писали (`task_new`: `profile: null`), тож для них
нічого не змінюється. Вихід API: `/api/task` (`serve.py:6022`) і рядки задач (`:1894`, `:2282`) більше не віддають `profile` —
жоден клієнт його не читає (JS — перевірено інвентарем); `track` лишається.

Невідоме значення (`'United'`, `''`, ключ поза переліком) у мігрованій ЛІЗІ — паритет за побудовою: `label_tag` для ненайденого
дає `read_tag(v)` = адаптерне `_LEGACY_LABELS.get(v, v)` (ключі `_LEGACY_LABELS` — це id з переліку); `task_ds` — саме значення в
обох; `track_repo` — `''` в обох.

### 4. Спільний реєстр (`bin/registry.py`)

- Пуш — без змін: `SHARED` несе і `profile`, і `track` (колеги на старому інструменті читають `profile`).
- Пул — **одна функція межі** `_track_of_entry(e)`: `track`, коли непорожній рядок, інакше `profile`, коли непорожній рядок. Запис
  з реєстру без `track`, але з `profile`, лягає локально з `track = profile` (і `profile` як є).
- `_work_root(cfg, task)` → `serve.track_root(<простір ЛІГИ>, task['track'])` через явні напрямки (імпорт лінивий, як зараз).

### 5. API `task-new` і `_liga_flow`

- `track` — **суворий для всіх просторів**, ЛІГА теж: не за шаблоном — `bad-track`, нема в переліку — `unknown-track`.
- `profile` — вхідне поле на межі (його досі шле зовнішній клієнт — dev-pipeline): `profile` не рядок — `bad-profile`;
  використовується, лише коли це id напрямку простору (правило звичайного простору 0.15–0.19 — тепер для всіх); інакше
  ігнорується. Конфлікт `track` з використаним `profile` — `bad-track`.
- `_liga_flow(payload)`: ознака «`profile` — один із `profile_repos()`» → «`profile` чи `track` — id напрямку з непорожнім `repo`
  у просторі ЛІГИ реєстру» (явні напрямки ЛІГИ замість кореня `tasks.json`). Сама функція і 409 `no-integrations-space` — до 4d-4c.

### 6. `bin/roots.py`

`plan`/`roots_in_use` беруть корені з явних напрямків простору ЛІГИ (`serve.space_tracks` + `track_root`); «свій/спільний»
→ «свій корінь / тека простору» (`root` напрямку `None`). Тексти CLI оновлюються; поведінка `migrate --apply` та сама.

## Свідомі відмінності (для людини)

1. API `task-new` у ЛІЗІ не приймає довільний рядок напрямку: `track: 'United'` → 400 `unknown-track`; `profile: 'United'`
   ігнорується (задача — у `united`). Інтерфейс таких значень не шле (вбудованої форми нової задачі в ЛІГИ нема).
2. Нотатки `root-dropped`/`non-id-keys`/`default-root-differs` — корінь НОВОЇ задачі (див. таблицю §1); старі теки на місці.
3. `/api/task` і рядки задач без ключа `profile`.
4. Немігрована ЛІГА — без напрямків (§2).

## Відкат

0.20 → 0.19: спершу `bin/migrate_liga.py restore <stamp-d> --hold` (повертає `tasks.json` і `space.json`; інакше 0.19 читатиме
записані напрямки — що для неї теж валідно, але без адаптера для `[]` і з іншими коренями за нотатками). Далі — як у 0.19 (c, b, a).
`--hold` четвертого кроку тримає лише його (ранніх він не тримає — правило «ранній `held` тримає пізніші» не змінюється).
