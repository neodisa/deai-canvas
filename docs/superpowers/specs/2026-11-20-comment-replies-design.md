# Етап «Відповіді в коментарях» (0.34.0) — спека

**Статус:** напрям погоджено власником 20.11.2026 (п'ять відповідей і прототип на знімку справжнього Deai). Реліз — наступна
вільна мінорна версія після етапу «Перший запуск» (орієнтовно 0.34.0). Рівень строгості — повний: зміни зачіпають спільний
коментатор і схему Supabase.

Прототип — `scratchpad/proto2/` сесії (не в репо): знімок справжнього Deai з worktree (сервер у пісочниці, модуль `memo`,
задача t45) і справжнього опублікованого превʼю, а поверх — нове: гілка в картці, розділ «Нове», тост, «Без знімка: …»,
форма над макетом у токенах оболонки, смуга «без міграції».

## Навіщо

- Власник 20.11.2026: «Все-таки зараз стає критичним, що нема реплаїв у коментарях, щоб на них можна було відповідати».
  У не-цілях `2026-11-13-shell-comments-design.md` відповіді були відкладені — власник це рішення переглянув.
- Ревʼю живого продукту (SPA на Angular, 20.11.2026) знайшло два баги коментатора:
  1. знімок піна мовчки не зберігається на важких сторінках — 19 з 39 пінів без скриншота;
  2. `url`/`route` піна береться в момент ЗБЕРЕЖЕННЯ (`_addComment` читає `location`), а не кліку: SPA встигає змінити
     маршрут, і пін прив'язується не до тієї сторінки.
- Фідбек 16.11.2026: форма коментатора над макетом — «стара модалка». Перевірено 20.11: вона темна, але у власній палітрі
  (`#15181D`, Inter), з білою кнопкою, курсивною цитатою з бурштиновою смугою й англійськими «Leave a change request… /
  Cancel / Comment». На токени оболонки її не переводили (не-ціль спек 16.11).
- Знайдено під час прототипу: в опублікованому превʼю **кожна** картка коментаря, залишеного в Deai, каже «На іншій
  сторінці». Коментатор порівнює `meta.route` (у Deai завжди `/commented`) зі шляхом сторінки превʼю
  (`/it1/<page>/index.html`). Той самий клас, що баг 2.

## Рішення власника (20.11.2026)

1. **Де відповідати:** у Deai і в опублікованому превʼю. Власна панель коментатора поза Deai (живий продукт, чужі
   проєкти) гілки не малює, лише рядок «N replies» на картці з відповідями (принцип 6).
2. **Хто відповідає в превʼю:** будь-хто з посиланням, на будь-який відкритий коментар; імʼя питається один раз (те саме,
   що для коментаря); змінити й видалити — лише свої відповіді (створені в цьому браузері). На закриті — не відповідають.
3. **Агент:** бачить гілки (`inbox.py` під піном) і відповідає сам (`inbox.py reply`) — щоб питати, а не вгадувати. Лише в
   тих пінах, які й так бачить: локальні й доручені командні.
4. **Сповіщення:** карток Teams на відповіді НЕМАЄ. Нові відповіді позначаються лише в Deai (розділ «Нове», бейдж острівця,
   тост, число на вкладці).
5. **Схема:** командні відповіді — окрема таблиця `comment_replies` (відповідь = рядок). Локальні — всередині піна у файлі
   задачі.

## Що робимо

### 1. Дані

**Відповідь** — `{ id, author, text, ts, editedTs?, agent? }`:
- `id` — uuid клієнта (як у коментаря, `genId()`); `ts`/`editedTs` — рядок `ДД.ММ.РРРР ГГ:ХХ` (`nowStamp()`);
- `agent: true` — лише в тих, що написав агент (`inbox.py reply`), автор тоді `AI`. Коментатор і оболонка `agent` не ставлять
  ніколи. Це позначка інтерфейсу, не захист: публічний ключ дозволяє її підробити (як і будь-яке поле).

**Коментар** отримує необовʼязкове поле `replies: Reply[]` у порядку `ts`. Немає поля — немає відповідей.

**Локальний канал** (`<task>/.dc-local-comments.json`): `replies` лежить усередині піна. Злиття вкладки з диском (адаптер
`app/vendor/local-adapter.js`, наявне злиття по полях) для `replies` іде **по id відповіді**, трьома сторонами: `s` — диск,
`w` — що вкладка знала, `m` — що вкладка шле:
- відповідь, змінена вкладкою (`m` ≠ `w`), — з вкладки;
- відповідь з диска, якої вкладка не знала (написав агент), — лишається;
- відповідь, яку вкладка знала й прибрала, — прибрана.

**Командний канал** (Supabase, модуль `supabase-comments`): таблиця `comment_replies`:

```sql
create table if not exists public.comment_replies (
  id         text primary key,          -- uuid клієнта
  comment_id text not null,             -- id коментаря; БЕЗ зовнішнього ключа й каскаду (див. нижче)
  project_id text not null,             -- канал, як у comments
  author     text not null,
  text       text not null,
  ts         text,
  edited_ts  text,
  agent      boolean not null default false,
  created_at timestamptz default now()
);
```

- Індекс `(project_id)`.
- RLS — ті самі відкриті політики на чотири дії, що й у `comments`, ті самі гранти, `revoke truncate`.
- Незмінний `project_id` — власна функція тригера.
- Охоронець видалення: один `project_id` на запит, ≤ 100 рядків.
- Таблиця додається до публікації `supabase_realtime`.

Усе — за зразками наявного `schema.sql`, без нових прийомів: локального Postgres нема, SQL перевіряється лише статично.

- **Чому без зовнішнього ключа й каскаду.** Старі клієнти — заморожені превʼю до 0.34 і живий продукт — видаляють лише
  рядок `comments`. Із зовнішнім ключем без каскаду таке видалення впало б на коментарі з відповідями. Каскад зі
  statement-тригером-охоронцем не перевірити без справжнього Postgres. Тож новий адаптер сам видаляє відповіді коментаря
  перед ним. Відповіді, що осиротіли після старого клієнта, нешкідливі: їх ніхто не показує, бо відповідь чіпляється лише
  до наявного коментаря.
- **Файли.** Новий `app/modules/supabase-comments/replies.sql` (ідемпотентний, лише блок відповідей). Той самий блок —
  наприкінці `schema.sql` для нових установок. Тест вимагає, щоб блок у `schema.sql` дорівнював `replies.sql` дослівно.
- **Teams.** Тригер карток висить на `comments` — на відповіді він не спрацьовує, зміни в `supabase-teams` не потрібні.
- **Наявні проєкти.** Інструкція власнику: один раз виконати `replies.sql` у SQL-редакторі кожного проєкту Supabase,
  зокрема бази ЛІГИ. `schema.sql` повністю в базі ЛІГИ не запускати: у неї своя версія політик. Перед цим — переконатися,
  що в проєкті ще нема таблиці з іменем `comment_replies` (`create table if not exists` прийняв би чужу). **До справжніх
  проєктів міграцію застосовує лише власник, після явного «да».**

### 2. Коментатор (`commenter/`)

Усе нове — **опційне**. Без нових опцій і без поля `replies` поведінка й розмітка байт-у-байт як були: охороняють наявні
юніт- і живі тести та новий золотий тест (§7).

- **Носій поля.** `replies` переноситься як є: `stripRuntime` знімає `_pending` і з відповідей; `snapshot()` віддає
  копію `replies`; `getComments()` — теж.
- **Методи для хоста** (лише з `host`; без нього — `false`/`null`):
  - `reply(id, text)` → id нової відповіді. Автор — `getUser(...)` (той самий ланцюжок, що для коментаря, зокрема
    `host.userName`). Відповідь іде з `_pending`, коментар — теж. Перед першим `onChange` лунає `host.onReply(commentId,
    replyId)` (необовʼязковий колбек; так превʼю записує «свою» відповідь), потім звичайний `_persist`. На закритий
    коментар — `null`.
  - `editReply(id, rid, text)` — змінює текст, ставить `editedTs`.
  - `removeReply(id, rid)`.
  - Порожній текст — відмова (`false`/`null`), як у `editComment`.
- **Злиття з живими оновленнями.** У `_onExternalChange` для коментаря з `_pending`, який уже є в зовнішньому наборі,
  відповіді з `_pending` зливаються в зовнішню копію (за id). Відповідь, яку ще не підтвердив запис, не зникає з екрана,
  коли інший рецензент щось змінив.
- **Власна панель (без `host`).** Картка коментаря з відповідями має один рядок `N replies` (`1 reply`). Без відповідей —
  нічого. Гілки, поля відповіді й дій над відповідями там нема.
- **Вигляд форми від хоста** (рішення фідбеку 16.11):
  - **`host.theme()`** → обʼєкт значень токенів. Білий список імен: `s1 s2 s3 s4 line line2 hi mid lo dim sel sel-hover
    sel-tint-2 on-sel open bad local-pin`; інші ключі ігноруються. Значення — рядок без `;{}<>`, інакше ключ ігнорується.
    Коментатор ставить ці змінні на `.root`, додає клас `themed` і **окремий** `<style>` з правилами `.root.themed` для
    форм `.compose` і `.mcompose`. Основний `STYLE` не змінюється. Правила:
    - поверхня `--s2`, радіус 8, тінь як у поповерів оболонки, шрифт `system-ui`;
    - цитата цілі — тьмяний рядок без курсиву, рамки й бурштинової смуги, з тегом у моноширинному чипі;
    - поле `--s1` з рамкою `--sel` у фокусі;
    - адресат — сегмент, як фільтр панелі;
    - кнопки 28 px: «Скасувати» — `--s3`, головна — `--sel` / `--on-sel`.
  - Піни, підсвітка елемента й решта шару — без змін.
  - **`host.labels`** → `{ placeholder, cancel, submit, target, quote, area, multiTitle, clear }`. `target`/`area` —
    шаблони з `{tag}` і `{text}`, `quote` — з `{text}`, `multiTitle` — з `{n}`. Відсутній ключ — англійський текст, як
    зараз. Значення — лише текст (`esc`).
- **Баг 2 — контекст у момент вибору цілі.** `url`, `route`, `version`, `viewport`, `fp`, `outerHTML`/`text` знімка й
  `meta.ctx` фіксуються, коли ціль вибрано:
  - «Елемент» і «Текст» — клік чи виділення, що відкриває форму;
  - «Область» — відпускання миші;
  - «Кілька» — перший вибраний елемент; `fps` — як зараз, при кожному виборі.

  У момент збереження беруться лише текст, адресат, автор і `ts`. Маршрут, що змінився, поки форма відкрита, форму не
  закриває; пін їде з маршрутом моменту кліку. Полотно («Огляд», `anchors`) не змінюється: там контекст уже приходить із
  цілі.
- **Баг 3 — «На іншій сторінці» в режимі хоста.** У `snapshot().where` (і всюди, де хост бачить «elsewhere») при `host`
  сторінку визначає скоуп піна (`_inScope`: ітерація й сторінка з `meta.version`), а **не** `meta.route`. Без `host` —
  як було (живий продукт розрізняє сторінки маршрутом). План перевіряє, що `_inScope` у превʼю й у Deai справді розрізняє
  сторінку. Якщо ні — у превʼю версія сторінки мусить мати той самий вигляд, що в Deai (`<ітерація>/<сторінка>`).
- **Баг 1 — знімок.**
  - **Ніколи мовчки.** Будь-яка гілка, де знімка нема, пише `meta.shotMiss` — код причини:
    - `too-big` — понад ліміт вузлів чи SVG;
    - `no-lib` — `html2canvas` не завантажився (мережа, CSP);
    - `timeout`;
    - `render` — `html2canvas` кинув помилку;
    - `detached` — елемента вже нема в документі (SPA перемалювала);
    - `upload` — `uploadShot` відмовив чи не встиг; інлайн-знімок, як і зараз, у сховище не їде.

    Ліміти бібліотеки й рендеру рахуються окремо: перше завантаження `html2canvas` з CDN не з'їдає бюджет рендеру.
  - **Причина — з доказів, потім виправлення.** Першим кроком реалізації — стенд «важкої SPA» у живих тестах (тисячі
    вузлів, сотні інлайн-SVG-іконок, зміна маршруту через `pushState` під час відкритої форми). Він міряє, яка гілка гасить
    знімок. Якщо власник дозволить — ще агрегати по 39 пінах ревʼю 20.11, лише читання й без імен: чи є `meta.shotUrl`,
    режим, розмір знімка HTML. Виправлення — за причиною:
    - `too-big` через SVG → у клоні (`onclone`) SVG понад ліміт замінюються порожніми блоками того самого розміру. Знімок
      є, іконки — плашками. Ліміт вузлів — за вимірюванням на стенді (рендер ≤ 2 с); понад нього — `too-big`;
    - `detached` → у момент збереження елемент шукається за відбитком (`findMatch`) у поточному документі, якщо маршрут
      той самий; інакше — `detached`;
    - `upload` → одна повторна спроба, потім `upload`;
    - `no-lib` → необовʼязкова опція `shotLib` (адреса копії `html2canvas`) для хостів із CSP. Без неї — CDN, як зараз.
  - **Критерій.** На стенді кожен пін має або знімок, або `shotMiss`; після виправлення домінантної причини ≥ 90 % пінів
    стенду — зі знімком.
  - **Доставка в живий продукт** — поза цим репо: живий продукт вбудовує бандл з окремої копії `comment-layer`. Після
    релізу — інструкція власнику, який файл підмінити (`app/vendor/comment-layer.min.js`; API зворотно сумісний).

### 3. Сховища

- **`local-adapter.js`:** `clean()` пропускає `replies` (лише поля відповіді з §1); злиття по id (§1).
- **`dual-store.js`:**
  - `replies` їдуть разом із коментарем у його сховище (`_aud`);
  - новий геттер `repliesDown` — причина, чому командні відповіді недоступні, або `null`;
  - нове поле `supportsReplies(aud)`: локальне — завжди так, командне — `team.supportsReplies === true`.
- **Адаптер `supabase-comments`:**
  - **Читання** — паралельно `comments` і `comment_replies` каналу; відповіді чіпляються до коментаря за `comment_id`,
    сортуються за `ts`/`created_at`.
  - **Таблиці нема** — відповідь PostgREST `PGRST205`, `42P01` чи 404 на `comment_replies`: `supportsReplies = false`,
    `repliesDown = 'no-replies-schema'` (людський текст дає оболонка), коментарі працюють як зараз. Інша помилка читання
    відповідей — `repliesDown` з її текстом.
  - **Запис різницею**, як для коментарів: окремий кеш `writtenReplies`; upsert лише змінених; видалення відповідей, які
    адаптер знав і яких більше нема в коментарі.
  - **`remove(ids)`** — спершу відповіді цих коментарів (`comment_id in …` і `project_id = канал`), потім коментарі.
  - **Realtime** — і на `comment_replies`; та сама логіка «своє відлуння не перечитує».
  - **Знімок сесії** (`sessionStorage`) — включає відповіді.
- **Свій модуль коментарів** (`docs/modules/comments.md`): сховище оголошує `supportsReplies: true`, якщо зберігає
  `replies` (модуль, що тримає коментар цілим JSON, отримує це даром). Без оголошення — командні відповіді недоступні з
  причиною «модуль не підтримує відповідей».

### 4. Оболонка Deai (`app/comments-model.js`, `app/comments-view.js`, `app/app.js`)

Вигляд — як у прототипі; розмітка картки й класи наявні, нове — `cmt-thread*`, `cmt-reply*`, `cmt-rsum`, `cmt-rbox`,
`cmt-shotmiss`.

- **Рядок гілки** (між текстом/знімком і рядком дій). У рядку дій нової кнопки нема.
  - відкритий коментар без відповідей — «Відповісти»;
  - з відповідями — «› N відповідей · <автор останньої>, <ДД.ММ ГГ:ХХ>» і бурштинове «+K нова», якщо є нові;
  - клік розгортає гілку;
  - у розгорнутій гілці внизу поле «Відповісти…»: у фокусі воно росте до трьох рядків, зʼявляються «Скасувати» /
    «Надіслати» і підказка «⌘↵ — надіслати»; Esc у полі — скасувати.
- **Відповідь:**
  - автор (жирно), «змінено», час, текст;
  - відповідь агента — фіолетова крапка кольором локального піна (`--local-pin`) перед «AI»;
  - нова — тонований фон `--open` 10 % і чип «нова».
- **Дії над відповіддю** (іконки 22 px):
  - змінити — лише свою (автор = імʼя цього користувача);
  - видалити — будь-яку, з підтвердженням на місці «Видалити відповідь?» (наявний `confirmHTML`);
  - у закритих — жодних.
- **Закриті й командні без відповідей:**
  - **закритий коментар** — гілка лише для читання (згорнута, «› N відповідей»), без поля. Заперечити — «Повернути»,
    потім відповісти;
  - **командні відповіді недоступні** (`repliesDown` чи модуль без `supportsReplies`):
    - у панелі смуга з причиною — наявний `cmt-teamdown`; для `no-replies-schema`: «Відповіді команди недоступні: у базі
      немає таблиці відповідей — виконайте `replies.sql` модуля»;
    - на командних картках замість «Відповісти» — тьмяний рядок «Відповіді команди недоступні — причина вгорі панелі»;
    - локальні відповідають як завжди.
- **Видалення коментаря з відповідями** — питання «Видалити назавжди разом із N відповідями?».
- **«Нове»** (розширення моделі «нових» з 0.27.0):
  - розділ «Нові від команди» перейменовується на «Нове» (en: «New»);
  - туди йдуть і нові командні коментарі, і коментарі будь-якого каналу з новою відповіддю не від мене (зокрема
    відповідь AI на локальному піні);
  - «Новизна» відповіді — та сама, що в коментаря: автор ≠ я і id не в наборі «бачив» задачі (`dc-seen:*`). Набір
    посувається так само (панель відкрита, картка видима; «Показати»);
  - бейдж острівця (бурштиновий) рахує коментарі з новим — і новий коментар, і нову відповідь;
  - «+K» на фільтрі — і для «Для AI», якщо відповів AI;
  - тост — лише на те, що прийшло під час сесії: «Нова відповідь від <автор> · #N» з «Показати» (розгортає гілку й
    прокручує до неї);
  - число на вкладці — див. §6.
- **Пошук** — і по тексту та авторах відповідей.
- **Тексти** — у словнику оболонки (uk/en) з правильними формами множини: «1 відповідь / 2 відповіді / 5 відповідей»;
  «1 reply / 2 replies».

### 5. Публічне превʼю (`app/ext-comments.js`, `PREVIEW_HOST_ARG`)

- Та сама гілка (той самий `commentsPanelHTML`), права — через наявні `st.actions` / `st.isOwn`:
  - відповісти — на будь-який відкритий;
  - змінити й видалити — лише свої (id відповідей ідуть у той самий `dc-own:<канал>` через `host.onReply`);
  - на закритих — нічого.
- Імʼя — тим самим діалогом «Як вас підписати в коментарях?» перед першою відповіддю, якщо імені ще нема; `prompt()` —
  ніколи.
- «Нового» в превʼю нема (як і зараз).
- Форма над макетом у превʼю — теж у токенах оболонки превʼю (`host.theme`/`host.labels` у `PREVIEW_HOST_ARG`).
- Сумісність: превʼю — заморожена копія. Нове отримують лише перепубліковані; старі превʼю відповідей не бачать і не
  ламаються.

### 6. Агент і сервер

- **Функції модуля** (`server.py`; обидві нові функції необовʼязкові, `ROLE_OPTIONAL_FUNCTIONS['comments']`):
  - `list(ctx, channel)` — коментарі з `replies`. Таблиці відповідей нема — без них і без помилки;
  - `reply(ctx, channel, id, text, author)` — **нова, необовʼязкова**: вставляє відповідь (`agent = true`, uuid сервера,
    `ts` за `nowStamp`) лише до наявного коментаря цього каналу;
  - `recent(ctx, channel)` — і відповіді: `{id, ts, author, status: 'open', version, parent}`, лише відповіді на відкриті
    коментарі, ≤ 200, без тексту;
  - `check(ctx)` — коментарі доступні, відповідей нема: `ok: true`, `replies: false`, `detail` каже, що виконати
    `replies.sql`. Таблиця є — `replies: true`.
- **`GET /api/comment-news`** — додає відповіді: командні — з `recent`; локальні — відповіді `agent: true` з файлу задачі.
  Клієнт рахує їх тим самим набором «бачив».
- **`bin/inbox.py`:**
  - під кожним показаним піном — гілка: `↳ відповіді (N):` і рядки `<автор>, <ДД.ММ ГГ:ХХ>: <текст>` (≤ 300 символів
    кожна, через наявне очищення `agent_line`);
  - пін без знімка — `↳ без знімка: <причина>`;
  - нова підкоманда `reply <ID> --text "…"`: той самий пошук за префіксом, що в `resolve`;
    - локальний пін — атомарний запис у файл задачі (той самий прийом, що `write_local_resolved`);
    - командний — через `reply` модуля, **лише доручений AI** (недоручений — відмова з поясненням);
    - модуль без `reply` — відмова «модуль не підтримує відповідей»;
    - закритий пін — відмова;
    - `--dry-run`, текст ≤ 4000.
- **Довідка агенту** — `app/templates/agents.md` (AGENTS.md простору): коли питати в гілці (`inbox.py reply`) замість
  того, щоб вгадувати; що відповідь у командному піні бачать колеги.

### 7. Перевірка

- **Юніт JS** (`commenter/test`, `tests/*.test.mjs`):
  - **Коментатор:**
    - `reply/editReply/removeReply`, `onReply` перед першим `onChange`, `null` на закритому;
    - `stripRuntime` вкладених `_pending`;
    - злиття живого оновлення з відповіддю в польоті;
    - контекст піна в момент вибору цілі: `location` змінено між відкриттям форми й збереженням — у піні маршрут кліку;
    - `shotMiss` на кожну гілку;
    - `host.theme`: білий список і відмова значень з `;{}<>`; `host.labels`: `esc`;
    - `where` у режимі хоста за скоупом;
    - **золотий:** `init` без нових опцій — DOM тіньового кореня й `STYLE` дослівно як до етапу (еталон з поточного
      бандла).
  - **Сховища:** злиття відповідей по id (три сторони), `dual-store` (`repliesDown`, `supportsReplies`), адаптер
    `supabase-comments` проти наявного фейкового REST (читання двох таблиць, запис різницею, `remove` спершу відповіді,
    `PGRST205` → `no-replies-schema`, realtime).
  - **Панель:** розмітка гілки, множина uk/en, права Deai і превʼю, закриті лише для читання, смуга й нотатка
    «недоступні», «Нове» з відповідями, пошук по відповідях.
- **Python:**
  - `list`/`recent`/`reply`/`check` модуля (фейковий REST);
  - `inbox.py` (вивід гілки, `reply` локальний і командний, відмови, `--dry-run`);
  - `/api/comment-news` з відповідями;
  - SQL статично: блок `schema.sql` == `replies.sql`, RLS увімкнено, чотири політики, `revoke truncate`, публікація
    realtime, жодного `references` / `on delete cascade`.
- **Живі** (по одному файлу, модуль `memo` — фікстуру навчити `replies`):
  - відповідь у Deai — локальна й командна; відповідь AI через `inbox.py` → тост, «Нове», бейдж, вкладка;
  - превʼю: імʼя один раз, своя змінюється/видаляється, чужа — ні, закритий без поля, `prompt()` ніколи;
  - форма в токенах оболонки — обчислені кольори з оболонки; без `host` — як була;
  - SPA-стенд: `pushState` між кліком і збереженням → маршрут кліку;
  - стенд знімків (§2, баг 1);
  - превʼю: картки з Deai без «На іншій сторінці».
- **Мутації** — на кожну нову перевірку.
- **Заборонений список** — перед злиттям.

## Не-цілі

- Згадки людей (@), реакції, вкладені гілки (лише один рівень), вкладення в відповідях, редагування чужих відповідей.
- Картки Teams на відповіді (рішення власника 4).
- «Нове» в публічному превʼю.
- Гілка у власній панелі коментатора поза Deai (лише «N replies»).
- Справжній замок прав у Supabase (RLS за автором) — як і для коментарів, поза етапом.
- Міграція наявних даних: відповідей до 0.34 нема.

## Сумісність

- **Коментатор поза оболонкою** (живий продукт, чужі проєкти, `/commented` без `host=1`) — без нових опцій той самий; бере
  виправлення багів 1–2 (контекст у момент кліку, `shotMiss`). Нове API лише опційне (принцип 6).
- **Заморожені превʼю до 0.34** працюють із тією самою таблицею `comments`; `comment_replies` не бачать. Видалений там
  коментар лишає відповіді-сироти — їх ніхто не показує.
- **Простір ЛІГИ:** до виконання `replies.sql` у базі ЛІГИ — смуга «відповіді команди недоступні»; локальні відповіді
  працюють.
- **Після релізу** — нагадати власнику перепублікувати активні превʼю (змінилася обгортка превʼю й коментатор у ній).

## Ризики

- **Великий коментатор** (~2100 рядків): усе нове — гілками під `host` / наявністю поля. Шлях без опцій охороняє
  золотий тест плюс наявні тести.
- **SQL без живої бази:** лише відомі з `schema.sql` прийоми; без каскадів; перевірка статична; застосування — власник.
- **Гонки:** дві відповіді одночасно — два рядки, конфлікту нема. Одночасна правка однієї відповіді — виграє остання
  (правити можна лише свою).
- **Знімок:** виправлення залежить від виміряної причини. Якщо стенд не відтворить 19 з 39, рішення — за агрегатами
  ревʼю (з дозволу власника). Мінімум, що гарантовано, — причина видима.
