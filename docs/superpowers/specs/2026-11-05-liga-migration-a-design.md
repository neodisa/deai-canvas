# Етап 4d-3a: міграція простору ЛІГА — механізм, напрямки, трекер, дашборд, Teams (0.17.0)

Дата: 05.11.2026. Попередній етап — 4d-2 (0.16.0, неявний постачальник і закон ізоляції). Дорожня карта —
`docs/design/spaces-and-modules.md`.

## Рішення власника

- **26.10.2026 (етап 4):** чисте ядро + паритет; усе, що робить простір ЛІГА, стає загальним механізмом або модулем.
- **04.11.2026:** 4d-3 — явні модулі ЛІГИ з **автоматичною міграцією конфігу з бекапом**.
- **05.11.2026:** розвідка показала, що шість ролей ЛІГИ роблять речі, яких вбудовані модулі через `space.json` не виражають
  (канал коментарів за `comment_project`, плоскі дзеркала git-синку, окрема гілка публікації з паролем 1100). 4d-3 ділиться
  на **три підрелізи**: **4d-3a (ця спека, 0.17.0)** — механізм міграції + напрямки + `tracker`, `dashboard`, `notify`;
  4d-3b (0.18.0) — `comments` (схема каналів) і `vcs` (плоскі дзеркала); 4d-3c (0.19.0) — `publish`. 4d-4 стає 0.20.0.
  Кожен крок мігрує лише те, що модуль уже вміє вести; решта ролей лишається неявною (ядро часткову міграцію підтримує:
  роль без явного модуля в просторі з інтеграціями — `Implicit`).
- **05.11.2026:** секрети **копіюються**, оригінали лишаються (корінь старого `tasks.json`, змінні оточення,
  `~/.claude/pipeline-feedback/`): їх досі читають інструменти `bin/`, і відкат на 0.16 працює без ручних дій. Перед записом —
  датований бекап. Прибирання оригіналів — 4d-4.

## Проблема

Простір ЛІГА (запис реєстру з `legacy: true`, `integrations: true`) досі бере конфіг ролей не зі свого `space.json`, а з
кореня старого `tasks.json` і з оточення: `jira_base` + `JIRA_EMAIL`/`JIRA_TOKEN` (або файли `pipeline-feedback`) для
трекера; `supabase_url`/`supabase_key` для дашборда, Teams і коментарів; `design_work_root(s)`/`profile_repos` для напрямків
(адаптер `tracks.legacy_tracks`). На екрані «Підключення» ці ролі ЛІГИ — «вбудовані» (`'legacy'`), їх не видно й не
налаштувати. Дві ролі (`dashboard`, `notify`) ще й покладаються на прапорець `ctx['legacy']`, який модулі читають
(`supabase-dashboard/server.py` ≈393, `supabase-teams/server.py` ≈233–347): база ЛІГИ — стара схема comment-layer, ключ —
публікабельний, `teams_notify_health` нема. Явний запис модуля цього виразити не може: `check` відповів би `public-key`.

## Мета

1. **Механізм міграції** ЛІГИ: автоматичний, ідемпотентний, «все або нічого» за розрахунком, з датованим бекапом і
   відкатом однією командою.
2. **Напрямки** ЛІГИ — явні `tracks` у `space.json` (вимога з плану 4d-1, «для 4d-3»), з перевіркою паритету з адаптером.
3. **`tracker`, `dashboard`, `notify`** ЛІГИ — явні вбудовані модулі (`jira-tracker`, `supabase-dashboard`,
   `supabase-teams`) у `space.json`, секрети — у `secrets.json`; поведінка для людини — та сама.
4. **Прапорець `ctx['legacy']` у модулях замінює задокументоване налаштування** `compat` (див. §3) — однаково для явного
   запису й для неявного шляху.
5. **Закон ізоляції охоплює мігровані записи**: запис модуля з позначкою `shared_state: true` (її ставить міграція) у
   тестовому прогоні поводиться як неявний постачальник — шов-фейк → відмова → справжній виклик.

## Не мета

- `comments`, `vcs` — 4d-3b; `publish` — 4d-3c. Вони лишаються неявними (`Implicit`, `'legacy'` у `capabilities`).
- Прибирання оригіналів у корені `tasks.json` / оточенні, прапорця `integrations`, `gitlab_*`, `profile` — 4d-4.
- Простір ЛІГА при вимкненому шарі (`DC_TASKS_FILE` без `DEAI_HOME`) і незафіксований простір запиту — реєстру нема,
  `space.json` нема: лишаються неявними, як у 0.16.0.
- Сервісний ключ Supabase (`SUPABASE_SERVICE_KEY`, лише оточення, синк з CLI) — не мігрує: найпривілейованіший секрет, у
  простору для нього місця нема.

## Дизайн

### 1. Коли й де біжить міграція

- **Коли:** раз на старті сервера канваса (`serve.py main`, ДО відкриття порту) і на вимогу командою
  `bin/liga_migrate.py run`. Не з `load_registry`, не з обробників запитів, не з інших інструментів `bin/`.
- **Не біжить:** шар вимкнено; ізольований прогін (`implicit.isolated()`) на старті сервера — щоб наявні живі тести й
  еталони ЛІГИ не змінились; виняток — тестовий шов `DC_MIGRATE_LIGA=1` (лише разом із тимчасовим `DEAI_HOME`, НЕ справжнім
  `~/.deai`), яким живий тест міграції вмикає її на старті; юніт-тести кличуть функцію міграції напряму; у реєстрі нема запису
  з `legacy: true`; запис уже має позначку
  §2; тека простору ЛІГИ (`path` запису) не існує; тека простору лежить у робочому дереві git (є `.git` у ній чи в предку —
  `space.json` не має потрапити в чужий коміт). Кожна причина пропуску — код у звіті (`skip-*`), без винятку назовні.
- **Де:** `space.json` — `<path ЛІГИ>/space.json` (як у кожного простору); секрети — `<DEAI_HOME>/secrets.json` під id
  простору ЛІГИ.
- Помилка міграції ніколи не валить старт: сервер стартує як 0.16 (усе неявне), звіт пише код і причину в stderr і у
  `<DEAI_HOME>/migrations/last.json` (без значень секретів).

### 2. Позначка й ідемпотентність

`space.json` дістає ключ верхнього рівня:

```json
"migrations": {"liga-4d3a": {"at": "2026-11-05T12:00:00", "roles": ["tracker", "dashboard"], "tracks": true,
                             "backup": "20261105-120000-liga-4d3a"}}
```

Є позначка — міграція не біжить (навіть якщо людина потім вимкнула модуль на екрані «Підключення»: це її рішення).
Невідомі ключі `space.json` наявні записувачі вже зберігають (`write_module_state`, `update_space`) — це закріплюється тестом.

### 3. Що розраховується (в памʼяті, до будь-якого запису)

- **Напрямки:** усі id адаптера (`united`, `liga360`, `seo`) плюс ключі `design_work_roots` і `profile_repos`; `label` — з
  `tracks._LEGACY_LABELS` (інакше id); `root` — розгорнутий `tracks.legacy_root(cfg, id)`; `repo` — з `profile_repos`;
  `default_track: "united"`. Перевірка паритету: `tracks.normalize(<розраховане>, path)` дає для КОЖНОГО id той самий корінь,
  репо й мітку, що адаптер (`legacy_tracks`/`legacy_root`/`legacy_repos`/`label_tag`), інакше — `abort-tracks-parity` (міграція
  цілком не пише нічого). Якщо в `space.json` уже є непорожні `tracks` — напрямки не чіпаємо (`tracks: false` у позначці).
- **`tracker`** (`jira-tracker`): `settings {base, email}`, `secrets {token}` — з тих самих джерел і в тому самому порядку, що
  `install_config.jira_config()` поза ізоляцією (корінь → оточення → `pipeline-feedback`). Неповна трійка — роль не мігрує
  (лишається неявною, як і було «tracker-unconfigured»).
- **`dashboard`** (`supabase-dashboard`): `settings {url, table: "overview_projects", compat: "comment-layer"}`,
  `secrets {key}` з `supabase_config()`. Нема пари — не мігрує.
- **`notify`** (`supabase-teams`): `settings {url, compat: "comment-layer"}`, `secrets {key}`. Нема пари — не мігрує.
- Кожен мігрований запис: `enabled: true`, `shared_state: true`.
- Якщо модуль уже є в `space.json` (людина щось вмикала) — цю роль не чіпаємо (`roles` у позначці її не має).
- Перевірка: для кожної мігрованої ролі `deai_modules` має вирішити саме цей модуль (`_provider_for` на розрахованому
  `space.json` у памʼяті) — інакше `abort-provider`.

### 4. Налаштування `compat` замість `ctx['legacy']`

`supabase-dashboard` і `supabase-teams` дістають необовʼязкове налаштування `compat` (тип `select`, значення `""` |
`"comment-layer"`, типово `""`), задокументоване в `module.json` і `docs/modules/authoring.md`: «база — стара схема
comment-layer: публікабельний ключ дозволений, `teams_notify_health` нема». Модулі читають `settings.compat`, а НЕ
`ctx['legacy']`; неявний шлях (`dashboard.legacy_ctx`, `notify.legacy_ctx`) кладе `compat: "comment-layer"` у `settings`
(прапорець `legacy` у ctx лишається до 4d-4 лише для зворотної сумісності чужих модулів — вбудовані його не читають).
`jira-tracker` прапорця не читав — без змін.

### 5. Запис

Порядок (усе — під наявними замками, `WRITE_LOCK` не тримається довше одного запису):

1. **Бекап:** `<DEAI_HOME>/backups/<YYYYMMDD-HHMMSS>-liga-4d3a/` (0700) — копії старого `tasks.json`, `space.json` ЛІГИ (якщо
   є), `secrets.json` (0600), `spaces.json`; `manifest.json` бекапу (шляхи-джерела, sha256, версія). Невдача бекапу —
   `abort-backup`, нічого не пишемо.
2. **Секрети:** злиття в `secrets.json` (`deai_modules.write_secrets` для кожного модуля) — лише ключі мігрованих ролей.
3. **`space.json`:** один атомарний запис (злиття з наявним вмістом: `name`, `color`, чужі ключі — як були) — `modules`,
   `tracks`/`default_track` і позначка `migrations` разом.

Збій між 2 і 3 лишає зайві секрети без записів у `space.json` — нешкідливо (їх ніхто не читає), наступний старт повторює
міграцію з нуля (позначки нема). Кеші (`_CAPS`, `own_sig`) уже ключуються відбитком `space.json` — сервер, що працює, побачить
зміну на наступному запиті.

### 6. Відкат і статус

`bin/liga_migrate.py`:
- `status` — є запис ЛІГИ? позначка? останній звіт `last.json`; список бекапів;
- `dry-run` — розрахунок §3 і звіт (ролі, напрямки, причини пропуску) БЕЗ запису й без значень секретів;
- `run` — §5;
- `restore <бекап>` — повертає `space.json` ЛІГИ й `secrets.json` з бекапу (старий `tasks.json` і `spaces.json` міграція не
  змінює, тож їх не чіпаємо; копії лишаються в бекапі для ручного відновлення). Після `restore` позначки нема — наступний
  старт мігрує знову; щоб не мігрував — `restore --hold` пише `"migrations": {"liga-4d3a": {"held": true}}`.

### 7. Закон ізоляції для мігрованих записів

Запис модуля з `shared_state: true` — спільний стан ЛІГИ, хоч і явний. Для ролей `dashboard`, `tracker`, `notify` ядро
вирішує такий запис так само, як `Implicit`: `implicit.route()` (шов-фейк ролі → відмова в ізольованому прогоні → справжній
виклик з `module_ctx`). Сам прапорець — звичайне поле запису `space.json` (людина бачить його в файлі; екран «Підключення»
його не показує й не змінює). `Implicit.shared` і `.fake_env` — та сама таблиця, що для неявного постачальника
(`implicit.for_role(role)`), тепер читається і для явних записів.

### 8. Що бачить людина

- Екран «Підключення» ЛІГИ: картки `jira-tracker`, `supabase-dashboard`, `supabase-teams` — увімкнені, з налаштуваннями
  (секрети — приховані, як у будь-якого простору); решта ролей — «вбудовані», як у 0.16.
- `capabilities` ЛІГИ: `tracker`/`dashboard`/`notify` — id модулів; `publish`/`comments`/`vcs` — `'legacy'`. JS екрана
  «Підключення» вже показує модулі звичайних просторів — треба лише, щоб `LEGACY_ROLES`-гілка (`connections-model.js` ≈317)
  не дублювала картку для ролі, яку веде явний модуль (план, Task 1 — знімок, далі правка, якщо знімок покаже дубль).
- Вкладка «Команда», статуси Jira, тиша Teams — працюють як у 0.16 (той самий URL, таблиця, канал).

## Паритет і перевірки

- **Знімок 0.16.0 до змін коду:** `tests/fixtures/liga-migration/before-4d3a.json` — для ЛІГИ з конфігом (вигадані значення):
  `capabilities`, `/api/spaces` (картки ролей), `/api/task` (напрямки, мітки, `?ds=`), статуси трекера/рядки дашборда/стан тиші
  через шви-фейки, `ctx`, які отримують модулі трьох ролей (через підміну `deai_modules.call`), `check` трьох модулів на тих
  самих ctx.
- **Паритет після міграції:** ті самі сценарії на мігрованому просторі дають ті самі результати, крім задокументованих
  відмінностей (`capabilities` трьох ролей — id модулів; `ctx` — з `module_ctx` замість легасі-збирача: ті самі значення
  налаштувань і секретів, `compat` замість `legacy`).
- **Міграція:** ідемпотентність (другий запуск — нічого); кожна причина пропуску й `abort-*` — окремий тест, нічого не
  записано; бекап — повний, права 0700/0600, sha256 у маніфесті збігаються; `restore` повертає побайтно; `--hold` не мігрує;
  збій між секретами й `space.json` — наступний запуск доводить до кінця; невідомі ключі `space.json` збережено; жодного
  значення секрету в звітах/stderr/`last.json`.
- **Ізоляція:** мігрований запис із `shared_state` у тестовому прогоні — фейк / відмова, модуль не кличеться; без
  `shared_state` — як звичайний модуль.
- **Модулі:** `compat: "comment-layer"` дозволяє публікабельний ключ і пропускає `teams_notify_health`; `ctx['legacy']`
  без `compat` більше нічого не змінює.
- Кожен новий охоронець — мутацією; повні прогони (`npm test`, обидва Python, живі по одному); живий тест: старт сервера
  з тимчасовим `DEAI_HOME` і ЛІГОЮ з конфігом → картки модулів на «Підключеннях», статуси на «Задачах».

## Свідомі відмінності від 0.16.0

- ЛІГА з конфігом після першого старту 0.17 — `tracker`/`dashboard`/`notify` явні (id у `capabilities`, картки на
  «Підключеннях», налаштування редагуються).
- Зміна токена Jira в `pipeline-feedback` чи оточенні більше не діє на ЛІГУ: копія — у `secrets.json` (міняти на екрані
  «Підключення»). Те саме — ключ Supabase в корені `tasks.json`.
- `supabase-dashboard` і `supabase-teams` читають `settings.compat`, а не `ctx['legacy']` (свій модуль, що підробляв ЛІГУ
  прапорцем, більше цього не може — прапорець лише для неявного шляху).

## Відомі обмеження

- Відкат на 0.16 після міграції: 0.16 не знає `compat` → явний `supabase-dashboard`/`supabase-teams` ЛІГИ відповість
  `public-key`. Перед відкатом — `bin/liga_migrate.py restore <бекап> --hold`.
- Тека ЛІГИ в робочому дереві git чи неіснуюча — міграції нема (`skip-path-in-git` / `skip-no-path`), ЛІГА лишається як у 0.16.
- Мігрований токен не синхронізується з оригіналом (див. «Свідомі відмінності»).
