## Проблема

Після етапу 1 простір без інтеграцій не може опублікувати жодного превʼю (409), не може
підключити свою дизайн-систему до інспектора, і нема способу щось «підключити»: усе, що
ходить назовні, — зашитий код ЛІГА за одним прапорцем `integrations`.

## Мета 2а

1. **Каркас модулів**: модуль = тека, роль = інтерфейс, який кличе ядро; у 2а — лише
   **вбудовані** модулі `app/modules/<id>/`; налаштування — у `space.json`, секрети — окремо.
2. **`static-publish`** (роль `publish`) — публікація в теку на диску; за замовчуванням діє в
   кожному просторі без інтеграцій.
3. **`css-tokens`** (роль `tokens`) — токени дизайн-системи з CSS-файла для інспектора.

Поза 2а: свої модулі з `<простір>/modules/` і довіра до них (етап 3, з діалогом); свій Vercel,

НЕ чіпаємо: він і далі діє лише в просторі з `integrations: true`.

## Модель

### Файли

- Ядро: `app/deai_modules.py` (НЕ `modules.py`: `bin/` стоїть у `sys.path` попереду й імпорт
  неоднозначний). Вбудовані модулі: `app/modules/<id>/module.json` + `app/modules/<id>/server.py`.
- CLI в 2а нема (агент і людина працюють через HTTP API нижче).

### `module.json`

```json
{"api": 1, "id": "static-publish", "name": "Публікація в теку", "version": "1.0.0",
 "roles": ["publish"],
 "settings": [
   {"key": "folder", "type": "path", "label": "Тека для превʼю",
    "default": "{home}/deai-published/{space_id}", "required": true},
   {"key": "password", "type": "secret", "label": "Пароль превʼю (необовʼязково)"}
 ]}
```

- `api` — рівно `1`, інакше модуль відхиляється (`bad-manifest`); `id` — `^[a-z0-9][a-z0-9-]{0,39}$`
  і збігається з назвою теки; кожна заявлена роль мусить мати функцію в `server.py`.
- Ролі: `publish`, `tokens` (кличе ядро в 2а); `comments`, `vcs`, `tracker`, `dashboard`,
  `notify` — зарезервовані (ядро їх не кличе).
- `settings[].type`: `text`, `path`, `bool`, `select` (`options: [{"value", "label"}]`),
  `secret`. Значення `secret` НІКОЛИ не пишуться в `space.json`, у відповіді API, логи й тексти
  помилок (лише `set: true|false`).
- `path`: `expanduser`; відносний — від теки простору; підстановки `{home}`, `{space}`
  (тека простору), `{space_id}` — зберігаються СИМВОЛЬНО в `space.json` (абсолютні шляхи
  ламали б колегу, з яким ділять теку) і підставляються під час читання.

### `server.py` і виклик

| Роль | Функція | Контракт |
|---|---|---|
| усі | `check(ctx) -> {"ok": bool, "error"?: str, "detail"?: str}` | без побічних ефектів (нічого не створює) |
| `publish` | `publish(ctx, build_dir, task) -> {"path": str}` | забрати зібрану теку; `task` = `{id, title, dir}` |
| `tokens` | `tokens(ctx) -> {"tokens": {name: [values]}, "source": str}` | токени ДС |

- `ctx` = `{"space": {id, path}, "settings": {…підставлені, без секретів…}, "secrets": {…лише
  цього модуля, оголошені в маніфесті як `secret`…}, "folder_ok": f(folder) -> (ok, код),
  "ModuleError": клас}`. Останні два — не дані, а засоби ядра: модулі НЕ імпортують ні `serve`, ні
  `deai_modules` (їхній список імпортів — явний stdlib-allowlist у тестах), тож правило теки
  публікації й клас помилки модуль отримує в `ctx`. `ModuleError` із кодом із таблиці статусів
  `call()` пропускає як є (текст очищено від секретів, ≤300), невідомий код стає `module-error`.
  `secrets.json` читається лише для модуля, що оголосив `secret`-налаштування: зіпсований файл не
  ламає `css-tokens`.
- Завантаження вбудованих: читаємо байти `server.py` один раз, `exec(compile(src, path, 'exec'))`
  у свіжий `types.ModuleType("deai_mod_<id>")`, без `importlib` з шляху й без `__pycache__`.
  Кеш за (шлях, mtime_ns, розмір, inode) обох файлів. Маніфест, що не пройшов перевірку, НЕ
  виконує `server.py` взагалі. `SyntaxError` / помилка імпорту / невідповідність маніфесту →
  модуль `status: "error"` з текстом (кешується до зміни файла).
- Будь-який виклик функції модуля — у `try/except BaseException` (окрім `KeyboardInterrupt`):
  → `module-error` з текстом, із якого вирізано значення секретів, ≤300 символів. Модуль має
  повний доступ до процесу — у 2а лише вбудовані, тож це межа, а не діра (див. «Межі»).
- `check` кличеться лише при `module-enable`, `module-settings`, `module-check` (не на кожному
  `GET`); останній результат кешується в памʼяті процесу. Тайм-аут 5 с (виклик у робочому
  потоці; по тайм-ауту — `check-timeout`). `tokens` кличеться з тим самим тайм-аутом (воно лише
  читає, потік-сирота нічого не зіпсує); `publish` — БЕЗ тайм-ауту: виклик у робочому потоці, що
  не вклався б, копіював би далі вже без замків диспетчера.

### Стан модулів простору

- **Увімкнення й налаштування** — у `space.json`: `"modules": {"<id>": {"enabled": bool,
  "settings": {…символьні…}}}`. Зберігаються лише явні рішення людини.
- **Неявне типове**: `static-publish` діє в просторі без `integrations`, доки в `space.json`
  нема явного `modules["static-publish"]` (так він працює і в просторах із v0.1.0, і в теках,
  підхоплених через «Новий простір», — без жодного запису на диск). У просторі з
  `integrations: true` неявного типового нема (зашитий шлях ЛІГА).
- **Запис `space.json`** — читання-зміна-запис під `WRITE_LOCK` (і ніколи
  `load_registry`/завантаження модулів під ним); перевірка `role-taken` — на свіжо прочитаних
  даних під тим самим локом; невідомі ключі зберігаються; нечитабельний `space.json` →
  409 `space-json-unreadable` (не перезаписувати); шар вимкнено чи порожній `path` → 409
  `spaces-off`. Порядок для `module-enable` з секретами: спершу `secrets.json`, потім
  `space.json` (сирітський секрет нешкідливий; увімкнений модуль без секрету — ні).
- **Секрети** — `<DEAI_HOME>/secrets.json`: `{"<space-id>": {"<module-id>": {"<key>": "<value>"}}}`.
  Після кожного запису — явний `chmod 0600` (і `0700` на `DEAI_HOME`); на Windows — no-op,
  записано в «Межах». У запиті: ключ відсутній → лишити; `null` → видалити; рядок → записати.
  `module-disable` секрети й налаштування НЕ видаляє (повторне ввімкнення їх повертає).
  Файл є, але не читається, — 409 `secrets-unreadable` (НЕ «порожньо»: це мовчки зняло б пароль
  превʼю); не записати `space.json`/`secrets.json` — 500 `unwritable`.
- **Постачальник ролі**: увімкнений (явно чи неявно), завантажений без помилки модуль із
  цією роллю; **один на роль** — друге ввімкнення → 409 `role-taken`. Увімкнений, але
  відсутній на цій машині модуль → у каталозі `status: "missing"`, постачальником не є.
- Простір із `integrations: true`: роль `publish` без явно ввімкненого модуля = **зашитий
  шлях ЛІГА** (`legacy`); явно ввімкнений `publish`-модуль має пріоритет. Не зафіксований
  простір запиту (поза запитом) → `legacy`, як `integrations_on()`.
- **`capabilities`** — `deai_modules.capabilities(space)`, а `serve.py` додає їх у відповіді
  (НЕ в `spaces.describe()` — точні тести рівності й опитування не мають вантажити модулі):
  `{"publish": "<id>" | "legacy" | null, "tokens": "<id>" | null}` — у `/api/task`, `/api/tasks`,
  `/api/tasks-overview`, `/api/spaces`; кеш за mtime `space.json` і маніфестів. ТОТАЛЬНА: не кидає
  ніколи, а нечитабельний `space.json` кладе в ключ `error` (опитування й списки не падають).

## Публікація

### Ядро

- Одна функція збірки `build_preview(task, tid, its, *, comments, gate_pw) -> {dir, frames,
  warnings}` на рівні модуля — і для зашитого шляху ЛІГА, і для модуля (жодної копії циклу).
  `comments=True` — як сьогодні (сніпет командних коментарів + `BUNDLES`); `comments=False` —
  без сніпета й без `BUNDLES`. `gate_pw=None` — без гейта (ні в обгортці, ні у внутрішніх
  сторінках).
- `_publish` лишається методом `Handler`, що вживає лише `self._current_task`, `send_error`,
  `_send_json`, `_overview_sync` (зовнішні заглушки на це розраховують); нові помічники —
  модульні функції.
- `POST /api/publish`:
  1. постачальник `legacy` → наявний шлях ЛІГА (через `build_preview(comments=True, gate_pw=…)`),
     поведінка й відповіді незмінні;
  2. постачальник — модуль → `build_preview(comments=False, gate_pw=<секрет password модуля
     або None>)`, потім (якщо не `build_only`) `provider.publish(ctx, build_dir, {id, title,
     dir})`; без `git_autocommit` пушу, `_registry_push`, `_overview_sync`. Порядок спостережуваний:
     400 «no iterations marked for publish» (код-less, текст ЛІГА) → 400 `bad-task-id` → `ctx` модуля
     (один раз, теку беремо З нього) → `folder_ok` (409 `bad-folder`, `error` = `path-*`) → пароль
     (порожній рядок = «пароля нема») → замки (409 `publish-busy`) → збірка → `publish` → перевірка,
     що модуль повернув саме `<тека>/<задача>` (інакше `module-error`, `publish_local` не пишемо);
  3. постачальника нема → 409 `no-publish-module`.
- **Замки.** Збірка й `publish` модуля йдуть під двома замками без очікування: (а) тека збірки задачі
  (`<задача>/publish/` стирається й пишеться незалежно від призначення), (б) призначення
  `(realpath(тека) у NFC+casefold, id задачі)` — тека однієї задачі може збігтися з текою іншого
  простору. Зайнятий будь-який → одразу 409 `publish-busy` (а не очікування: зависла мережева тека не
  нагромаджує потоки). Замок збірки є лише на модульному шляху: шлях ЛІГА не змінено.
- **Помилки публікації** (HTTP / `code`): 400 `bad-task-id`, 400 `bad-settings`, 400 без коду (нічого не
  позначено); 409 `no-publish-module`, `bad-folder`, `publish-busy`, `space-json-unreadable`,
  `secrets-unreadable`; 502 `module-error`. Успіх: `{ok, local: {path, url:
  '/published/<простір>/<задача>/'}, iterations, frames, …}`.
- Результат модуля → `iterations.json`: `publish_local = {"module": id, "path": …,
  "published_at": …}`. `publish_url` / `publish_verified` НЕ змінюються (вони для
  посилань, якими діляться, і їдуть у `.canvas-state.json`/дашборд).
- `/api/preview-password` і пункт `pubpw` — лише для `legacy`; для модуля пароль — його
  секрет. `preview_gate` у `/api/task` для модуля — `"module"` (без попередження «без гейта»).
  (Текст 409 `/api/preview-password` «публікація зʼявиться з модулями» застарів — UI його не показує.)

### `static-publish`

- `folder` за замовчуванням `{home}/deai-published/{space_id}` — ПОЗА текою простору (не
  їде в git разом із простором, не перетинається з id задач, пароль із гейта не опиняється в
  спільній теці).
- **Перевірка теки — при кожній публікації й кожній роздачі**, не лише при ввімкненні
  (`deai_modules.folder_ok`; ядро й модуль ділять одне правило, модуль перевіряє ще раз сам через
  `ctx['folder_ok']`): `spaces.check_new_path` над усіма просторами реєстру й теками всіх задач, плюс
  `path-deai-home`. Тека не може бути домівкою чи її предком, `DEAI_HOME` (дорівнювати, бути всередині
  чи над ним), текою інструмента, системною чи прихованою текою домівки (`~/Library`, `/Applications`,
  `/System`…), і не дорівнює, не всередині й не над текою простору чи задачі. Порівняння — за `realpath`,
  у NFC й за файловою системою (`samefile`: на macOS регістр не різнить теки, тож `~/library` — та сама
  `~/Library`; посилання `~/lnk -> /APPLICATIONS` не обхід). Реєстр чи файл задач якогось простору не
  читається — відмова (`spaces-unreadable`), а не «пускаємо». Відмова → 409 `bad-folder` (`error` = код
  `path-*`).
- **Ідентифікатор задачі** = імʼя теки: `[A-Za-z0-9_-]{1,128}` (ASCII, `fullmatch`) і не імʼя пристрою
  Windows (`CON`, `NUL`, `COM1`…). Інакше диспетчер відмовляє ДО збірки (400 `bad-task-id`); те саме
  правило — у модулі й у роздачі (паритет стережуть тести).
- `publish`: збірка → `<folder>/.tmp-<task-id>-<rand>/`, копія завершується маркером
  `.deai-published` (ознака завершеної копії); якщо `<folder>/<task-id>/` існує — він МУСИТЬ бути
  справжньою текою (не посиланням) із маркером (інакше `bad-folder`, нічого не видаляємо; на ФС без
  урахування регістру тека з іншим регістром імені — теж чужа); старе → `.old-<task-id>-<rand>`, нове →
  на місце, старе — `rmtree`. ПІСЛЯ перейменування перевіряється те, що саме перейменували: чужу, що
  стала на місце за цей проміжок, повертаємо назад і відмовляємо. Коротке вікно 404 між перейменуваннями
  — прийнятне. Збій посеред заміни: якщо `<task-id>/` нема, а є марковані `.old-*`, наступна публікація
  повертає НАЙНОВІШУ (за mtime маркера) на місце, перш ніж прибирати залишки `.tmp-*`/`.old-*` цієї
  задачі (чужі й немарковані не чіпаються). Прийнята поведінка: навмисно видалену людиною `<task-id>/`
  за наявності маркованого `.old-*` наступна публікація «воскресить» застарілою версією, а тоді замінить
  новою. Паралельні публікації однієї пари (тека, задача) серіалізує диспетчер (замки вище): сам
  модуль від них не безпечний.
- `password` — необовʼязковий секрет; порожній рядок = «пароля нема». Пароль вкладає в сторінки збірка
  (ядро), тож модуль його не читає, і в його помилках його не може бути. Гейт — клієнтський, пароль
  лежить у сторінках відкритим текстом.
- `check`: тека проходить правила вище; вона або її найближчий наявний предок — записувані; нічого не
  створює.

### Локальна роздача

- `GET /published/<space-id>/<task-id>/<rel>` у `Routed.do_GET` — ДО `_take_task` (простір бере URL, а не
  запит); `/published/` — у `HANDLED_PREFIXES`. Простір — з URL через `read_registry()` (не простір
  запиту); постачальник `publish` цього простору мусить бути `static-publish`; тека — `published_root`
  ЗАНОВО на кожен запит (не `publish_local.path`: налаштування могли змінити) і `folder_ok`. Теку
  віддаємо лише з маркером `.deai-published`. Будь-яка непройдена перевірка (і нечитабельні реєстр чи
  `space.json`) — один і той самий порожній 404 (постійне тіло, без шляху й причини).
- Сегменти: `<space-id>` — `SPACE_ID_RE`, `<task-id>` — те саме правило, що в диспетчері; кожен
  сегмент декодується суворо (`%ff`, `%c0%af`, `%00` — відмова), без крапки на початку, `/`, `\`, `:` і
  керівних символів.
- **Обхід теки.** На macOS і Linux (де є `open(dir_fd=)`, `O_NOFOLLOW`, `O_DIRECTORY` і шлях відкритого
  дескриптора — `F_GETPATH` чи `/proc/self/fd`): тека відкривається дескриптором, далі кожна складова —
  `openat` з `O_NOFOLLOW`; файл: `lstat` → `open` → `fstat` із тим самим `(dev, ino)`, звичайний файл,
  `st_nlink == 1` (жорсткі посилання відхиляються); шлях дескриптора теки мусить дорівнювати перевіреній
  теці (підміну предка посиланням ловимо), і `folder_ok` кличеться ще раз на відкритій теці; збій —
  404 (закрито по збою). Файл віддається потоком (шматками) з того самого дескриптора, з якого взято
  ETag і довжину. На Windows (а також macOS із Python < 3.9 і Linux без `/proc/self/fd`) діє слабший
  запасний шляховий спосіб (`realpath` усередині теки, без симлінків на шляху); який режим діє —
  друкується рядком старту сервера.
- ETag/MIME — тією ж логікою, що й `_send_iter_file`; текстові типи — з `charset=utf-8`. Тека без
  завершального `/` — 301 на `/…/`. `HEAD` не підтримується.
- **Пісочниця**: кожна відповідь `/published/…` (200, 304, 301, 404) несе `Content-Security-Policy:
  sandbox allow-scripts allow-forms allow-popups` (без `allow-same-origin` → Origin `null`, POST канваса
  відповідають 403), `X-Content-Type-Options: nosniff` і `Access-Control-Allow-Origin: *` (без нього в
  непрозорому origin не вантажаться ні модульні скрипти оболонки, ні `fetch`, ні шрифти — див. «Межі»).
  Гейт і оболонка превʼю працюють без сховища (`sessionStorage` в пісочниці кидає → гейт питає пароль
  щоразу, і на внутрішніх сторінках теж).
- Відкриття теки через `file://` не підтримується (модульні скрипти оболонки) — тека для
  хостингу; корене-абсолютні адреси ассетів у макеті під підшляхом `/published/…` не
  працюють (на хостингу в корені домену — працюють) — записано в «Межах».

## Токени

- `inspector_ds_arg` додає `&sp=<space-id>` (простір задачі сторінки) — лише на сторінках, які
  віддає канвас; опублікована збірка не змінюється (до `/api/ds-tokens` вона не дістанеться; у ній
  росте лише `shell/i18n.js` новими ключами). `inspector.js` питає `GET /api/ds-tokens?space=<id>` ОДИН
  раз за завантаження рамки, У ФОНІ (перший звіт не чекає), з клієнтським тайм-аутом 7 с (довшим за
  серверні 5 с, щоб почути `check-timeout`); коли токени надійшли — перемальовка. Запит іде через
  власний `fetch` сторінки макета (макет, що підміняє `fetch`, його бачить).
- Відповідь: `{"profile": "space:<id>", "tokens": {name: [values]}, "source": …}`, `{"profile": null}`
  або `{"profile": null, "error": <код>}` (помилка модуля: `check-timeout`, нечитабельний `space.json`,
  не та форма відповіді) — завжди 200 для відомого простору (невідомий — 404): інспектор працює й без
  токенів. `inspector-dom.js`: профіль `space:…` бере токени з відповіді; інші профілі (`?ds=united`
  тощо, простір ЛІГА) — як сьогодні зі статичного `ds-tokens.js` (статичний імпорт ЛИШАЄТЬСЯ). `dsInfo`
  для `space:…` показує `source` замість commit/figma; пакет тюнера несе `ds.source` для профілів
  `space:`.
- Порожній список значень токена (імʼя відоме, значення нема з чим звіряти) — «токен», а не
  «перевизначено».
- Нема постачальника → `{profile: null}` → `DS_NONE` (як сьогодні для невідомого профілю).

### `css-tokens`

- Налаштування `file` (`path`, обовʼязкове).
- Читання: лише звичайний файл (`S_ISREG`, перевірка на дескрипторі), ≤2 МіБ, обмежене читання; кеш за
  (шлях, mtime, розмір).
- **Що є токеном.** Декларація `--name: value`, чиє правило має суб'єктом (крайнім складеним
  селектором) хоча б одного селектора списку `html`, `:root` або атрибут `[data-*theme*…]` (теми
  Bootstrap `[data-bs-theme=dark]` теж). `[data-theme=dark] .card { --x }` задає змінну картці, а не
  темі, тож токеном не є, а `html.dark`, `:root[data-theme=dark]`, `.dark :root` — є. Голий клас
  (`.dark { … }`) НЕ береться навмисно: клас стоїть на будь-якому елементі, і токени змішалися б із
  локальними змінними компонентів. Декларації ПРЯМО в `@theme { … }` (Tailwind v4; також `@theme
  inline|static|default`) — токени; скидання `--x-*: initial` — ні.
- **Вкладеність.** Правила в будь-яких at-правилах (`@media`, `@layer`, `@supports`, `@container`,
  `@document`…) розгортаються й оцінюються за власним селектором (`@keyframes`/`@font-face` токенів не
  дають); декларації ПРЯМО в умовній групі — токени лише тоді, коли група вкладена в правило рівня
  кореня (CSS nesting); інші at-правила обходяться, але самі токенів не дають.
- **Значення.** Збираються СПИСКОМ на імʼя (теми, медіа), без повторів; коментарі прибираються,
  `!important` відкидається; `;`/`}` усередині лапок, `url(…)` і дужок значення не ріжуть.
  `var(--x)` розгортається, якщо `--x` визначено в ЦЬОМУ файлі (до 5 стрибків, без циклів; значення-
  список множиться на теми); не вдалось розгорнути хоча б одне значення токена (цикл, невизначена,
  надто глибоко, стелі) — список токена порожній (імʼя відоме, інспектор значення не звіряє). Стелі:
  64 комбінації в одному значенні, 1024 на токен, 20000 на весь файл (за першою появою імені; решта
  токенів із `var()` — `[]`). `@import` не відстежується.
- `check`: файл проходить правила читання, знайдено ≥1 токен (`detail`: «N tokens»).

## API

Усі `/api/module*` і `/api/ds-tokens` — у `_REGISTRY_ROUTES` (заголовок задачі й префікс
`/t/` на них не діють); простір — параметр `space` (query для GET, тіло для POST),
за замовчуванням — простір, зафіксований на вході; невідомий — 404 `unknown-space`. Усі POST — за
центральною перевіркою Origin (`do_POST`); CORS на цих маршрутах нема.

- `GET /api/modules?space=` → `{modules: [{id, name, version, api, roles, builtin, enabled, implicit,
  status: "ok"|"error"|"missing"|"unchecked", last_check?, settings: [{key, type, label, required,
  value?, set?, options?}], error?}]}`. Модулі НЕ виконуються (лише завантажуються й читається
  запамʼятований `check`). Секрет — лише `set: true|false`, а `set: null`, коли `secrets.json` не
  читається (статус модуля тоді `error`: `secrets-unreadable`). `missing` — увімкнений у `space.json`
  модуль, якого нема на цій машині (`builtin: false`). `required` — доповнення до ревізії 2.
- `POST /api/module-enable {space?, id, settings?, secrets?}` і `POST /api/module-settings` (ті самі
  поля) → валідація типів (`bad-settings` 400, `unknown-module` 404) → пре-перевірка (читання
  `space.json` без запису; для вмикання `role-taken` 409) → запис секретів → запис `space.json` →
  `check` → `{ok: true, module, check}`. **Вердикт `check` іде з HTTP 200**: `ok` = «запит оброблено»,
  `check.ok` = вердикт, бо стан уже записано (400/409/502 збрехали б, що нічого не змінилось). Вердиктом
  стають усі відмови `check`, крім `unknown-module` і `space-json-unreadable` (ті — HTTP-відмови):
  `{ok: false, error: <код>, detail}`. `bad-settings` має дві форми: 400 до запису (валідація) і
  вердикт `check` (обовʼязкове налаштування не задане).
- `POST /api/module-disable {space?, id}` — налаштування й секрети лишає; працює й для модуля, якого
  нема на машині (`module: null` у відповіді — вимкнений відсутній не показується).
- `POST /api/module-check {space?, id}` → `{ok: true, module, check}`.
- `GET /api/ds-tokens?space=` — див. «Токени».
- Коди й HTTP-статуси — `deai_modules.STATUS`: `bad-manifest` 500, `module-error` 502, `role-taken` 409,
  `unknown-module` 404, `bad-settings` 400, `space-json-unreadable` 409, `spaces-off` 409,
  `check-timeout` 504, `secrets-unreadable` 409, `unwritable` 500, `bad-folder` 409.
- Залишкова гонка (прийнята): паралельна правка між пре-перевіркою й локом чи недоступний для запису
  `space.json` після запису секрету лишають записаний секрет (сирітський секрет нешкідливий).

## Інтерфейс (мінімальний у 2а)

- Предикат публікації: `hasPublish = space.capabilities ? !!space.capabilities.publish :
  space.integrations !== false` (відповіді старої форми лишаються валідними).

- Нові рядки — `i18n.js` (uk + en). Керування модулями в UI — етап 3 (у 2а — API).

## Межі

Прийняті рішення власника (стан на 0.2.0):

1. **`Access-Control-Allow-Origin: *`** на кожній відповіді `/published/…` потрібен пісочниці (непрозорий
   origin: модульні скрипти оболонки, `fetch`, шрифти). Наслідок: БУДЬ-ЯКА вебсторінка, відкрита в тому ж
   браузері, може прочитати опубліковане превʼю, вгадавши `/published/<простір>/<задача>/` — разом із
   паролем гейта. Гейт клієнтський (як на превʼю Vercel у ЛІГА), пароль — не секрет.
2. **Пароль у локальному перегляді**: у пісочниці нема `sessionStorage`, тож внутрішні сторінки питають
   пароль знову (на справжньому хостингу — один раз).
3. **`file://` не підтримується**; корене-абсолютні адреси ассетів у макеті під підшляхом
   `/published/…` не працюють (у корені домену — працюють).
4. **Нема перевірки заголовка `Host`** на сервері канваса (DNS rebinding) — пізніший етап безпеки.
5. `/t/<id>/published/…` не обробляється.
6. `HEAD` на `/published` не підтримується.

Решта меж:

- Свої модулі з теки простору — етап 3 (довіра людини в діалозі «Підключень», хеш усієї теки,
  заборона симлінків, ключ довіри з `realpath` теки).
- Модулі виконуються в процесі сервера з повним доступом (у 2а — лише вбудовані).
- Секрети не шифруються (0600, як `~/.ssh`); на Windows права не виставляються; Keychain —
  пізніше. Пароль превʼю `static-publish` лежить у відкритому вигляді в зібраних сторінках
  (гейт — клієнтський, як і в ЛІГА) — тому тека за замовчуванням поза текою простору.
- Зашитий код ЛІГА лишається (до модулів ЛІГА).
- `var()` розгортається лише всередині того самого файла; `@import` не відстежується.
- На Windows (і macOS із Python < 3.9, Linux без `/proc/self/fd`) `/published` іде запасним шляховим
  способом — слабшим проти підміни файлів посиланнями; режим друкується при старті сервера.
- Відомі вади, не з 2а: живі `tests/live/canvas.test.mjs` K2 (нестабільний клік палітри) і
  `tests/live/inspector-ds.test.mjs` тести 2 і 4 (у репо продукту нема статичного знімка ДС `united`).
  Технічний борг: статичний фолбек `Handler.do_GET` кидає traceback на шляхах із `%00`; замок теки
  збірки є лише на модульному шляху (шлях ЛІГА не змінено); текст 409 `/api/preview-password`
  «публікація зʼявиться з модулями» застарів.

### Відхилення від ревізії 2 (стан на 0.2.0)

Що збудовано інакше (чи додатково) проти тексту ревізії 2:

- **Id задачі**: `[A-Za-z0-9_-]{1,128}` і не імʼя пристрою Windows (ревізія 2: `^[\w-]+$`/`NAME_RE`);
  диспетчер відмовляє 400 `bad-task-id` до збірки.
- **Маркер `.deai-published` потрібен і при роздачі** (ревізія 2: лише при заміні): налаштування `folder`
  може вказувати на теку з чужим вмістом, а CORS `*` дав би його читати.
- **`ctx` несе `folder_ok` і `ModuleError`** (ревізія 2: `{space, settings, secrets}`): модулі не
  імпортують ядро.
- **Замки диспетчера й 409 `publish-busy`** (ревізія 2 їх не мала): тека збірки задачі + призначення.
- **`Access-Control-Allow-Origin: *`** на кожній відповіді `/published/…` (ревізія 2 мовчала): потрібен
  пісочниці; наслідок — «Межі» п. 1.
- **Обхід теки дескрипторами** з `O_NOFOLLOW`, звіркою `(dev, ino)`, `st_nlink == 1`, шляхом дескриптора
  й повторною `folder_ok` (ревізія 2: «`realpath` усередині теки, без симлінків»), із слабшим запасним
  способом на Windows тощо; режим друкується при старті.
- **Роздача лише для `static-publish`**, постійний порожній 404, текстові типи з `charset=utf-8`, 301 для
  теки без `/`, потокова віддача, захисні заголовки і на 304/301/404.
- **API**: вердикт `check` іде з HTTP 200 (див. «API»); додатково `secrets-unreadable` 409 і
  `unwritable` 500; `set: null`, коли `secrets.json` не читається; `required` у записах налаштувань;
  `module-disable` працює для відсутнього модуля (`module: null`); дві форми `bad-settings`.
- **`capabilities`** — і в `/api/tasks-overview`; ТОТАЛЬНА (помилка в `capabilities.error`); обчислює
  `deai_modules.capabilities`, `serve.py` лише додає її до відповідей.
- **`css-tokens`**: токен — за суб'єктом селектора (ревізія 2: «список селекторів містить»), додано
  `@theme` Tailwind v4 і теми Bootstrap `[data-bs-theme]`; голий клас не береться; умовні групи — лише
  коли вкладені в правило рівня кореня; стелі розгортання `var()` (64/1024/20000).
- **Інспектор**: токени простору приходять У ФОНІ з клієнтським тайм-аутом 7 с (ревізія 2: `await` на
  верхньому рівні ДО першого звіту); відповідь `{profile: null, error}` при збої модуля; `ds.source` у
  пакеті тюнера; запит іде через власний `fetch` сторінки макета.
- **UI**: «Скопіювати посилання» для модуля — абсолютна адреса канваса без `#k=` (ревізія 2: «локальний
  шлях/адресу з підписом «локально»»); стале повідомлення «Опубліковано локально» з «Відкрити».
- **Відновлення `static-publish`**: `.old-*` за mtime маркера, перевірка після перейменування, правила
  для регістру імен (ревізія 2 описувала лише `.tmp-*`/`.old-*` із маркером).
- **Свої модулі** і довіра до них — етап 3, як у ревізії 2; у `GET /api/modules` усі записи `builtin: true`,
  окрім `missing`.
