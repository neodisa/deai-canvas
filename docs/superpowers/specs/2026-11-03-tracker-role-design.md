# Етап 4c-2: статуси трекера як роль `tracker` і модуль `jira-tracker` (0.13.0)

Дата: 03.11.2026. Попередній етап — 4c-1 (0.12.0, командний дашборд). Дорожня карта — `docs/design/spaces-and-modules.md`.

## Рішення власника

- **26.10.2026 (етап 4):** чисте ядро + паритет; усе, що робить простір ЛІГА, стає модулем.
- **02.11.2026:** модулі 4c — вбудовані й загальні, специфіка ЛІГИ — у конфігу й адаптері ядра. 4c-1 дашборд (0.12.0) →
  **4c-2 трекер `jira-tracker` (ця спека, 0.13.0)** → 4c-3 тиша Teams через роль `notify` (0.14.0).
- **03.11.2026:** статуси трекера — **і на екрані «Задачі», і в дашборді**: екран сам питає трекер про задачі цієї машини,
  тож простір із трекером, але без дашборда, теж бачить статуси. Підхід — роль з однією функцією «статуси за ключами»;
  кеш і підмішування — у ядрі. Повна задача (назва, виконавець) — ні: зайве й ризик PII в дашборді.

## Проблема

Статуси Jira — зашитий шлях ЛІГИ, паралельний модулям:

- їх тягне лише синк дашборда: колбек `statuses=jira_statuses` у `bin/overview_push.py` (`_JIRA_BASE` — константа в коді,
  облікові — `JIRA_EMAIL`/`JIRA_TOKEN` з оточення або файли `~/.claude/pipeline-feedback/jira-email|jira-token`),
  `POST <base>/rest/api/3/search/jql`, будь-який збій → `{}`;
- екран «Задачі» бачить статус своєї задачі ЛИШЕ з рядка дашборда (`tasks_overview`: `jiraStatus`/`jiraCat` з
  `jira_status`/`jira_status_cat`): нема дашборда — нема статусів, навіть коли трекер є;
- звичайний простір трекера не має взагалі: роль `tracker` лише зарезервована (`ROLES_RESERVED`).

## Мета

1. Роль `tracker` у ядрі: ядро кличе модуль за статусами задач за їхніми ключами.
2. Вбудований модуль **`jira-tracker`** (Jira Cloud): будь-хто зі своїм сайтом Jira отримує статуси задач.
3. ЛІГА — через той самий модуль як **неявний постачальник** (зразок 4b/4c-1): `ctx` будує ядро з конфігу установки.
   Адреса Jira переїжджає з константи коду в `tasks.json` (`jira_base`), як адреса Supabase у 4b-2.
4. Два споживачі статусів у ядрі: синк дашборда (статуси на картках) і екран «Задачі» (статуси своїх задач напряму).
5. Паритет ЛІГИ: той самий запит у Jira, ті самі картки в дашборді. Свідомі відмінності — нижче.

## Не мета

- Тиша Teams — 4c-3. Прапорець `integrations`, літерал `'legacy'`, ключ `profile` в API — 4d.
- Перейменування поля задачі `jira` (ключ задачі в трекері) — 4d разом з API; у 4c-2 поле лишається `jira`, а відповіді —
  `jiraStatus`/`jiraCat`.
- Jira Server / Data Center (особистий токен `Bearer`), Linear та інші трекери — свої модулі пізніше; контракт ролі їх
  дозволяє.
- Посилання з ключа задачі на сторінку задачі в трекері, назва чи виконавець задачі з трекера.
- Статуси на рядках вкладки «Команда» — як і були, лише з дашборда.

## Дизайн

### 1. Роль `tracker`

- `ROLES_CALLED` += `'tracker'`, з `ROLES_RESERVED` прибирається (лишається `notify`).
- Обовʼязкові функції `server.py`: `check(ctx)` (як в усіх ролей) і `statuses(ctx, keys)`.
  - `keys` — список рядків-ключів (до `TRACKER_BATCH = 100`, без повторів). Ядро шле лише ключі за
    `KEY_RE = [A-Z][A-Z0-9_]{0,31}-[1-9][0-9]{0,9}` (форма і Jira, і Linear); решту відкидає ДО виклику: сміття з ручної
    правки `tasks.json` не потрапляє в JQL.
  - Повертає `{ключ: {'name': str, 'cat': str|None}}`. Ядро нормалізує (`tracker.normalize`): лише запитані ключі; `name` —
    непорожній рядок, обрізаний до 80 знаків, без керівних символів, інакше запис відкидається; `cat` ∈ `new` |
    `indeterminate` | `done` (категорії статусу Jira), інше → `None`. Не словник → `ValueError`.
  - Задачі, якої трекер не знає, у відповіді просто нема (не помилка).
- `LEGACY_ROLES` += `'tracker'`; `STRICT_LEGACY_ROLES` += `'tracker'` (зламаний `space.json` — не `'legacy'`: зашитий шлях —
  сайт Jira ЛІГИ); у `LEGACY_ON_ERROR_ROLES` — НІ.
- `capabilities.tracker` — id модуля / `'legacy'` / `null`.
- Коди помилок у `STATUS`: `tracker-unconfigured` 409 (ЛІГА без адреси чи облікових Jira), `tracker-error` 502.
- Тайм-аути: ядро кладе в `ctx['timeout_s']` бюджет сокета для модуля і чекає довше за нього (щоб показати текст модуля, а не
  `check-timeout`): екран — сокет 4 с, ядро чекає `TRACKER_READ_TIMEOUT = 6` с на виклик; синк — сокет 15 с (як у 0.12.0),
  ядро чекає `TRACKER_SYNC_TIMEOUT = 30` с на пакет. `ctx['timeout_s']` — нове загальне поле контракту ролі `tracker`.
- Нове ядро `app/tracker.py` (БЕЗ імпорту `serve`, як `app/dashboard.py`): `KEY_RE`, `keys_of(tasks)` (унікальні валідні
  ключі задач у порядку файла), `normalize(data, keys)`, `statuses(module, ctx, keys, timeout)` (пакетами по 100, збір
  відповідей; збій пакета → `ModuleError` вгору), `legacy_ctx(...)`, `legacy_module()`.

### 2. Модуль `jira-tracker` (вбудований, 1.0.0)

- Налаштування: `base` (text, обовʼязкове: адреса сайту Jira Cloud `https://<сайт>.atlassian.net` чи власний домен —
  лише https, DNS-імʼя щонайменше з двох міток, не IP і не localhost, без шляху, параметрів і облікових даних; ті самі
  правила, що `_host_ok` модулів Supabase), `email` (text, обовʼязкове, ≤ 254 знаки, з `@`), `token` (secret, **НЕ**
  `public`, обовʼязкове: API-токен Atlassian; живе в `~/.deai/secrets.json`).
- `statuses(ctx, keys)`: `POST <base>/rest/api/3/search/jql`, тіло `{"jql": "key in (K1,K2,…)", "fields": ["status"],
  "maxResults": 100}`, заголовки `Authorization: Basic base64(email:token)`, `Accept`/`Content-Type: application/json`;
  тайм-аут сокета — `ctx['timeout_s']` (бюджет, який дає ядро: 4 с для екрана, 15 с для синку — як було в 0.12.0; не число
  чи поза 1…30 → 4 с). Відповідь: `issues[].key` → `{'name': fields.status.name, 'cat':
  fields.status.statusCategory.key}`.
- `check(ctx)`: `GET <base>/rest/api/3/myself` → 200 — «підключено»; 401/403 — «невірний email чи токен» (код
  `module-error`); інше — текст зі статусом HTTP.
- Помилки: фіксовані слова + HTTP-статус, ≤ 200 знаків; ⛔ ні токена, ні email, ні тіл запиту й відповіді в текстах
  (повідомлення Jira може повторити ключі й назви). Значення токена вичищається ще раз (`_clean`).
- Без переходів за редиректами (`_NoRedirect`: заголовок `Authorization` не піде на чужий хост); TLS — certifi, якщо є.
  Шов мережі — `_open(req, timeout)`. Хелпери адреси й TLS ПРОДУБЛЬОВАНО з модулів Supabase (модулі не знають один про
  одного). Лише stdlib.
- `ctx['legacy']` модуль не читає: поведінка для ЛІГИ та сама (прапорець лишається в `ctx` для однорідності з 4c-1).

### 3. Адаптер ЛІГИ (неявний постачальник)

- `install_config.jira_config()` → `(base, email, token)` або `(None, None, None)`:
  - `base` — корінь старого `tasks.json`, ключ `jira_base` (повністю `https://<хост>[:порт][/]`, без `/` у результаті;
    той самий файл, що несе `supabase_url`); інше чи нема → конфігу нема;
  - `email`/`token` — як зараз: `JIRA_EMAIL`/`JIRA_TOKEN` з оточення, інакше файли
    `~/.claude/pipeline-feedback/jira-email|jira-token` (вміст `strip()`); обидва непорожні, друковний ASCII без пробілів
    для токена — інакше конфігу нема.
  - Значень — ні в текстах, ні в журналах; кешу нема.
- `tracker.legacy_ctx(base, email, token, space_id='')` — `{'space': …, 'settings': {'base', 'email'}, 'secrets': {'token'},
  'ModuleError': …, 'legacy': True}`; `base is None` → `ModuleError('tracker-unconfigured', message='Jira не налаштовано:
  додайте jira_base у tasks.json і облікові JIRA_EMAIL/JIRA_TOKEN')`. ⛔ НЕ `module_ctx()` (той самий урок, що 4c-1).
- Модуль — вбудований `jira-tracker` з каталогу (`tracker.legacy_module()`).
- ⛔ Ізоляція (закон 03.08.2026): `DC_TASKS_FILE` чи `DC_NO_OVERVIEW` → шлях ЛІГИ не ходить у Jira (екран: статусів нема,
  `tracker.error` — текст ізоляції). Шов для тестів — `DC_TRACKER_FAKE` (локальний JSON `{ключ: {name, cat}}` замість
  Jira, лише для шляху ЛІГИ, як `DC_TEAM_FAKE`). Синк ЛІГИ в ізоляції й так не стартує (4c-1).
- `bin/overview_push.py`: `_JIRA_BASE`, `_jira_creds`, `jira_statuses`, `_ssl_context` зникають; колбек `statuses` для
  `dashboard.sync` будує CLI з постачальника ролі `tracker` того самого простору (§4).

### 4. Синк дашборда

- `dashboard.sync(…, statuses=…)` — сигнатура та сама (колбек `keys → {ключ: {name, cat}}`), але колбек тепер є в
  **будь-якого** простору з постачальником `tracker`: CLI (`overview_push.py sync`) вирішує `deai_modules.provider('tracker',
  простір)` і передає `lambda keys: tracker.statuses(module, ctx, keys, TRACKER_SYNC_TIMEOUT)`; ЛІГА — `legacy_module()` +
  `legacy_ctx(*jira_config())`. Нема постачальника чи нема конфігу ЛІГИ → `statuses=None` (крок пропущено, як у звичайного
  простору в 0.12.0).
- Збій трекера в синку → `{}` (наявні статуси на картках НЕ затираються — `build_card` не шле `None`), і ⛔ НЕ мовчки: рядок
  у лог синку `⚠ overview: статуси трекера недоступні: <текст>` (до 4c-2 збій Jira мовчав).

### 5. Екран «Задачі»

- `/api/tasks-overview` кличе `tracker_snapshot(keys)` для ключів задач «Моїх» (`tracker.keys_of`, перші 100 — один
  виклик) — постачальник ролі `tracker` простору запиту (`tracker_resolve()`, як `team_resolve()`).
- Кеш на простір: `_TRACKER_CACHE {space_id: {'at', 'statuses', 'error', 'okAt', 'who', 'keys'}}` під ОКРЕМИМ
  `_TRACKER_LOCK` (не `_TEAM_LOCK`: мертвий Jira не тримає рядки команди). `TRACKER_TTL = 300` с, помилка —
  `TRACKER_ERR_TTL = 30` с; інший постачальник (`who`) чи новий ключ, якого нема в `keys` кешу, → новий запит; `?refresh=1`
  (кнопка «Спробувати ще») оминає й цей кеш. ⛔ Збій НЕ стирає останні статуси: оновлюються лише `error` і `at`.
- Пріоритет для `mine[].jiraStatus`/`jiraCat`: статус від трекера (кеш) → рядок дашборда → `None` («невідомо», бейджа нема).
- Відповідь отримує `tracker: {'error': str|None, 'okAt': епоха|None} | null` (`null` — у простору нема трекера).
- Клієнт (`app/tasks-home.js`): коли `tracker.error` — тиха строка над «Моїми» тим самим стилем, що «дані на …» вкладки
  «Команда»: «Трекер недоступний — статуси на ГГ:ХХ» (`okAt` є) або «Трекер недоступний: <текст>» (успіху ще не було).
  Текст — через `esc()`, словник UK/EN. Ізоляція (текст ізоляції) строки не показує: це не збій для людини.
- Рядки вкладки «Команда» — без змін (статуси з дашборда).

### 6. «Підключення» й майстер

- Роль `tracker` у `ROLE_ORDER` (між `dashboard` і `tokens`), `ROLE_ICONS` (іконка з наявного набору), `LEGACY_ROLES` клієнта;
  `BUILTIN_TEXT["jira-tracker"]` з підказками полів `base`/`email`/`token`; i18n UK/EN: «Трекер задач» / "Issue tracker",
  опис, рядок «Зараз: …», `disableConsequences` — «статуси задач зникнуть з екрана «Задачі» й перестануть оновлюватись у
  дашборді». Майстер нового простору показує роль серед інших.
- Тести, що приколюють `roleKeys("tracker") == null` чи «tracker зарезервований», оновлюються (тепер — `notify`).

## Паритет і перевірки

- **Знімок 0.12.0 ДО змін** (`tests/fixtures/tracker/before-4c2.json`): (а) запит `jira_statuses` на заглушці мережі (метод,
  шлях, тіло, заголовки — `Authorization` лише як «є/нема», без значення) і його розбір; (б) картки `overview_push.py sync`
  ЛІГИ з заглушками Jira, реєстру й коментарів; (в) `/api/tasks-overview` ЛІГИ на `DC_TEAM_FAKE` (`mine` зі статусами з
  дашборда).
- Диференційні після змін: запит модуля = запит знімка (крім адреси: тепер з `jira_base`); ті самі картки; `mine` без
  трекера (ізоляція) — як у знімку.
- Модуль: правила адреси; `check` 200/401/403/мережа; `statuses` — розбір, порожні `issues`, сміття у відповіді; тексти
  помилок без токена й email; без редиректів.
- Ядро: `KEY_RE` відкидає сміття до виклику; `normalize` (лише запитані ключі, обрізання, `cat` поза набором → `None`);
  пакети по 100; пріоритет трекер → дашборд → `None`; кеш на простір, окремий замок, збій не стирає, новий ключ → запит.
- Мутації: ізоляція `DC_TASKS_FILE`/`DC_NO_OVERVIEW` для трекера ЛІГИ; `'tracker'` у `LEGACY_ON_ERROR_ROLES`; фільтр
  `KEY_RE`; кеш без ключа простору; збій стирає статуси; синк мовчить про збій трекера; токен у тексті помилки.
- Живі: «Задачі» у звичайному просторі з фейковим модулем трекера без дашборда (бейджі статусів є; збій → строка
  «Трекер недоступний…»; без модуля — бейджів нема); «Підключення» — картка ролі. Наявні живі — зелені.
- Мережі в тестах нема; справжньої Jira — нема.

## Свідомі відмінності від 0.12.0

- Адреса Jira ЛІГИ — з `tasks.json` (`jira_base`), а не з коду: **без цього ключа ЛІГА статусів не отримує** (нотатка до
  оновлення).
- Екран «Задачі» ЛІГИ питає Jira напряму (раз на 5 хв на машину, ≤ 6 с очікування при промаху кешу); статус своєї задачі
  свіжіший за дашборд (до 30 хв запізнення раніше).
- Збій Jira в синку — рядок у лозі, а не тиша.
- Ключі задач поза `KEY_RE` у Jira не йдуть (раніше йшли в JQL як є).

## Відомі обмеження

- Один невідомий трекеру ключ у пакеті (Jira відповідає 400 на весь JQL) — увесь пакет без статусів і помилка (як у 0.12.0
  — тоді мовчки). Обхід — виправити ключ задачі.
- Лише Jira Cloud (Basic email:token); Server/DC — пізніше.
- Екран бере лише перші 100 ключів «Моїх».
- Промах кешу трекера додає до 6 с першому входу на екран (послідовно з рядками команди).
