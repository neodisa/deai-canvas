# Етап 4d-1: напрямки простору (`tracks`) замість профілю задачі (0.15.0)

Дата: 04.11.2026. Попередній етап — 4c-3 (0.14.0, сповіщення Teams). Дорожня карта — `docs/design/spaces-and-modules.md`.

## Рішення власника

- **26.10.2026 (етап 4):** чисте ядро + паритет; усе, що робить простір ЛІГА, стає загальним механізмом або модулем.
- **04.11.2026:** етап 4d — чотири підрелізи: **4d-1 профіль → напрямки (ця спека, 0.15.0)** → 4d-2 шов «шар вимкнено» й
  ізоляція спільного стану без літерала `'legacy'` (0.16.0) → 4d-3 явні модулі ЛІГИ з **автоматичною міграцією конфігу з
  бекапом** (0.17.0) → 4d-4 прапорець `integrations` і старі псевдоніми геть (0.18.0).
- **04.11.2026:** профіль задачі замінюють **«напрямки» простору** — загальна можливість будь-якого простору; ЛІГА лишається
  ОДНИМ простором із трьома напрямками; старий ключ `profile` в API приймається як синонім до 4d-4.

## Проблема

Профіль задачі (`profile` у записі `tasks.json`: `united` / `liga360` / `seo`) — поняття лише ЛІГИ, вшите в ядро. Він
визначає чотири речі:

1. **Теку задачі** — `work_root(cfg, profile)` (`app/serve.py`): `design_work_roots[profile]` → `design_work_root` →
   `~/deai-work` з кореня старого `tasks.json`.
2. **Репозиторій макетів** — `profile_repos()` (ключ `profile_repos` кореня `tasks.json`): нова задача дістає
   `gitlab: {repo, path: mockup/<id>}` і бутстрапиться з репо.
3. **ДС інспектора** — `inspector_ds_arg(profile, sp)`: `?ds=<profile>` у розмітці макета; вендорний інспектор знає статичні
   ДС `united` / `liga360`, на `seo` чесно каже «ДС нема».
4. **Мітку задачі** — `task_tags`: задача без `tags` показує похідну мітку з `_LEGACY_PROFILE_TAGS`
   (`united → United`, `liga360 → LIGA360`, `seo → SEO`, невідомий — як є).

Плюс: маршрут `task-new` у просторі з `integrations` ставить `profile or 'united'`, без інтеграцій — `None`; `/api/tasks`,
`/api/task` віддають `profile`; реєстр задач (`bin/registry.py`, `SHARED`) возить `profile` між машинами; `bin/roots.py` і
`bin/state.py` читають його. Звичайний простір такого механізму не має взагалі: тека задачі — завжди шлях простору, репо —
лише явний `vcs` у тілі `task-new`, ДС — лише токени простору.

## Мета

1. **Напрямки простору** — загальний механізм: простір описує свої напрямки (тека, репо, ДС, назва), задача несе `track`.
2. Ядро більше не знає імен `united` / `liga360` / `seo` і не має `_LEGACY_PROFILE_TAGS`, `profile='united'`, `profile_repos()`
   як частини ядра, `work_root(cfg, profile)`.
3. ЛІГА — без жодної зміни для дизайнерів: її напрямки дає неявний адаптер із того, що вже лежить у корені `tasks.json`; ті
   самі теки, репо, мітки, `?ds=` у розмітці байт-у-байт.
4. Перехідна сумісність: старі клієнти (скіл пайплайну шле `profile`) і машини колег на 0.14.0 (спільний реєстр) не ламаються.

## Не мета

- Перенесення напрямків ЛІГИ в `space.json` — це автоміграція 4d-3 (разом з модулями, одна міграція й один бекап).
- Вибір напрямку в діалозі «Нова задача» і редактор напрямків у «Підключеннях» — не в 4d-1 (сьогодні профіль теж задає лише
  скіл пайплайну через API; напрямки звичайного простору правляться в `space.json` руками, як описано в README).
- Прибирання ключа `profile` з API й записів задач — 4d-4. Вендорні статичні ДС інспектора (`united` / `liga360`) не
  чіпаються: напрямок лише називає їх.
- Прапорець `integrations`, літерал `'legacy'`, псевдоніми `gitlab_*` — 4d-2…4d-4.

## Дизайн

### 1. Опис напрямків у `space.json`

```json
{
  "name": "Студія",
  "tracks": [
    {"id": "web",    "label": "Web",    "root": "~/work/web", "repo": "git@example.com:studio/web.git", "ds": ""},
    {"id": "mobile", "label": "Mobile", "root": "mobile",     "repo": "",                                "ds": ""}
  ],
  "default_track": "web"
}
```

- `id` — `[a-z0-9-]{1,32}` (той самий шаблон, що `_PROFILE_KEY`); унікальний у просторі; обовʼязковий.
- `label` — підпис і похідна мітка задачі; правила мітки (`_read_tag`: 1…32 знаки без коми й керівних); нема чи поганий — `id`.
- `root` — тека задач напрямку. Абсолютний, `~/…` або відносний до шляху простору; системні теки (`spaces.SYSTEM_DIRS`)
  відкидаються. Нема чи порожній — шлях простору.
- `repo` — репозиторій макетів за замовчуванням для нової задачі (той самий `_REPO_OK`, що для `profile_repos`). Нема — без
  типового репо.
- `ds` — імʼя статичної ДС інспектора (`[a-z0-9-]{1,32}`). Порожньо — статичної нема, інспектор бере токени простору (як зараз).
- `default_track` — id напрямку для задачі без `track`; нема чи не з переліку — перший напрямок; нема напрямків — `None`.
- Не більше 20 напрямків. Читання НЕ кидає: поганий запис (не словник, поганий `id`, дубль `id`) мовчки відкидається, решта
  працює; поганий `root` / `repo` / `ds` — поле вважається відсутнім. Значення шляхів і репо не потрапляють у тексти помилок.

Новий модуль ядра **`app/tracks.py`** (чистий, без мережі):

```python
MAX_TRACKS = 20
def normalize(raw, space_path) -> list[dict]    # [{id, label, root, repo, ds}] — root уже розгорнутий в абсолютний шлях
def default_id(tracks, raw_default) -> str|None
def of_task(task) -> str|None                   # task['track'], інакше task['profile'] (перехід до 4d-4); лише за шаблоном id
def find(tracks, tid) -> dict|None
def label_tag(tracks, task) -> str|None         # похідна мітка: label знайденого напрямку; невідомий id — сам id (як сьогодні)
```

### 2. Звідки беруться напрямки простору

`serve.space_tracks(sp) -> (tracks, default_id)`:

- **Звичайний простір:** `tracks` / `default_track` з `space.json` простору (`tracks.normalize`).
- **Простір ЛІГИ (`integrations`) без ключа `tracks` у `space.json`:** неявний адаптер `tracks.legacy_tracks(cfg)` з кореня
  старого `tasks.json` — рівно те, що робили `work_root` і `profile_repos()`:
  - перелік id — `united`, `liga360`, `seo` плюс ключі `design_work_roots` і `profile_repos` (у такому порядку, без дублів);
  - `root` — `design_work_roots[id]` → `design_work_root` → `~/deai-work`;
  - `repo` — `profile_repos[id]` (ті самі перевірки) або порожньо;
  - `label` — таблиця адаптера `{'united': 'United', 'liga360': 'LIGA360', 'seo': 'SEO'}` (переїжджає з
    `_LEGACY_PROFILE_TAGS` у `tracks.py` під іменем `_LEGACY_LABELS`, піде в 4d-3, коли міграція запише назви в `space.json`),
    інакше `id`;
  - `ds` — `id` (сьогодні `?ds=<profile>` для будь-якого профілю за шаблоном; вендорний інспектор сам каже «ДС нема» для
    невідомого);
  - `default_track` — `united`.
  - Простір ЛІГИ, у чиєму `space.json` УЖЕ є `tracks`, — бере їх (так 4d-3 перемкне ЛІГУ записом у `space.json`, без коду).
- **Шар вимкнено (неявний простір, лише `DC_TASKS_FILE`):** як ЛІГА (адаптер із того самого файла) — паритет тестів до 4d-2.

### 3. Що читає напрямок

- **Тека нової задачі:** `track_root(sp, track_id)` — `root` знайденого напрямку; напрямку нема — `root` напрямку за
  замовчуванням; напрямків нема — шлях простору (звичайний) / `design_work_root` → `~/deai-work` (ЛІГА, як `work_root(cfg, None)`
  сьогодні).
- **Репо нової задачі:**
  - ЛІГА: як сьогодні — `gitlab: {repo, path: mockup/<id>}`, коли `gitlab` нема в тілі й у напрямку є `repo`.
  - Звичайний простір із постачальником ролі `vcs`: коли в тілі нема `vcs`, а в напрямку є `repo` — задача дістає
    `vcs: {repo}` (далі все як із явним `vcs`: `validate`, бутстрап, запис у задачу). Без постачальника `vcs` — репо напрямку
    мовчки не застосовується (явний `vcs` у тілі без ролі й далі 409, як зараз).
- **ДС інспектора:** `inspector_ds_arg(ds, sp)` отримує вже `ds` напрямку задачі (не профіль). ЛІГА: `ds = id`, тож
  `?ds=united` тощо байт-у-байт; звичайний простір без `ds` — лише `?sp=<id>` (як зараз).
- **Мітка:** `task_tags` — ключ `tags` є: лише вони (без змін); нема — `tracks.label_tag` напрямку задачі. Для ЛІГИ через
  адаптер — ті самі `United` / `LIGA360` / `SEO` / невідомий як є.

### 4. Запис задачі й API

- `task_new(cfg, tid, …, track=None, root=…, repo=…)`: у запис задачі лягає **`track`**; у просторі ЛІГИ — **ще й
  `profile` з тим самим значенням** (машини колег на 0.14.0 читають `profile` зі спільного реєстру; без нього їхня тека, репо
  й мітка зламались би). `profile=None` / `track=None` у записі не пишуться (сьогодні звичайний простір пише `profile: null` —
  це лишається як є для `profile`, щоб не міняти формат записів звичайних просторів у 4d-1; `track` пишеться лише коли є).
- **`POST /api/task-new`:** нове поле `track` (рядок за шаблоном id чи `null`); `profile` — синонім (обидва з різними
  значеннями — 400 `bad-track`; не рядок — 400 `bad-track`, `bad-profile` лишається для поля `profile`, як було).
  Невідомий у просторі id — 400 `unknown-track` (для ЛІГИ — лише id за шаблоном, як сьогодні: невідомий профіль дозволений).
  Нема поля — `default_track` простору (ЛІГА: `united`, як `profile or 'united'`; звичайний простір без напрямків — `None`).
- **`GET /api/tasks`, `GET /api/task`:** нове поле `track` (`tracks.of_task`); `profile` лишається в відповіді (як було).
- **`GET /api/spaces`** (опис простору): нове поле `tracks: [{id, label}]` і `default_track` — без `root` / `repo` (шляхи й
  адреси не їдуть у браузер).
- `bin/registry.py`: `SHARED` + `track`; `_work_root` — через `tracks` (той самий адаптер). `bin/roots.py`, `bin/state.py` —
  `tracks.of_task` замість `t.get('profile')`, тексти — «напрямок».

### 5. Що прибирається з ядра

`_LEGACY_PROFILE_TAGS` (→ `tracks._LEGACY_LABELS`, адаптер), `profile='united'` у сигнатурі й маршруті, `profile_repos()` і
`work_root(cfg, profile)` як функції ядра (їхня логіка — у `tracks.legacy_tracks`; імена в `serve` лишаються тонкими
обгортками, лише якщо на них тримаються наявні тести, — кожна з причиною в звіті), `_PROFILE_KEY` (→ `tracks.ID_RE`). Уроки
(⛔) прибраного коду переносяться в нові місця.

### 6. Уточнення після знімка 0.14.0 (04.11.2026, Task 1) — мають перевагу над §1–§4 для простору ЛІГИ

Знімок `tests/fixtures/tracks/before-4d1.json` показав, що 0.14.0 поводиться інакше, ніж §3–§4 описують для ЛІГИ. Паритет —
понад усе, тож для ЛІГИ (адаптер `legacy_tracks`, шар вимкнено теж) діють такі правила:

1. **Тека напрямку без власного кореня — спільний корінь, НЕ корінь дефолтного.** Адаптер дає ще й `fallback_root`
   (`design_work_root` → `~/deai-work`). `track_root` для ЛІГИ: id з власним `design_work_roots[id]` → він; будь-який інший id
   (зокрема `liga360` без кореня, невідомий, `United` з великої, `None`) → `fallback_root`. Правило «нема напрямку → корінь
   дефолтного» з §3 стосується лише звичайних просторів.
2. **Значення напрямку ЛІГИ не звіряються з `ID_RE`.** Як у 0.14.0: будь-який рядок `profile`/`track` приймається й лягає в
   запис як є (`'United'` — так само); невідомий — `fallback_root`, без репо; `?ds=` — лише якщо значення після `strip()`
   проходить `[a-z0-9-]{1,32}` (як `inspector_ds_arg` сьогодні, включно з `?ds=zzz` для невідомого); мітка — `_LEGACY_LABELS`
   або саме значення через правила мітки (`_read_tag`). Тому `tracks.of_task` повертає збережений РЯДОК (`track`, інакше
   `profile`; не рядок чи порожній — `None`), а перевірка `ID_RE` — справа місця, що читає (звичайний простір і `?ds=`).
   `bad-track` для ЛІГИ — лише не рядок (і конфлікт `track`/`profile`); `unknown-track` для ЛІГИ не буває.
3. **Дефолт маршруту:** `profile`/`track` відсутній, `null` або `''` → `default_track` (ЛІГА: `united`), як `profile or
   'united'`. Прямий виклик `task_new(..., track=None)` лишає `None` (дефолт ставить маршрут).
4. **`design_work_roots` не словник** у 0.14.0 давав `AttributeError` (500). Адаптер читає його як `{}` — свідома відмінність
   (не обвал, а спільний корінь).
5. **`/api/task`** не має `?id=`: задачу вибирає заголовок `X-Canvas-Task` (або `current`) — тести й план звертаються так само.
6. `tags: []` у тілі `task-new` не зберігається (похідна мітка повертається) — поведінка 0.14.0 не змінюється.
7. **Старий ключ `profile` у ЗВИЧАЙНОМУ просторі ніколи не падає там, де 0.14.0 його приймав** (ревʼю Task 4: скіл пайплайну
   шле `"profile": "united"`). `profile`: не рядок — 400 `bad-profile` (як було); рядок за `ID_RE`, що є напрямком простору, —
   стає напрямком; будь-який інший рядок (нема напрямків, невідомий id, `'United'`) — **ігнорується**, як у 0.14.0 (задача йде в
   дефолтний напрямок або, без напрямків, у шлях простору з `profile: null`). Суворим (`bad-track` / `unknown-track`) є лише
   новий ключ `track`. Конфлікт `track` ≠ `profile` — 400 `bad-track` лише коли `profile` справді був би використаний.

## Свідомі відмінності від 0.14.0

1. Записи нових задач дістають `track` (у ЛІГИ — поряд із `profile`).
2. `/api/tasks`, `/api/task`, опис простору дістають `track` / `tracks` / `default_track`.
3. Нові коди `bad-track` (400) і `unknown-track` (400, лише звичайні простори з явними напрямками).
5. ЛІГА: `design_work_roots` не словник — спільний корінь замість 500 (§6.4).
6. ЛІГА: власний корінь напрямку чи `design_work_root` не рядок — фолбек (спільний корінь / `~/deai-work`) замість `TypeError`.
4. Звичайний простір із напрямками: тека задачі — `root` напрямку, а не шлях простору; репо напрямку стає `vcs` задачі.

## Відомі обмеження

- Напрямки звичайного простору правляться лише в `space.json` (нема UI); задачу в напрямок кладе лише API (скіл пайплайну).
- Ключ `profile` живе в записах і API до 4d-4; задачі, створені до 0.15.0, мають лише `profile` — читання бере його.
- Назви `United` / `LIGA360` / `SEO` і дефолт `united` поки живуть в адаптері `tracks.py` — до міграції 4d-3.

## Implementation notes (відхилення, прийняті на ревʼю)

Де код відрізняється від тексту вище — правда за кодом; тут усе, що розійшлося з первинним задумом:

- **`root` перевіряється правилом шляху простору, а не лише `SYSTEM_DIRS`** (§1): `tracks.normalize` кличе `spaces.check_new_path` з
  порожнім реєстром — системні теки й підтеки (за текстом і `realpath`), надто широкий корінь (домівка чи її предок), приховані теки
  й `Library` у домівці, тека інструмента, файл замість теки; довший за `ROOT_MAX` = 1024 знаків чи з керівним знаком — відсутній.
  Відносний `../..` нормалізується ДО перевірки. Перетин з ІНШИМ простором реєстру (збіг чи вкладеність) ловить лише
  `serve.space_tracks` (`_drop_foreign_roots`): `normalize` чистий і реєстру не бачить. Усе це мовчки дає `root: None` (шлях
  простору), без попередження.
- **`normalize(raw, space_path, roots=True)`** має третій параметр: `roots=False` не перевіряє корені (кожен `root: None`) — для
  `GET /api/spaces`, якому потрібні лише `id`/`label`/дефолт; ⛔ перевірка кореня — це `realpath` по кожному напрямку, а корінь
  може лежати на відімкненому томі, тож список просторів не мусить його чекати. Звідси відоме обмеження: корені перевіряються на
  `/api/tasks` і при створенні задачі, не на `/api/spaces`.
- **`legacy_tracks(cfg)` повертає трійку** `(tracks, default_id, fallback_root)` (§6.1), а `track_root` для ЛІГИ йде через
  `tracks.legacy_root`, не через `find`: адаптер перелічує лише id за `ID_RE`, а 0.14.0 шанував власний корінь будь-якого ключа.
  Перелік адаптера не обмежений `MAX_TRACKS` (репо 21-го ключа 0.14.0 теж віддавав).
- **`of_task` повертає збережений РЯДОК** (`track`, інакше `profile`) без звірки з `ID_RE` (§6.2); порожній чи не рядок `track` не
  затуляє валідний `profile`. `label_tag(tracks, task, legacy=False)` має прапорець `legacy` (ЛІГА: `_LEGACY_LABELS.get(v, v)` без
  звірки з переліком); обидва шляхи проходять правила мітки: значення з комою чи довше за 32 знаки дає «без похідної мітки», бо
  діалог правки мітки заповнюється поточними й не пройшов би `bad-tags`.
- **`profile` у звичайному просторі — поблажливий** (§6.7, доданий на ревʼю Task 4: скіл пайплайну шле `"profile": "united"`): не
  рядок — 400 `bad-profile`; рядок, що є напрямком простору, — напрямок; будь-який інший — ігнорується, як у 0.14.0. Суворий лише
  `track`. Конфлікт `track` ≠ `profile` — `bad-track` лише коли `profile` справді був би використаний.
- **`_TrackView`** (немає в спеці): напрямки одного простору рахуються раз за запит і ліниво; простір передається явно. ⛔ Урок
  ревʼю: проміжна версія мітила рядки `?all=1` щодо простору того, хто кличе, і підпис задачі ЛІГИ з боку звичайного простору
  виходив сирим id; тепер кожен рядок — щодо СВОГО простору.
- **`?ds=`: знайдений напрямок говорить сам** — його `ds` (`''` = без `?ds=`); не знайдений — збережене значення як є, як 0.14.0
  (еталон `page-none-project.html` тримає `?ds=tool&sp=…` для задачі звичайного простору). Не рядок — `''` (0.14.0 рвав
  зʼєднання).
- **`profile_repos` лишилась тонкою обгорткою над `tracks.legacy_repos`** (§5 це дозволяв): на ній тримається `_liga_flow`, `track_repo`
  й тести, що її підміняють; піде в 4d-4. `_liga_flow` дивиться лише на `profile`, не на `track` (шлях 409 `no-integrations-space`) —
  теж до 4d-4.
- **Нумерація «Свідомих відмінностей» вище збита** (1, 2, 3, 5, 6, 4): правда — список у `CHANGELOG.md [0.15.0]`, де вони пронумеровані
  по порядку й доповнені: коди `bad-track`/`unknown-track` — лише за ключем `track` (§6.7); `roots_in_use` і `plan` у `bin/roots.py`
  більше не падають на числовому профілі; числовий профіль на сторінці задачі не рве зʼєднання; `?ds=` і `?all=1`, як вище.
- **Порожній список `tracks: []` у `space.json` ЛІГИ адаптер НЕ вимикає** (рішення фінального ревʼю; текст до нього казав навпаки):
  порожній чи такий, що після `normalize` порожній, — для ЛІГИ це «власного списку нема», діє адаптер (інакше все мовчки
  спорожніло б: спільний корінь, нема репо, мітки малими літерами, нема `united`). Для звичайного простору порожній список — нема
  напрямків. ⛔ Непорожній власний список ЛІГИ — вона стає звичайним простором із ним: семантика адаптера закінчується (невідомий id більше
  не падає в спільний корінь; «будь-який рядок» як напрямок не приймається), `design_work_roots` і `profile_repos` ігноруються. Це
  свідома межа: міграція 4d-3 мусить записати все разом (див. поправку контролера в плані).
- **Корені перевіряються лише при створенні задачі** (`_TrackView.tracks` → `track_root`/`track_repo`); мітки, `?ds=` і `/api/*` читають
  напрямки без перевірки коренів (`_TrackView.lite`).
- **`from` рахується проти справжньої теки задачі** `<корінь напрямку>/<id>`, а не `<шлях простору>/<id>`: джерело не містить її, і вона не
  містить джерела (`from-contains-space`); «вже є» — теж за нею (`task-dir-exists`).
- **`bin/state.py`:** шапка тепер «Напрямок:» (була «Профіль:»), нічого її не парсить.
- **Знімок 0.14.0** (`tests/fixtures/tracks/before-4d1.json`) заморожено: генератор `tests/make_before_4d1.py` описує 0.14.0, його
  охорона fail-closed, і його НЕ запускають повторно на новому коді. Живий тест — `tests/live/tracks.test.mjs` (`PORT_BASE` 23000).
