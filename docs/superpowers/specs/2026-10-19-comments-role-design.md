# Етап 2b-2: універсальна роль `comments` і модуль `supabase-comments`

Дата: 19.10.2026 · репо продукту `neodisa/deai-canvas` · реліз **0.4.0**.
Попередні: 2a (`2026-10-14-modules-2a-design.md`), 2b-1 (`2026-10-16-vercel-publish-design.md`).

## Проблема

Командні коментарі є лише в зашитому шляху ЛІГА: адреса й ключ Supabase вшиті в код, спільний
проєкт на всіх, вкладка «Команда» — лише в просторі з `integrations`. Людина зі своїм сервісом
коментарів підключити його не може; іншого сервісу, ніж Supabase, ядро не знає взагалі.

## Мета 0.4.0

- Роль `comments` — **універсальний контракт**, що не залежить від сервісу: будь-який модуль, який
  його виконує, дає командні коментарі в канвасі, на «Огляді», в опублікованих превʼю й агенту.
- Перший вбудований модуль — `supabase-comments` (власний проєкт людини).
- Документ «як написати модуль коментарів» — щоб людина чи агент згенерували модуль під свій
  сервіс (PocketBase, Firebase, власний API…). Підключення **своїх** модулів із теки простору —
  етап 3 (діалог довіри); у 0.4.0 — лише вбудовані.
- Зашитий шлях ЛІГА не змінюється (відповіді й збірки побайтно ті самі).

Поза 0.4.0: скриншоти до коментарів (сховище файлів), Teams і дашборд (модулі ЛІГА, етап 4),
локальні коментарі для агента лишаються в ядрі як є (`/api/local-comments`).

## Контракт ролі `comments`

Модуль складається з двох половин.

### 1. Браузерний адаптер

`module.json` оголошує `"client": ["<файл>.js", …]` — файли з теки модуля, що вантажаться в
сторінку по порядку (≤ 8 файлів, кожен ≤ 512 КБ, імʼя `^[A-Za-z0-9_][A-Za-z0-9_.-]{0,63}\.js$`,
лише звичайні файли, без симлінків; інакше `bad-manifest`). Останній файл реєструє фабрику:

```js
window.DeaiComments = { create(cfg) { return store; } };
```

`cfg` = `{...client_config, channel, onChange}`; `store` — сховище CommentLayer:

| метод | контракт |
|---|---|
| `ready` | `Promise`, що завершується після першого завантаження (необовʼязково) |
| `load()` | поточний масив коментарів (синхронно, з кешу) |
| `save(comments)` | `Promise`; зберегти весь масив (upsert за `id`) |
| `remove(ids)` | `Promise`; жорстко видалити (необовʼязково) |
| `subscribe(fn)` | `fn(comments)` на зовнішні зміни (необовʼязково; realtime) |
| `close()` | звільнити опитування/зʼєднання сховища (необовʼязково); кличуть `CommentLayer.destroy` і «Огляд», коли запуск застарів |

Коментар — форма CommentLayer: `{id, author, text, status, fp, htmlSnapshot, meta, bornV,
resolvedV, resolveReason, ts}`. Канал (`channel`) ізолює коментарі задачі.

### 2. Серверні функції (`server.py`)

| функція | контракт |
|---|---|
| `client_config(ctx) -> dict` | ПУБЛІЧНА конфігурація для сторінки (адреса сервісу, публічний ключ) |
| `list(ctx, channel) -> [коментар]` | читання для агента (`inbox`) |
| `resolve(ctx, channel, id, reason) -> None` | закрити коментар (агент) |
| `check(ctx)` | як у всіх модулів |

- `client_config` перевіряє ЯДРО: JSON-обʼєкт ≤ 4 КБ, рядки/числа/булеві, без вкладених; жодне
  значення секрету модуля, крім позначених `"public": true` у маніфесті, не може в ньому
  зʼявитися (інакше `module-error`). `public` — новий необовʼязковий прапорець налаштування типу
  `secret`: значення зберігається поза `space.json` (як секрет), але може потрапити в сторінки
  (публічний ключ Supabase за задумом публічний — його захищають правила доступу сервісу).
- Канал задачі: `deai/<space-id>/<task-id>` (внутрішній — `…/internal`); `channel` модуль
  отримує готовим і не будує сам.
- `list`/`resolve` — тайм-аут виклику `CHECK_TIMEOUT`-подібний (10 с), помилки — як у ролі
  `publish` (`module-error`, коди модуля).
- `resolve` мусить бути ІДЕМПОТЕНТНИМ (повторне закриття вже закритого — не помилка) і ДІЄВИМ (після нього
  `list` віддає коментар зі `status: "resolved"`): агент не перечитує сервіс після закриття й вірить відповіді.
  `id` для `resolve` — лише `[A-Za-z0-9][A-Za-z0-9_.:-]{0,199}` (формати CommentLayer: UUID чи `c-<цифри>-<base36>`):
  ядро не передає модулю інших; `list` з іншим `id` відкидається. Текст помилки модуля ядро очищає від керівних
  і невидимих символів перед показом.

## Ядро

- `ROLES_CALLED += ('comments',)`. Постачальник `comments`: явно ввімкнений модуль → він;
  простір із `integrations` без модуля → `'legacy'` (зашитий Supabase ЛІГА); інакше `None`
  (лише локальні коментарі агенту). Неявного типового нема. `capabilities.comments`.
- `GET /api/module-client/<module-id>/<file>` — роздача файлів адаптера: лише вбудовані модулі,
  лише файли зі списку `client` маніфесту, `text/javascript; charset=utf-8`, `nosniff`, з тим
  самим захистом шляху, що `/published` (без симлінків, обхід дескрипторами де можливо).
- Сторінка задачі (`/commented?ch=project`), постачальник-модуль: ядро вставляє
  `comment-layer.min.js`, файли адаптера модуля, `window.__deaiCommentsCfg = {…client_config,
  channel}` і завантажувач, що створює CommentLayer з `storage: DeaiComments.create(cfg)`.
  `'legacy'` — як сьогодні (байт-у-байт); `None` — пониження до `local`, як сьогодні.
- «Огляд» (`/api/comment-config?ch=project`): для модуля — `{ch:'project', module, client:[адреси],
  config, channel, version, user}`; `overview-comments.js` вантажить адаптер модуля замість
  зашитого CDN Supabase (для `'legacy'` — як було).
- Опубліковані превʼю: `build_preview(..., comments=<провайдер>)` — для модуля копіює
  `comment-layer.min.js` і файли адаптера в `publish/comment-layer/` і вставляє той самий
  сніпет із `client_config`; і `static-publish`, і `vercel-publish` публікують із коментарями,
  коли в просторі є постачальник `comments` (зараз — завжди без). ЛІГА-збірка побайтно та сама.
- Агент: `bin/inbox.py` і серверне читання проєктних пінів для простору з модулем ідуть через
  `list`/`resolve` модуля (а не через зашитий REST); для `'legacy'` — як було.
- UI: вкладка «Команда»/аудиторія `project` і режим коментарів `project` доступні, коли
  `capabilities.comments` не `null` (а не лише за `integrations`); `noOutward` не чіпаємо.

## Модуль `supabase-comments`

```json
{"api": 1, "id": "supabase-comments", "name": "Supabase", "version": "1.0.0",
 "roles": ["comments"], "client": ["supabase.min.js", "adapter.js"],
 "settings": [
   {"key": "url", "type": "text", "label": "Адреса проєкту (https://<ref>.supabase.co)", "required": true},
   {"key": "key", "type": "secret", "public": true, "label": "Публічний ключ (anon / publishable)", "required": true}
 ]}
```

- `supabase.min.js` — supabase-js **2.110.0** (MIT), UMD-збірка без змін, з рядком ліцензії;
  жодного CDN у просторах із модулем.
- `adapter.js` — `DeaiComments.create(cfg)` поверх supabase-js: таблиця `comments`, фільтр
  `project_id = channel`, upsert за `id` з повторами, видалення в межах каналу, realtime
  `postgres_changes` → перечитування (як `CommentLayerSupabase`).
- `schema.sql` у теці модуля (таблиця `comments`, RLS, тригери незмінного `project_id` і
  обмеження видалення, публікація realtime) — людина один раз виконує в SQL-редакторі свого
  проєкту; модуль схему НЕ змінює (для цього потрібен сервісний ключ — його модулю не дають).
- `server.py` (stdlib): REST `<url>/rest/v1/comments` з заголовками `apikey`/`Authorization:
  Bearer <key>`; `list` — `project_id=eq.<channel>`; `resolve` — `PATCH` `status/resolve_reason`;
  `check` — `GET …?select=id&limit=1`: 200 → `ok`; 401/403 → `bad-key`; 404 чи помилка
  «relation does not exist» → `no-schema` з підказкою виконати `schema.sql`; мережа →
  `network`. `url` — лише `https://`, хост — DNS-імʼя (та сама перевірка, що в ядрі для
  `url`-модулів); власні домени Supabase дозволені. Ключ іде лише в заголовки запитів до `url`.

## Межі

- Правила доступу схеми відкриті: хто має публічний ключ (а він у кожній опублікованій сторінці),
  той читає й пише коментарі цього проєкту. Рекомендація — окремий проєкт сервісу на команду.
- Адаптер виконується в сторінках канваса (той самий origin, що API канваса). Тому в 0.4.0 —
  лише вбудовані модулі; свої (етап 3) — лише після діалогу довіри, і їхній код у сторінках —
  частина того, чому людина довіряє.
- Локальні коментарі агенту лишаються в ядрі; модуль їх не замінює.
- Локальний перегляд опублікованого (`/published/…`) іде в пісочниці з непрозорим origin (`Origin: null`): сервіс коментарів мусить дозволяти CORS і для такого походження (`Access-Control-Allow-Origin: *`), інакше піни в цьому вигляді не працюють (на справжньому хостингу запити йдуть з origin сторінки). Пісочниця має `allow-modals`: без нього `prompt()`/`confirm()` шару коментатора повертали б `null`/`false` (автори були б «Anonymous», «Видалити» нічого не робило); `allow-same-origin` лишається відсутнім.

## Документ для авторів модулів

`docs/modules/comments.md` (англійською й українською коротко): контракт обох половин, форма
коментаря, канал, прапорець `public`, приклад мінімального модуля (адаптер у памʼяті +
`server.py` з REST до власного API), як перевірити його тестами ядра.

## Перевірка

- Ядро: маніфест (`client`, `public`), постачальник/`capabilities.comments`, роздача файлів
  адаптера (захист шляху, лише оголошені файли), сніпет сторінки/«Огляду»/збірок для модуля,
  ЛІГА побайтно та сама, `client_config` без непублічних секретів, `inbox` через модуль.
- **Доказ універсальності:** тестовий модуль `memo-comments` (фікстура в
  `tests/fixtures/modules/memo-comments/`; адаптер синхронізує коментарі з маленьким тестовим
  HTTP-сервером на `127.0.0.1`) проходить ту саму наскрізну перевірку, що й Supabase. Живий
  сервер тестів отримує додаткову теку модулів через змінну оточення `DEAI_EXTRA_MODULES`
  (лише для тестів; модулі з неї вважаються вбудованими — оточення контролює сама людина, що
  запускає сервер).
- `supabase-comments`: підставний REST Supabase в процесі (жодного реального запиту), `check`
  (ok, bad-key, no-schema, network), `list`/`resolve`, ключ ніде, крім заголовків до `url`.
- Node: адаптер Supabase проти підставного клієнта supabase-js; UI-гейтинг вкладки «Команда».
- Живий: простір із модулем `memo-comments` (без мережі) — пін у канвасі видно на «Огляді» й у
  опублікованому превʼю `/published/…`; простір ЛІГА — без змін.

## Відхилення (стан на 0.4.0)

Що збудовано інакше (чи додатково) проти тексту вище; усе звірено з кодом.

**Ядро (`app/deai_modules.py`)**

- **`provider('comments')` може кидати помилку замість `'legacy'`** (приватність: `'legacy'` — спільний Supabase ЛІГА, куди піни
  несуть знімки приватних макетів). У просторі з `integrations`: нечитабельний `space.json` — `space-json-unreadable`;
  явно ввімкнений запис, чий модуль відсутній, не завантажився чи має невизначену роль, — `module-error`
  (`COMMENTS_MODULE_BROKEN`); `'legacy'` лише тоді, коли такого запису нема. `capabilities()` лишається тотальною: у цих
  випадках `comments: None` + `error`, ніколи `'legacy'`. Для `publish` усе як було.
- **`client` у маніфесті**: на додачу до тексту вище — жорстке посилання (`st_nlink != 1`) і імʼя, що не збігається з диском
  буква в букву (ФС без регістру), — `bad-manifest`; дубль імені — теж.
- **`DEAI_EXTRA_MODULES`**: модуль із `id`, що вже є вбудованим, **не потрапляє в `catalog()`** — він у `shadowed()` зі
  `status='error'` (`bad-manifest`), його `server.py` не виконується (у плані було «інший — `status:'error'`» у каталозі). Сервер
  друкує ОДИН рядок у stderr при старті: `DEAI_EXTRA_MODULES: додаткова тека вбудованих модулів '<тека>' (тестовий шов; модулі
  звідти діють як вбудовані)`; без змінної (чи порожньої) рядка нема. Ключ кешу `capabilities()` враховує теки джерел і
  відбитки `module.json`, `server.py` та файлів `*.js` кожного модуля.
- **`comments_client`**: перевірка суворіша за спеку — копія модульного обʼєкта (перевіряється й віддається саме копія); ключі
  теж скануються; секрет шукається в сирому вигляді, у `repr`/JSON-екрануванні, URL-кодуванні й після
  `unquote`/`unquote_plus`; «непублічні» — оголошені без `public` **і** ключі `secrets.json`, яких у маніфесті нема; самотні
  сурогати й величезні цілі — відмова `module-error`, а не сирий виняток. Усі тексти відмов фіксовані (без значень секретів).
  Це охоронець від ВИПАДКОВОГО витоку, а не межа довіри (модулі вбудовані).
- **`channel_for`**: id простору — за `spaces.SPACE_ID_RE`, id задачі — непорожній рядок без `/` і керівних символів (інакше
  `a`+`b/t` і `a/b`+`t` дали б один канал). `channel` і `onChange` у `cfg` адаптера — ЯДРА: однойменні ключі
  `client_config` їх не перекривають.
- **Таймаути**: `client_config` і `check` — `CHECK_TIMEOUT` = 5 с (далі `check-timeout`), `list`/`resolve` — `COMMENTS_TIMEOUT`
  = 10 с. `supabase-comments` ставить 10 с на кожен свій запит, тож на повільному зʼєднанні `module-enable` відповідає
  `check-timeout` (модуль при цьому працює); `check-timeout` — відповідь ядра, не вердикт `check`.

**Сторінки, «Огляд», вкладка «Команда»**

- **Зламаний модуль у сторінці** (`/commented?ch=project`): не 5xx й не мовчазний перехід на спільний сервіс, а локальний
  шар коментатора з видимою приміткою `командні коментарі не піднялись (<код>), показано локальні` (код — лише код відмови
  ядра); вкладок аудиторій тоді нема. `/api/comment-config` віддає центральну відповідь модулів (`module-error`,
  `bad-settings`…), «Огляд» показує тост із кодом.
- **`hasTeamComments`**: відсутній ключ `comments` у `capabilities` (відповідь форми 2а від сервера, якого не
  перезапустили) — «не знаємо», рішення за `integrations !== false`; «нікого» каже лише явний `null`.
- **Завантажувач сторінки й «Огляду»**: сховище без `load`/`save`, `create`, що кинув, і відхилений `ready` — банер
  «Коментарі недоступні», а не тихо мертвий шар; `ready` необовʼязковий (`Promise.resolve`). «Огляд» кешує фабрику ЗА МОДУЛЕМ
  і перед завантаженням скидає глобал `window.DeaiComments` присвоєнням (не `delete`). `close()` кличуть
  `CommentLayer.destroy` і «Огляд», коли запуск застарів.

**Опубліковані превʼю**

- **`publish_comments(space, tid, module_publish=)`** — одне рішення на публікацію, з `provider('comments', простір)`:
  модуль → його канал на всіх трьох шляхах; **`'legacy'` у збірці МОДУЛЯ публікації (`static-publish`, `vercel-publish`) —
  без коментарів** (зашитий Supabase ЛІГА не їде в превʼю, яке зібрав модуль), на шляху ЛІГА — як було; відмова
  (`ModuleError`) — без коментарів + `comments_unavailable: <код>` у відповіді публікації (UI показує рядок у вікні
  попереджень), публікація йде далі. ЛІГА-простір із нечитабельним `space.json` тепер публікує без спільних коментарів.
- **Мітка збірки**: `build_preview(..., build='legacy'|'module')` — обовʼязковий іменований аргумент; пишеться ОСТАННІМ ключем
  `manifest.json` (`"build"`). `ops/reseal_gate.py` перепечатує й деплоїть лише збірки `legacy` (старі збірки без мітки — за
  запасним правилом: ОБИДВА бандли ЛІГА в `comment-layer/`). Це єдина зміна ЛІГА-збірки проти «побайтно тієї самої»: у
  маніфесті зʼявилось поле `build`; оболонка читає лише названі поля.
- **`comment-layer/`** модульної збірки — рівно `comment-layer.min.js` і оголошені в `client` файли (читаються
  `open_module_client` ДО `rmtree` попередньої збірки); імʼя файла, що збігається з бандлом ядра (без урахування регістру), —
  `module-error`. `bin/import_preview.py` знімає сніпет коментарів модуля (із гейтом і без) і зупиняється, якщо в сторінці
  лишився `__deaiCommentsCfg`/`DeaiComments`.
- **`/published`**: у CSP-пісочницю додано **`allow-modals`** — без нього `prompt()`/`confirm()` шару коментатора повертали б
  `null`/`false` (автори «Anonymous», «Видалити» нічого не робило); `allow-same-origin` відсутній, origin непрозорий
  (`Origin: null`), тож у цьому вигляді немає й `localStorage`/cookies, а сервіс коментарів мусить дозволяти CORS для `null`.

**Агент (`bin/inbox.py`, `bin/state.py`, маршрут `/comments`)**

- Рішення бере `ProjectComments(space)` (простір — явним аргументом, один раз на запит чи команду CLI); простір запиту, що не
  зафіксований, — `broken`, а не `'legacy'`; нікого (`off`) — як простір без інтеграцій; `ModuleError` — лише локальні піни й
  повідомлення, ніколи спільний Supabase.
- **`list`**: форма CommentLayer → рядки REST ЛІГА (`agent_pin`): лише відомі поля потрібних типів, `meta.shot` відкинуто,
  однорядкові поля без переносів, керівні й невидимі символи (C0/C1, U+00AD, U+034F, U+061C, U+180B–180F, U+200B–200F,
  U+2028/9, U+202A–202E, U+2060–206F, U+3164, U+FE00–FE0F, U+FEFF, U+FFA0, U+FFF9–FFFB, символи-теги, сурогати) вирізано;
  не-список — `module-error`; зіпсований елемент і дубль `id` — `skipped`, понад 5000 коментарів чи 2 МіБ — `truncated`
  (`inbox` і `state` кажуть про обидва). `id` — за білим списком `[A-Za-z0-9][A-Za-z0-9_.:-]{0,199}`, інший — `skipped`.
- **`resolve`**: модулю йде лише `id` із білого списку; для піна модуля `--it` не потрібен (лише ЛІГА й локальним), короткий
  префікс id (< 6) закриває лише як повний id. Контракт — ідемпотентність і дієвість (див. вище). Тексти помилок модуля
  очищаються централізовано (`agent_error`: один рядок, ≤ 300, без керівних і невидимих символів, без сурогатів) і ще раз у
  місцях друку `inbox`.

**Модуль `supabase-comments`**

- `list` просить `limit=5001` (`MAX_ROWS + 1`): зайвий рядок ядро відкидає й заявляє `truncated`, а не віддає «повний» список
  мовчки. `resolve` — `PATCH … Prefer: return=representation` з ОБОМА фільтрами (`id` і канал): 0 змінених рядків —
  `module-error` «коментар не знайдено», відповідь без підтвердження — теж помилка; повторне закриття — не помилка,
  `resolved_v` не чіпається (номера ітерації в контракті нема).
- `check`: `ok` / `bad-key` (401, 403) / `no-schema` (404 чи код PostgREST `42P01`/`PGRST205`) / `network` / `supabase-error`;
  звичайні збої — вердикт `{ok: false, error, detail}`, а не виняток. `url` — лише `https://<DNS-імʼя>[:порт]`, без шляху,
  параметрів, облікових даних, IP й `localhost`; редиректи не виконуються; ключ іде лише в заголовки `apikey` і
  `Authorization` запитів до `url`.
- `supabase.min.js` — рівно 2 байти U+001F у вендореному файлі (виняток у `tests/no-control-bytes.test.mjs`); SHA-256 приколото.
- Реальний Supabase у CI не запускається: підставний REST-сервер у процесі й підставний клієнт supabase-js у node.
- Скриншоти до коментарів у ролі не підтримуються (сховища файлів нема): знімок, який додає шар, їде всередині коментаря
  (`meta.shot`), агент його відкидає; шар підтягує `html2canvas` із jsDelivr при створенні піна (було до модулів).
